## 1. 范围

F09 把规则变更流程（需求文档 5.8）加进 troy-mode 的入口技能（F07）。有了它，收到"加一条规则 ……"时，主会话会：

1. 当请求没有说明时，问 Troy 5.8 第 1 步需要的内容：规则本身，以及它只适用于这个项目还是所有 troy-mode 项目；
2. 让架构师选出可行的最强执行方式，并找出违反这条规则的现有代码（5.8 第 2 步，D79）；
3. 给 Troy 看一份提案，Troy 的回答既批准这条规则，也做出 5.8 第 4 步的选择（D82）；
4. 对这个项目的规则，用一个 `[rules]` PR 合入规则表、检查配置，以及现有违规的基线（5.8 第 3 步，D80、D81）。如果规则需要改架构，架构改动先在它自己的 `[docs]` PR 里合入。如果 Troy 选择现在就修现有代码，清理 PR 跟在后面；
5. 对适用于所有项目的规则，写一份给 troy-pstack 的提案，Troy 同意后在那里开一个 issue（D83）。

F09 还让项目可以修改或废止自己的规则，并在 troy-check 的配置允许时，通过一条项目规则调整 troy-mode 的规则（D84）。F08 的复盘会把 Troy 选中的规则交给这个流程。

F04 说 `docs/rules.md` 和 `.troy-mode/**` 不属于任何角色，只有 troy-init 和这个流程会改它们（F04 第 3 节）。F07 D62 把除了它自己的 `[flow]` 设置之外的所有规则变更都留给了 F09。F09 不新增技能，而是扩展 F07 的技能和引擎。它按 Q10 对每个功能的规定，用一个 PR 合入。

## 3. 引擎

### 3.1 命令

```text
python troy_flow.py rule-id   [common options]
python troy_flow.py rule-row  --id <P-ID> --rule-file <path> [--retire] [--date <YYYY-MM-DD>] [common options]
python troy_flow.py snapshot  --role rules [common options]
```

| 命令 | 作用 |
| --- | --- |
| `rule-id` | 读取 `origin/main` 上的 `docs/rules.md`，给出下一个可用的 P 编号、每一条 P 规则行及其是否已废止，以及每条 P 规则在配置文件和依赖文件里的基线行（第 5.3 节）。 |
| `rule-row` | 在 `docs/rules.md` 及其镜像里写入一条 P 规则行。新编号加在最后一条 P 规则行后面，已有编号替换原来的行，`--retire` 把它标为已废止（第 6 节）。新规则的 Since 单元格写这个日期，修改的规则保留原来的日期。两个文件都升到下一个主版本，状态改为 "Approved by Troy on <日期>"，并各加一行修改记录（D82）。`--rule-file` 是一个 JSON 文件，包含中英文的 Rule、Type 和 Enforced by 单元格以及修改记录的文字。 |
| `snapshot --role rules` | F07 快照的一个新角色：主会话自己编写 `[rules]` PR 的工作。它的范围是 `config` 和 `dependencies` 两个路径类别，也就是 `[rules]` PR 可以改动的内容（F02 D9）。`check-run` 会把其他任何路径标为问题。 |

- `check-run` 增加一条规则：对 `dependencies` 路径的改动，如果只是删除带 `baseline: P<nn>` 的行，就不算依赖问题。清理运行就这样删除它负责的文件的基线行，不需要 `--allow-dependency`（第 5.4 节）。
- `status` 增加下一步 `cleanup`（第 3.2 节）。`brief` 学会 AR6、DV5 和 TE6（第 7 节）。
- 和 F07 一样，引擎从不提交、推送或写 GitHub，退出码与 F07 相同。

### 3.2 状态和下一步

规则状态保存在 git 和 GitHub 上（F07 D58）：

| 内容 | 读取来源 |
| --- | --- |
| 项目的规则 | `origin/main` 上 `docs/rules.md` 里的 P 规则行 |
| 进行中的规则变更 | 标题为 `[rules] Add P01, ...`、`[rules] Change P01, ...` 或 `[rules] Retire P01, ...` 的开着的 PR，F07 像处理其他开着的 PR 一样接着做 |
| Troy 对现有代码的选择 | 规则表里这条规则最近一次变更的修改记录行，写的是 "Existing code: fixed by cleanup PRs." 或 "Existing code: fixed when touched." |
| 还要做的清理 | `origin/main` 上配置文件和依赖文件里带 `baseline: P01` 的行 |

当一条规则最近的修改记录行写的是 "fixed by cleanup PRs"、而它的基线行还在时，`status` 给出 `next.action` `cleanup`。接下来是下一个清理 PR（第 5.4 节），新会话也用同样的方式找到它。`cleanup` 排在开着的 PR 之后、功能循环的下一个阶段之前。

## 4. 流程

### 4.1 分派

| 请求，例如 | F09 怎么做 |
| --- | --- |
| "加一条规则：源代码里不许有 print 调用"、"这个项目的一条规则：……" | 项目规则（第 5 节） |
| "所有项目的一条规则：……" | 适用于所有项目的规则（第 5.6 节） |
| "修改 P01 ……"、"废止 P02" | 第 6 节 |
| "在这个项目里，R03 的上限是 800 行" | 一条调整 R03 的项目规则（第 6 节） |
| Troy 在 F08 的复盘里选中的规则 | 按上面的方式逐条处理 |

当请求没有说明规则是给这个项目还是所有项目时，F09 只问 Troy 这一个问题，推荐"这个项目"。适用于所有项目的规则要改 troy-pstack，是更大的一步。

### 4.2 步骤

| 步骤 | 做什么 | 由谁 | PR | 合并者 |
| --- | --- | --- | --- | --- |
| 1. 询问 | 请求没给出时，问规则和它的适用范围 | 主会话 | 无 | |
| 2. 执行方式 | 可行的最强层级、具体的配置，以及现有的违规 | AR6 | 无 | |
| 3. 提案 | 给 Troy 的一条消息，以及 Troy 的回答 | 主会话 | 无 | |
| 4. 架构 | 只在规则需要改架构时 | AR6 的第二次运行 | `[docs] Change the architecture for P01` | F07 |
| 5. 规则 PR | 规则表、配置和基线 | 主会话，在 `snapshot --role rules` 之下 | `[rules] Add P01, <summary>` | F07 |
| 6. 清理 | 只在 Troy 选择现在就修现有代码时 | DV5 或 TE6，由 CR1 审查，测试另由 TM2 审查 | `[refactor] Apply P01 to <area>`、`[P01 test-fix] Apply P01 to tests` | F07 |

每个 PR 只有一个 commit，commit 标题就是 PR 标题（R01），检查通过后由 F07 合并（F07 第 8.6 节）。Troy 在第 3 步的回答就是批准，所以这个流程里没有 PR 需要再等 Troy（D82）。

## 5. 项目规则

### 5.1 执行方式（D79、D80）

5.8 第 2 步按从强到弱列出四个层级。在一个项目里，每个层级落在这里：

| 层级 | 在项目里可以是什么 | 落在哪里 |
| --- | --- | --- |
| 架构 | 模块边界或依赖方向，R07 的检查器从架构里读取它们。一条用一个表格单元格写不下的规则，写在架构的第 8 节"命名和编码规则"里。 | 架构师在规则 PR 之前开的 `[docs]` PR。Troy 和规则一起批准它。 |
| lint 或 CI 检查 | 语言包已经在运行的工具里的一条规则：Python 的 ruff 或 mypy，C/C++ 的 clang-tidy 或 clang-format。`.troy-mode/config.toml` 里的一项 troy-check 上限。项目自己的工作流 `.github/workflows/project-rules.yml` 里一个不需要环境的步骤，比如一个必须什么都找不到的 `git grep`。 | 规则 PR |
| 测试 | F09 不为项目规则提供（D80） | 无 |
| 角色说明 | P 规则行本身，类型为 Review，写明由哪个角色检查。每个角色都会读 `docs/rules.md`（F04 公共规则 3），审查者会检查写明自己的 Review 规则（第 7 节）。troy-mode 自己必须遵守的规则类型为 Process，F07 每次开始时都会读这些行。 | 规则 PR |

类型跟着层级走：lint 或 CI 检查是 Hard；像 R03 那样允许给出理由的是 Soft；角色说明是 Review 或 Process。

**AR6** 读取规则、`docs/rules.md`、架构，以及语言包的配置：`pyproject.toml`、`.clang-tidy`、`.clang-format` 和 `.troy-mode/config.toml`。它报告 `escalate`，因为由 Troy 决定，提案写在它的 Question 字段里：

- 可行的最强层级，以及为什么更强的层级不行；
- 写进表格的规则文字、它的类型和 Enforced by；
- 对每个配置文件的具体改动，或者架构改动；
- 违反这条规则的现有代码：对检查类规则，AR6 在整个仓库上运行检查，列出文件和数量；对审查类规则，它阅读代码；
- 如果选"现在就修"，它预计的清理 PR，每个都在 R03 之内。

AR6 不改任何文件。它通过 Bash 运行工具，用命令行选项打开这条规则，从不改配置。Troy 批准架构改动之后，AR6 再运行一次把它写进去，并附上 ADR，就像 AR3 处理依赖那样（F07 第 8.7 节）。

### 5.2 提案（D82）

给 Troy 的一条消息，用 Troy 的语言：

- 表格里会写的规则，中英文都有，带上 `rule-id` 给出的编号、类型和 Enforced by；
- 执行方式，以及为什么没有更强的层级可行；
- 规则 PR 会改的文件，以及架构 PR（如果有）；
- 违反它的现有代码，以及 5.8 第 4 步的选择和推荐：现在就用清理 PR 修好，或者只对新代码和改动的代码执行这条规则（第 5.4 节）。

Troy 的回答批准这条规则并做出选择，或者要求修改。要求修改时，把 Troy 的原话放进 Input 再运行一次 AR6，F09 给出新的提案。Troy 批准之前什么都不写。

### 5.3 规则 PR

在从 `origin/main` 建出的 `troy-mode/rule-p01` 上，在 `snapshot --role rules` 之下：

1. **规则表。** 主会话把这一行的中英文单元格写进一个 JSON 文件，运行 `rule-row --id P01 --rule-file <文件>`。修改记录行写明这条规则、Troy 的批准，以及 Troy 对现有代码的选择。
2. **配置。** 主会话按 AR6 的提案修改配置。
3. **基线。** 当现有代码违反一项检查时，这个 PR 还在工具自己的配置里豁免今天违规的文件：每个文件一行，每行都带注释 `baseline: P01`。在 Python 里，就是 `pyproject.toml` 里 ruff 的 `per-file-ignores` 条目。这样这个 PR 和之后的每个 PR 都能通过 CI，而新文件从一开始就必须遵守这条规则。
4. **检查。** 运行 `check-run`，然后只暂存它列出的路径，以 `[rules] Add P01, <summary>` 提交。
5. **本地检查。** `troy-check pr`；如果改了某个工具的配置，再运行语言包的步骤，这样新规则和它的基线在推送之前就能通过。
6. **PR 和合并。** PR 说明写明 Why（Troy 的规则，用英文）、What（规则行、配置和基线的行数）以及 Checks。F07 推送、开 PR、等 CI，然后合并。

当一个工具没有 `[rules]` PR 可以改的按文件豁免方式时，比如 clang-tidy 的豁免写在源文件里，这条规则就没有基线。AR6 会在提案里说明。这时清理 PR 先做，规则 PR 在它们之后才打开检查。这样的规则不提供"只管新代码和改动的代码"这个选项。

### 5.4 现有代码（D81）

- **现在就修。** 规则 PR 之后，清理 PR 修好基线里的文件，每个都在 R03 之内，并在同一个 commit 里删除它负责的文件的基线行。源文件放在 `[refactor] Apply P01 to <area>` 里，由 DV5 编写、CR1 审查。测试文件放在 `[P01 test-fix] Apply P01 to tests` 里，由 TE6 编写、TM2 和 CR1 审查。主会话把文件分组，每个 PR 最多 5 个文件。直到不再有 `baseline: P01` 行之前，`status` 都会给出 `cleanup`（第 3.2 节）。审查类规则的清理，按 AR6 列出的文件以同样的方式进行。
- **只管新代码和改动的代码。** 基线保留。开发工程师或测试工程师改动基线里列出的文件时，要按这条规则修好这个文件，并删除它的基线行，就像 Q6 处理旧代码那样。这部分是 F04 里的书面说明（第 8 节），因为没有检查能看出一次改动是否碰到了这条规则的旧违规。

### 5.5 规则 PR 不能包含的内容

R02 不允许文档进入 `[rules]` PR，所以架构改动是在它之前的单独 `[docs]` PR（第 4.2 节）。源代码和测试也从不放进规则 PR：清理在它们自己的 PR 里进行。执行项目规则的测试不在 F09 里（D80）。

### 5.6 适用于所有项目的规则（D83）

适用于所有 troy-mode 项目的规则放在 troy-pstack 里，随新的插件版本发布（5.8）。F09 不改 troy-pstack。它为 troy-pstack 自己的流程准备好这项改动：

1. **AR6** 像对项目规则那样提出执行方式，另外写明 troy-pstack 里要改的文件：需求文档第 6 节里新的 R 行、规则模板、troy-check 里的一项检查及其测试，或者某个角色的代理文件。它还说明升级带来这条规则时，现有项目的代码会不会违反它。AR6 在插件文件夹里读这些文件。
2. **提案**按第 5.2 节发给 Troy，并询问是否在 troy-pstack 里开一个 issue。
3. **Troy 同意后**，F09 把提案用英文写进一个文件，用 `check-text` 检查，然后运行 `gh issue create --repo <owner>/troy-pstack --title "Rule proposal: <summary>" --body-file <文件>`。仓库取自插件文件夹的 `origin` 远程。项目这时不做任何改动。
4. **之后**，troy-pstack 通过它自己的设计和实现流程做出这条规则。新的插件版本通过 troy-init 的升级到达每个项目，升级会替换 R 行和 troy-check（F06 D54）。项目的副本比插件旧时，F07 的 `status` 会说明。

开 issue 会触及项目之外，所以总是需要 Troy 同意，就像创建仓库一样（F06 D52）。

## 6. 修改和废止规则（D84）

- **修改 P 规则**走同样的步骤，标题为 `[rules] Change P01, <summary>`。`rule-row` 替换这一行，保留它的 Since 日期，并在修改记录里写明改了什么。配置和基线行在同一个 PR 里修改。
- **废止 P 规则**的标题为 `[rules] Retire P01, <summary>`。`rule-row --retire` 保留这一行，在它的 Rule 单元格开头写上 "Retired on <日期>."。它的 Enforced by 单元格改为 "None"。这个 PR 删除这条规则的配置和基线行。废止的编号永远不再使用。废止不需要运行 AR6：主会话给 Troy 看这个 PR 会删除什么，Troy 同意就是批准。
- **R 规则**属于 troy-mode，troy-init 的升级会替换 R 行（F06 D54），所以项目从不修改它们。在 troy-check 的配置允许调整的地方，比如 R03 的上限、R11 的覆盖率下限或 R19 的署名模式，用一条 P 规则行来记录，例如 "P02: In this project, R03's limit is 800 changed lines."，规则 PR 同时修改配置。对 R 规则的其他任何改动，都是适用于所有项目的规则（第 5.6 节）。
- **`[flow] troy_approves_first`** 仍由 F07 自己的 `[rules]` PR 处理（F07 D62）。

## 7. 角色任务（F04）

| 任务 | 角色 | 什么时候 | 做什么 | PR |
| --- | --- | --- | --- | --- |
| AR6 规则执行方式 | 架构师 | 第 2 步，以及 Troy 批准架构改动之后的第 4 步 | 第 5.1 节。第一次运行不改任何东西。第二次写入架构改动及其 ADR。 | 无，然后是 `[docs] Change the architecture for P01` |
| DV5 清理 | 开发工程师 | 第 6 步 | 按这条规则修好任务简报列出的源文件，并删除它们的基线行。保持在 R03 之内。 | `[refactor] Apply P01 to <area>` |
| TE6 测试清理 | 测试工程师 | 第 6 步 | 对测试文件做同样的事 | `[P01 test-fix] Apply P01 to tests` |

- 审查者（AR2、TM2 和 CR1）也检查每一条 Enforced by 写明自己角色、类型为 Review 的 P 规则，并在意见里写出这条规则的编号。
- 开发工程师和测试工程师因为其他原因改动基线里的文件时，要修好它并删除它的基线行（第 5.4 节）。
- TE5 属于 F08 的设计，所以这个流程的测试工程师任务是 TE6。两者谁先合入都可以。

## 8. 对之前功能的改动

- **F01 模板。** 规则模板的说明描述 P 规则行：编号、已废止的行，以及 `baseline: P01` 注释。README 的 PR 种类增加 `[P01 test-fix]`。F01 的设计加一行修改记录。
- **F02 troy-check。** `test-fix` 标题接受 P 编号，例如 `[P01 test-fix] Apply P01 to tests`。F02 的设计加一行修改记录。
- **F03 `troy-check code`。** 对带 P 编号的 test-fix PR，R10 不去找功能的测试方案。R09 和 R10 把它当作"其他任何种类"。F03 的设计加一行修改记录。
- **F04 角色。** AR6、DV5 和 TE6，以及第 7 节的两条规则。结构测试统计新任务。F04 的设计加一行修改记录。
- **F07 入口技能。** 分派表把规则请求交给 F09。引擎增加第 3 节的命令、`rules` 快照角色、`check-run` 的基线规则和 `cleanup` 下一步。技能每次开始时读取类型为 Process 的 P 规则行并遵守它们。F07 的设计加一行修改记录。
- **F05 和 F06** 不改。F05 的 hook 不限制主会话的文件（F05 第 4 节），这个流程里的每个角色都在自己的范围之内。troy-init 的升级保留 P 规则行（F06 D54），也从不碰 `project-rules.yml`，因为 troy-init 并不拥有它。

F08 的设计也会改 F07 的引擎和技能。F08 和 F09 谁后合入，谁就 rebase 到先合入的那个之上。

## 9. F09 与需求的对应

| 需求 | F09 在哪里覆盖 |

## 10. F09 怎样检查

### 10.1 测试

测试用 `unittest` 和标准库。由另一个代理在代码写出来之前，根据这份设计来写，沿用 F07 的做法：一个临时 git 仓库，用本地裸仓库作 `origin`；一个假的 `gh`，从一个 JSON 文件提供 PR 和 issue，并记录每次调用。测试放在 `troy-mode/flow/tests/`，对 troy-check 和角色的改动在各自的测试套件里加测试。

| 分组 | 用例包括 |
| --- | --- |
| 规则编号 | P01 到 P03 之后、废止的 P04 之后，以及没有 P 规则行的表里，下一个可用的编号。在 TOML 和 YAML 文件里按规则找到基线行。 |
| 规则行 | 中英文的新行，带 Since。替换的行保留 Since。废止的行。两个文件都升到下一个主版本、改状态，并各加一行修改记录。会破坏表格的单元格被拒绝。 |
| 快照和检查 | `rules` 角色只能改配置和依赖文件。文档、源代码或测试路径是范围问题。只删除 `baseline:` 行的依赖改动不需要 `--allow-dependency` 也能通过，同时增加或修改了一行的就不行。 |
| 状态 | 还有 "fixed by cleanup PRs" 的基线行时给出 `cleanup`，"fixed when touched" 时不给出，开着的 `[rules]` PR 先接着做。 |
| 任务简报 | AR6、DV5 和 TE6：它们的标题、Read first 和检查。 |
| troy-check | `[P01 test-fix]` 能解析，只能改测试和依赖。对 P 编号，R10 不找测试方案。 |
| 角色和技能 | 代理文件和 F04 结构测试里的 AR6、DV5 和 TE6。审查者关于 Review 规则的那一行。技能写出规则流程的步骤，并读取 Process 规则。 |

### 10.2 埋 bug

代码通过之后，在一份临时副本里一次埋一个 bug，每个都必须让某个测试失败。这些 bug 包括：重用了废止的编号、规则行只写了英文、修改规则时改了 Since、版本只升了一个次版本而不是下一个主版本、`rules` 角色可以改文档、同时增加了一行的基线删除通过了 `check-run`、"fixed when touched" 时也给出 `cleanup`、最后一条基线行删掉之后仍给出 `cleanup`，以及 `[P01 test-fix]` 可以改源代码。数量写进 PR 说明。

### 10.3 试运行（D85）

PR 开出之前，F09 在 Troy 电脑上的嵌套 `claude -p` 会话里运行，troy-pstack 从 PR 分支加载，用的是 `ZJUCao/troy-mode-trial`，和 F07 的试运行一样。试运行的提示给出 Troy 的回答。只有 Troy 在聊天里同意之后才开始。

1. **升级。** troy-init 的升级通过它自己的 PR 带来新的 troy-check。
2. **一条现有代码违反的 lint 规则**，例如"异常消息里不用 f-string"，由 ruff 的 EM102 检查，`counting.py` 现在就违反它。AR6 提出提案，Troy 的回答选择"现在就修"，规则 PR 带着一条基线行合入。那个会话结束。
3. **接续。** 一个新会话收到"继续"，从 `status` 找到清理，由 DV5 编写、CR1 审查的 `[refactor]` PR 修好这个文件并删除基线行。
4. **一条审查类规则**，例如"每条错误消息都写明它涉及的文件"。AR6 找不到能检查它的工具，规则 PR 只加这一行。
5. **废止**这条审查类规则，不运行任何角色。
6. **一条适用于所有项目的规则。** AR6 写明 troy-pstack 里要改的文件。Troy 的回答（来自提示）不同意开 issue，所以不在 troy-pstack 里开任何东西。

按 F07 试运行的花费估算，大约运行 5 次角色（AR6 三次、DV5、CR1），约 4 到 7 美元，另外大约 5 个 PR 各用几分钟 Actions 时间。

### 10.4 状态

| 时间点 | 需求文档 7.2 中 F09 的状态 |
| --- | --- |
| F09 的 PR 在试运行通过后合入 | 在示例项目上跑通：troy-mode 给一个临时 GitHub 项目加了两条规则，一条由 lint 检查，带基线和一个清理 PR，一条在审查中检查；废止了其中一条；并提出了一条适用于所有项目的规则。还没有在真实项目上用过。 |
| 试点（F11）增加或修改一条规则 | 在真实项目上用过 |

如果试运行没能在 PR 之前完成，状态就是"已编写"，直到试运行完成。状态更新单独开一个 PR。
