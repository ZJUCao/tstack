## 1. 范围

F11 用 troy-mode 带 Troy 的一个小的真实项目走完一个版本。这是流水线的第一次完整运行（Q10），也是 troy-mode 的功能第一次用在真实项目上，而不是临时仓库 `ZJUCao/troy-mode-trial`。

F11 交付：

1. 试点项目的第一个版本，完全通过 troy-mode 的流程做出来、发布，并由 Troy 在自己的设备上验收（第 4 节和第 5 节）；
2. troy-pstack 里的一份试点报告，列出发现的问题、候选规则，以及每一步的时间和花费（第 8 节，D97）；
3. 通过 troy-pstack 自己的流程，修复挡住试点的问题（第 7 节，D96），其他每个问题在 troy-pstack 里开一个 issue；
4. 更新试点真正用到的每个 troy-mode 功能的状态（第 9 节，D100）。

F11 自己不写 troy-mode 的代码。修复是 troy-pstack 里各自的 PR。试点项目的代码、文档和 PR 属于那个项目，由 troy-mode 来做，不由 F11 来做。

## 2. 前提条件

满足下面全部条件，试点才开始：

1. **F08 和 F09 已合入**，并且试运行通过：两者的状态都是"在示例项目上跑通"。
2. **F10 已合入**（F10 设计 D91），这样 Troy 有指南可用，troy-pstack 的版本是 0.2.0 或更新（F10 设计 D89）。
3. **Troy 的 Claude Code 运行的是这个版本。** Troy 按 `01-install.md` 安装或更新 troy-pstack，并重启 Claude Code。在试点文件夹里新开一个会话，能看到 `/troy-pstack:troy-mode`。
4. **合并权限**已经加到试点项目的 `.claude/settings.local.json` 里（D98，F10 设计第 4.3 节）。
5. **工具**：`gh auth status` 通过；如果是 Python 项目，Miniforge 和 uv 在 troy-init 能找到的位置（F06 设计 5.4）。
6. **仅对 C/C++ 项目**：第 3.3 节的 F07 修复已合入。

F11 会话（第 6.3 节）逐项检查，在 Troy 开始之前报告没通过的项。

## 3. 选择项目

### 3.1 什么样的项目适合试点

- **真实。** Troy 会用它的成果，这样 Troy 的设备测试和验收才有意义。
- **小。** 第一个版本能放进 4 到 5 个功能，每个都在 R03 的 500 行以内（D94）。
- **有现成的语言包。** Python 已经可用。C/C++ 要先做 F07 修复（第 3.3 节）。TypeScript/JavaScript 还没有语言包（Q1）。
- **在 Troy 的电脑上。** 它能在 Windows 11 上构建和测试，设备测试只需要 Troy 自己的设备。
- **除了 GitHub 和 Anthropic 不用别的外部服务**（需求文档第 8 节"隐私"），测试里也没有密钥。
- **一个私有 GitHub 仓库**，新的或已有的都可以。

### 3.2 候选项目（D93）

| 候选 | 是什么 | 试点会用到什么 | 需要先做什么 |
| --- | --- | --- | --- |
| 1. 一个新的小 Python 项目 | 一个 Troy 想要的命令行项目，从空文件夹开始。如果 Troy 没给想法，就做 Troy 以前的菜谱应用 `PrivateRecipes`（私房菜单）和 `MyMenu`（个人菜单）的 Python 命令行版：菜谱、一周的菜单和对应的购物清单，支持中英文。 | 从空文件夹开始的每一步：troy-init 创建私有仓库（F06 D52）、从零开始的需求文档和终端会话原型（Q9）、架构和它的系列问题、Python 语言包和它的环境、4 到 5 个功能走完全部六个 PR、第三个功能之后的那个问题（F07 D62）、版本测试计划、包含 Troy 在自己电脑上测试的发布、GitHub release，以及复盘。 | 第 2 节之外不需要别的。它不测试接手已有代码（Q6）。 |
| 2. `nuo_voice` | Troy 给 AI 代理做的语音前端：Python，`src/` 结构，约 2,300 行源码，有单元测试和集成测试，有中英文设计文档。最近一次改动是 2026-11-03。 | 接手已有项目（Q6）：遗留测试、旧代码只在改动时检查、把语言包的 `pyproject.toml` 表和已有的 `[tool.ruff]`、`[tool.pytest.ini_options]` 合并、把共用的 `nuo_env` 环境改成 mamba 加 uv 和锁文件，以及把它的设计文档转成 troy-mode 的需求文档。 | troy-init 的语言步骤现在遇到已有的工具表会停下（F06 第 5.2 节），所以要先合并这些表。它的集成测试需要 Ollama 运行 `qwen3.8:27b`，而 troy-voice 的笔记里写的 Troy 电脑显卡只有 12 GB，放不下，所以它的发布场景要用 Troy 的另一台机器。 |
| 3. `HiCommonUtils` 里的 HiLog | 一个用 CMake 的小 C++ 日志库，源码约 10 KB。最近一次改动在 2024 年。 | 在真实项目上使用 C/C++ 语言包，这件事还没人做过；它的已有代码适用 Q6，已有的 `CMakeLists.txt` 必须引入 `cmake/troy.cmake`。 | F07 修复（第 3.3 节）。它从 2024 年起就没改过，所以它的 v0.1 会是 Troy 未必需要的新工作。 |

**现在不建议：troy-voice。** 它是 Troy 最活跃的项目，但 Python 语言包要求根目录有一个 `pyproject.toml` 和一个 `src/`，而 troy-voice 把每个包放在 `packages/<名字>/` 里，各有自己的 `pyproject.toml`。它还有约 5,900 行代码、自己的 CI、自己的代理钩子和自己的需求文档格式。等 troy-mode 支持这种结构之后，它适合做第二次试点。

Troy 也可以指定别的项目。这时 F11 会话会在试点开始前，按第 3.1 节检查它，并说明它会用到什么、需要先做什么。

**Troy 的选择。** Troy 于 2026-11-08 选了候选 1，没有给出别的想法（D93）。所以试点是一个新的 Python 命令行项目：菜谱、一周的菜单和对应的购物清单，支持中英文。它不需要第 3.3 节的 F07 修复。

### 3.3 C/C++ 和 F07 修复

在 C/C++ 项目里，测试用 `troy_add_test` 注册在 `CMakeLists.txt` 里，而这个文件属于 `dependencies` 类。F07 在每次运行后的检查，会把 `--allow-dependency` 没有点名的依赖文件改动都标出来，所以 C/C++ 项目里每次测试工程师的运行都过不了检查，会被撤销（F08 设计第 9 节）。F07 的试运行只用过 Python。

如果 Troy 选了 C/C++ 项目，就先做一个小的 F07 修复，带一份简短的设计改动，经 Troy 批准。例如：测试注册改到 `tests/CMakeLists.txt` 和 `version-tests/CMakeLists.txt` 里，这两个文件属于 `tests` 类；或者 `check-run` 对写测试的角色放行只增删 `troy_add_test` 行的改动。Python 试点不需要这个修复，它留作在任何 C/C++ 项目之前要做的后续工作。

## 4. 准备

对新项目（候选 1）：

1. **文件夹。** `D:\Troy\Projects\<名字>`，空的。F11 会话按想法建议一个名字，Troy 可以改。
2. **会话。** Troy 在桌面应用里，在这个文件夹里打开一个 Claude Code 会话，并加上合并权限（D98）。
3. **开始。** Troy 输入 `/troy-pstack:troy-mode start a project: <想法>`。troy-mode 问要不要把这个文件夹变成 troy-mode 项目，troy-init 问要不要创建私有仓库 `ZJUCao/<名字>`（F06 D52）。Troy 两个都回答"要"。初始化 PR 合入。
4. **需求。** 产品经理提问，Troy 回答，Troy 在聊天里批准需求文档（需求文档 3.3 第 1 步）。版本计划里写明 v0.1（第 5 节）。
5. **架构。** 架构师写好架构，Troy 用同样的方式批准（3.3 第 2 步）。同一条消息会问这个项目属于哪个系列。除非 Troy 另有说法，这个项目不属于任何系列，有自己的环境。
6. **语言步骤。** troy-init 的语言步骤加入语言包，它的 PR 合入。

对已有项目（候选 2 和 3），第 1 步就是它已有的文件夹和仓库，troy-init 的初始化和语言步骤按 F06 第 5.5 节在它上面运行，F11 会话会先列出第 3.2 节说的、这个项目需要先做的事。

## 5. 一个版本（D94）

"一个版本"指项目版本计划定义的 v0.1：**4 到 5 个功能**，每个都在 R03 以内。最少四个，因为前三个功能的 PR 1 和 PR 2 要等 Troy（Q2），只有第四个功能，才能在 F07 D62 的那个问题之后，看到 troy-mode 自己合并它们。

满足下面这些条件，版本才算完成：

- v0.1 的每个功能在项目需求文档里都是"在 Troy 的设备上可用"；
- GitHub release `v0.1.0` 已经建在发布 PR 的合并提交上（F08 D73）；
- 发布 PR 上已有 `Retrospective: v0.1.0` 评论，Troy 从中挑出的每条规则，都已走完规则变更流程，或者（对适用于所有项目的规则）已成为 troy-pstack 里的 issue（F09 D83）。

版本进行中的 bug、需求变更、旁支 PR 和升级都是试点的一部分，不是停下试点的理由。只有在 v0.1.0 之后出现 bug 时才会有 v0.1.1 这样的补丁版本，它不是必需的。

### 6.2 试点会话（D95）

Troy 按指南说的，在桌面应用里、在试点文件夹中的一个 Claude Code 会话里输入请求。troy-mode 完全按安装的样子运行。"the rest of v0.1" 这样的请求会让 troy-mode 做完这个版本的每个功能，只在第 6.1 节 Troy 的步骤停下（F07 D63）。中断之后，在同一个文件夹里新开一个会话，用 "continue" 继续（需求文档 5.10）。

试点会话从不修改 troy-pstack，也从不手动修补试点项目里 troy-mode 的文件。出了问题交给 F11 会话（第 7 节）。

### 6.3 F11 会话

一个 troy-pstack 会话，在 F10 合入后由协调会话启动，负责 F11 自己的工作：

- 检查前提条件（第 2 节），并用一条消息告诉 Troy 在哪里输入什么；
- 在旁支会话笔记文件夹里记一份试点的流水日志，这样对话被压缩时也不会丢东西；
- 读取试点仓库的 PR、评论、CI 运行和 issue，试点会话的对话记录，以及项目的 `hooks.log`（第 8 节）；
- 处理 Troy 或 troy-mode 的升级报告的问题（第 7 节）；
- 写试点报告和状态 PR（第 8 节和第 9 节）。

它不在试点项目里运行 troy-mode，也不替 Troy 回答。

## 7. troy-mode 出问题时（D96）

| 问题 | 怎么办 |
| --- | --- |
| **挡路的问题**：troy-mode 无法继续，或者继续就会违反规则或丢失工作 | 试点暂停。F11 会话在 troy-pstack 里开一个带 `pilot` 标签的 issue。修复走 troy-pstack 的流程：涉及设计时先改设计，先写测试，PR 升插件的补丁版本号（F10 D89）。Troy 更新插件并重启 Claude Code。然后 troy-mode 用 "upgrade troy-mode"（F06 第 6 节）把试点项目更新到新版本，再继续。 |
| **troy-mode 能过去的问题**：回答了升级，或者重做了一步 | F11 会话开一个带 `pilot` 标签的 issue，试点继续。修复放在试点之后，或者在不影响试点正在做的事时并行进行。 |
| **指南写错或漏写的地方** | 记进流水日志，在最后的状态 PR 之前，用一个指南 PR 一起修正（F10 第 9.5 节）。 |

没有 Troy 在聊天里的同意，谁都不手动绕过挡路的问题。如果 Troy 同意，报告会把这个绕过办法列为一个问题。

## 8. 记录什么（D97）

### 8.1 试点报告

`docs/troy-mode/pilot/<项目>-v0.1.md` 和它的中文镜像，放在 troy-pstack 里，由 F11 会话在版本完成后用一个 PR 写好：

| 节 | 内容 |
| --- | --- |
| 1. 概要 | 项目、版本、日期，以及几句话的结果 |
| 2. 时间线 | 从初始化到复盘的每一步，带它的 PR 和日期 |
| 3. 问题 | 第 8.2 节 |
| 4. 候选规则 | 第 8.3 节 |
| 5. 时间和花费 | 第 8.4 节 |
| 6. 指南 | 第 8.5 节 |
| 7. 状态 | 每个功能前后的状态，以及变化的原因 |
| 8. 下一步 | 未关闭的 issue，以及第二次试点应该试什么 |

### 8.2 问题

每个问题一行：它在报告里的编号、发生在哪里（流程、步骤、PR 链接）、发生了什么、它的类型（挡路、已绕过或外观问题）、它属于哪个 troy-mode 功能（F01 到 F10），以及修复（PR 链接）或未关闭的 issue。问题来自试点 PR 上 troy-mode 的升级和失败的尝试、钩子的拦截、Troy 的意见，以及 F11 会话在对话记录里看到的、违反设计或规则的任何事。

### 8.3 候选规则

- **项目的规则：** 复盘发现的重复问题（F08 D76）、Troy 挑出的规则，以及规则变更流程对每条规则做了什么。
- **troy-mode 的规则：** 在试点的多个功能或流程里重复出现、能用一条适用于所有项目的规则或检查来防止的问题。报告提出它们，Troy 接受的每一条都会成为 troy-pstack 里的一个 issue，以后通过 troy-pstack 的流程实现。

### 8.4 时间和花费

| 指标 | 来源 |
| --- | --- |
| 每个功能和阶段的角色运行次数，带模型和推理强度 | 试点会话的对话记录：每次 Agent 调用 |
| 每个功能、每个角色和主会话的花费（美元） | 对话记录里按模型统计的 token 数（包括子代理），按当天的标价计算。桌面应用显示了会话花费的地方，报告把它放在计算结果旁边。 |
| 每个功能经过的时间 | 从第一个 PR 创建到验收 PR 合入，取自 GitHub |
| 每个阶段的审查轮次、尝试次数和升级 | troy-mode 在 PR 上的评论（F07 第 8.4 节），按 `retro` 的统计方式 |
| troy-mode 等 Troy 的次数，以及 Troy 花的时间 | 对话记录里 Troy 的消息，以及 Troy 最后自己的估计 |
| CI 分钟数 | 试点仓库 `gh run list` 的时长 |
| 钩子拦截 | 项目的 `hooks.log`（F05 第 10 节） |

按试运行的数据估算，一个 4 到 5 个功能的版本大约要运行 50 到 70 次角色，约 50 到 90 美元，另有约 35 个 PR，每个用几分钟 Actions 时间。Troy 自己的时间估计为 2 到 3 小时，分散在整个试点里：主要是需求对话、前三个功能的六次批准，以及设备测试。报告会把实际数据和这些估计对比。

读取对话记录的脚本放在 F11 会话的临时目录里，不提交，因为它们只为这份报告服务。

### 8.5 指南

Troy 照着指南做时，指南写错、漏写或不清楚的每个地方，以及修正。指南 PR（第 7 节）在最后的状态 PR 之前合入，这样 F10 的状态才能变。

## 9. 状态（D100）

troy-pstack 里有两个状态 PR，各自独立：

1. **试点的第一个功能验收时。** F11 的状态是"在真实项目上使用，进行中：troy-mode 初始化了 <项目>，并验收了它的第一个功能。v0.1 尚未发布。"到那时已满足下表条件的功能，也一起更新。
2. **版本完成时**（第 5 节），并且报告和指南修正都已合入。F11 的状态是"在真实项目上使用：troy-mode 把 <项目> 从需求带到 v0.1.0，Troy 于 <日期> 在自己的设备上验收。试点报告列出 <n> 个问题：<m> 个已修复，<k> 个作为 issue 未关闭。"其他功能按下表更新。

| 功能 | 试点做到什么时，改为"在真实项目上使用" | 它的设计 |
| --- | --- | --- |
| F01 | 用 troy-mode 的模板写出它的文档 | |
| F02 | 在它的 PR 上以 CI 运行 `troy-check pr` | |
| F03 | 在它的代码 PR 上运行语言包的 CI 任务和 `troy-check code`。只有用到的那个语言包会变。 | |
| F04 | 运行了每个角色 | |
| F05 | 在钩子开启的情况下运行 | |
| F06 | 以 troy-init 开始 | F06 第 11.5 节 |
| F07 | 在 troy-mode 上运行 | F07 第 14.4 节 |
| F08 | 发布了一个版本 | F08 第 11.4 节 |
| F09 | 增加或修改了一条规则（D99） | F09 第 10.4 节 |
| F10 | 结束，指南的修正已合入 | F10 第 9.5 节 |

每个新状态都写明实际发生了什么，并带上试点仓库的名字，这是 R13 的要求。条件没有满足的功能保持原状态，报告说明原因。
