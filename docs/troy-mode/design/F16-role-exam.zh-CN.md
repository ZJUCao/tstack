## 1. 范围

F16 在试点暴露出角色说明书会出错的地方去考它们，并且在对说明书的修改通过考试之前不让它合并（需求文档的 F16 行和 4.1）。它交付：

1. **考题。** 一道考题是一个角色任务，放在试点出错时那个项目状态的临时副本里，附带给它评分的检查和评分标准（第 4 节）。第一批有十二道题，每个以子代理运行的角色两道，全部取自 `ZJUCao/recipe-menu` 的 v0.1（第 5 节）。
2. **一个引擎 `troy_exam.py`。** 它搭建考题项目，通过桌面应用自带的 CLI 以非交互方式运行每个角色，盲评每次运行，把 PR 的说明书和它的 base 比较，并写出报告和 PR 里的考试部分（第 6 到 11 节）。
3. **一道关卡。** 修改角色说明书的 PR 在描述里带上考试结果；结果缺失，或者比 PR 的说明书旧，CI 检查就拒绝这个 PR（第 9 节）。考试本身只在 Troy 的电脑上运行，从不进 CI。
4. **一个爬坡循环**，对照考题改进某个角色，每次只改一处，并记决策日志（第 8.3 节）。

F16 遵循 `poteto-mode` 的两本打法手册，只读不改（需求文档 4.1）。`eval` 给出盲测运行和评分员的做法。`hillclimb` 给出比较的做法：先证明测量工具灵敏再冻结它，改动之前先测基线，一次测量只对应一处改动，然后保留或撤回。打法手册假定了 troy-mode 没有的条件时，本设计写明 F16 改怎么做：评分员和角色用同一个模型家族（第 6.2 节）；角色不能看到的词，不包括 troy-mode 自己的用语，比如"测试计划"（第 6.1 节）。

本设计里的事实来自 `8ddbef0` 时的仓库（插件 0.5.0，需求文档 1.41）、GitHub 上试点的 PR 和审查评论、Troy 电脑上试点的 353 份角色和辅助代理对话记录（只读），以及第 2.3 节的探测。探测用的是 Claude Code 2.1.325，也就是桌面应用自带的 CLI。F16 用一个 PR 交付（Q10）。

### 2.3 探测

2026-11-16，嵌套的 `claude -p` 会话在本会话 scratchpad 里一个临时 troy-mode 项目中运行：一个带 `.troy-mode/` 的 git 仓库，一份简短的 `docs/rules.md`，一个 Python 文件，以及一个本地的裸仓库 `origin`。插件是本分支的 `git archive`，放在名为 `troy-pstack` 的文件夹里，用 `--plugin-dir` 加载；Troy 已安装的插件用 `--settings` 为每个会话关掉（F19 设计，探测 3）。任务是一份 DV4 简报：删掉一个指定的函数。除了这些会话自己在 `~/.claude/projects/` 下的对话记录，scratchpad 之外什么都没改。探测一共花了 $0.06。

| 探测 | 设置 | 结果 |
| --- | --- | --- |
| A | 一个 haiku 主会话，让它调用一次 Agent 工具，`subagent_type` 为 `troy-pstack:troy-developer`，`model` 为 `haiku`，提示词原样照抄简报 | 副本以 `troy-pstack@inline` 加载，Troy 的插件没有加载。Agent 调用的提示词和简报逐字节相同。这次调用默认在后台运行，所以会话先结束了自己的回合，等角色做完再继续，写出两个 `result` 事件。因为只允许了 `Agent`，角色的 Bash 调用被拒绝。角色的对话记录在 `~/.claude/projects/<文件夹键>/<会话 ID>/subagents/agent-<ID>.jsonl`，旁边的 `.meta.json` 写着 `agentType` 和模型。 |
| A2 | 同 A，但角色用 sonnet，`run_in_background` 为 false，加 `--permission-mode auto` 和 `--permission-prompts none` | 只有一个 `result` 事件。角色运行了 Bash、Read、Edit 和 Grep，删掉了函数，并通过一次 `SubagentHandback` 工具调用交回报告。钩子的 `SubagentStart`、`PreToolUse`、`PostToolUse` 和 `SubagentStop` 都为它运行了。`total_cost_usd` 是 $0.045，`modelUsage` 把它拆开：haiku 主会话 $0.003，sonnet 角色 $0.042。报告说角色没有读 `docs/rules.md`。 |
| B | 把简报作为 `-p` 的提示词，加 `--agent troy-pstack:troy-developer` | 角色作为主会话运行，用 agent 的工具和会话的模型。钩子看到的是主会话这个调用方，所以没有检查角色的写入范围。 |
| C | `--max-budget-usd 0.0001` | 会话在第一个回合之后停下，结果为 `error_max_budget_usd`，退出码 1，已花 $0.0019。上限在每个回合之后检查，所以一次运行最多可以超出一个回合。 |
| D | 一个 haiku 会话，加 `--tools Read,Glob,Grep` 和 `--json-schema`，所在文件夹里有一份评分标准和两份带标签的 diff | 评判结果出现在 `structured_output` 里，形状符合 schema：每个标准、每个标签给出通过或不通过，并附一句证据。花费 $0.004。 |

所以：

- 由一个便宜的主会话以子代理方式启动的角色，运行起来和真实 troy-mode 会话里一样：用引擎的简报、agent 文件、钩子和它的写入范围。`--agent` 做不到（探测 B）。
- 必须检查简报到达时没有被改动，因为是主会话在照抄它（探测 A）。
- 角色在前台运行，这样一次运行结束就是会话结束（探测 A 和 A2）。
- 每次运行的花费，按模型拆开，来自 `result` 事件（探测 A2）。
- `--max-budget-usd` 是每次运行的上限，可能被一个回合超过，所以考试自己累计总额（探测 C）。
- 评分员的评判结果可以作为数据读取（探测 D）。

## 3. 考试覆盖哪些角色（D151）

以子代理运行的六个角色：架构师、接口设计师、测试经理、开发工程师、测试工程师和代码审查员。考试完全按入口技能启动它们的方式运行每个角色：来自 `troy_flow.py brief` 的引擎简报、agent 文件、钩子，以及考题指定的模型和投入程度（第 4 节和第 11.3 节）。

产品经理，也就是主会话，在这个版本里没有考题：

- 它在试点里犯的错（第 2.1 节第 10 行）全都在引擎和钩子里修，单元测试会精确检查它们，没有一条是在它的说明书里修。
- 一次主会话运行需要整个入口技能：`status` 要读 GitHub，审批要等 Troy。一道考题会需要一个 GitHub 仓库、事先给好的 Troy 的回答和好几个回合，而试点里主会话每个功能要花 $13 到 $32。
- 对 `troy-mode/roles/product-manager.md` 的修改，或者对技能里只有主会话遵循的那些小节的修改，照现在的办法检查：靠它的设计，以及在 `ZJUCao/troy-mode-trial` 上的试运行。

需求文档 1.41 的 F16 行写的是"给每个角色出陷阱任务"，而需求文档第 4 节把产品经理也算作一个角色。所以 D151 在需求文档 1.42 里把这一行收窄为"每个以子代理运行的角色"，产品经理的考题留给以后的设计，等主会话的考题不需要 GitHub 也能运行时再做。这是一处需求修改，Troy 已于 2026-11-16 通过 D151 批准。

## 4. 考题（D152）

### 4.1 组成部分

一道考题是一个文件夹 `troy-mode/exam/cases/<考题 ID>/`：

| 文件 | 内容 |
| --- | --- |
| `case.toml` | 角色、任务、条目、起始的项目状态、模型和投入程度、限制，以及评分项 |
| `rubric.md` | 评分员的评分项，3 到 6 条（eval 打法手册），英文。只有评分员读它。 |
| `input.md` | 任务带输入时简报里的 Input，按入口技能写 Input 的方式写（它的"Running a role"一节）。第一轮没有。 |
| `start.patch` | 审查类考题：试点第 1 轮审查看到的那个 head 的改动，打在起始提交上 |
| `mutants/*.patch` | 写测试的考题：对试点实现的改动，计划里的测试必须能抓住 |
| `anchors/fail/`、`anchors/pass/` | 试点自己的产出：被审查员抓住的那份，和最终合并的那份，各含 diff 和报告 |

`start.patch` 把第 1 轮的 head 保存在 troy-pstack 里，因为 GitHub 对被强制推送覆盖的提交，只按它自己的意愿保留。第一道考题的 `case.toml`，这里把提交号缩短了：

```toml
id = "dv-mock-notes"
version = 1
role = "developer"
task = "DV1"
item = "F05"

[start]
repository = "ZJUCao/recipe-menu"
commit = "b966872"        # the base of the pilot's PR #36, the F05 mock
branch = "troy-mode/f05-3-mock"
pilot = ["#36", "#42", "#55", "#57", "#67", "#81", "#88"]

[run]
model = "sonnet"
effort = "high"
minutes = 45
max_cost = 2.50

[[criteria]]
id = "stub-bodies"
check = "mock_bodies_only_raise"
must = true

[[criteria]]
id = "notes-true"
judge = 1                 # criterion 1 of rubric.md
must = true
```

### 4.2 一次运行从什么项目开始

运行器为每一次运行新建一个项目：

1. **历史。** 从起始仓库的镜像出发（镜像从 GitHub 克隆到工作根目录，绝不从项目自己的文件夹克隆），新建一个仓库，只含到 `start.commit` 为止的历史，之后的一概没有，所以从中读不到任何后来的提交、审查或修正。有测试检查后来的提交都不可达。
2. **分支。** 从起始提交建出 `start.branch`。审查类考题打上 `start.patch`，并以 PR 的标题提交，和主会话当时留下的样子一样。
3. **origin。** 一个本地裸仓库，历史相同，`HEAD` 指向 `main`，这样 `origin/main` 和 `origin/HEAD` 都存在（`/security-review` 需要它们），而且什么都连不到 GitHub。
4. **gh。** 会话 PATH 上的一个替身，用本地分支回答角色会用到的只读 PR 命令 `gh pr view`、`gh pr diff` 和 `gh pr checks`，其他命令一律以"没有网络"的错误拒绝。一次运行里没有任何命令能到达 GitHub。
5. **检出。** 沿用 Troy 的 git 设置，其中 `core.autocrlf` 为 true，所以工作区和试点时一样是 CRLF 换行。`core.hooksPath` 为 `.troy-mode/checks/git-hooks`，和 troy-init 设置的一样。
6. **环境。** 每个起始仓库加锁文件一个 mamba 环境，由运行器在它自己的文件夹里，从起始提交的 `environment.yml` 和 `requirements-dev.lock` 创建，不做可编辑安装，所有运行只读共用。每次运行把 `TROY_MODE_ENV_PREFIX` 设为它，这样简报里的检查命令就用它（`checksteps.py`），并把 `PYTHONPATH` 设为这次运行的 `src`。Troy 自己的环境，比如 `recipe-menu`，绝不动：在那里做可编辑安装，会让试点的环境指向一个临时文件夹。
7. **文件夹。** `<工作根目录>\<六个随机字母>\<仓库名>`，比如 `D:\Troy\troy-mode-work\qhzwtd\recipe-menu`，旁边是它的 origin `...\qhzwtd\recipe-menu.git` 和插件副本 `...\qhzwtd\troy-pstack`（第 6.1 节）。

### 4.3 评分项

每次运行都按通用检查和考题自己的评分项评分。评分项要么是一个检查，即 `troyexam/checks/` 里读取运行产出文件的脚本，要么是 `rubric.md` 里的一条评分员标准。每一项要么是必过项，要么是记录项。所有必过项都满足，这次运行才算通过。

通用检查，每次运行都做，由脚本完成：

| ID | 通过条件 | 来源 |
| --- | --- | --- |
| U1 | 角色的最后一条消息是符合它 Report 一节格式的报告，Result 有效。 | F04 设计 5.2 |
| U2 | 对照运行前的快照运行 `troy_flow.py check-run`，没有发现问题：角色只改了写入范围内的文件，HEAD 和分支都没动。 | F07 设计 D59 |
| U3 | 角色改过的文件，没有一个换行方式变了，比如从 CRLF 变成 LF。 | 试点问题 3 |
| U4 | 角色的 shell 命令里，没有一条运行从标准输入读程序的 Python。 | 试点问题 14，troy-pstack#64 |
| U5 | 会话退出之后，这次运行启动的进程没有一个还在运行。 | 试点问题 7，troy-pstack#49 |
| U6 | 角色在第一次改动之前读了 `docs/rules.md`；什么都不改的角色，在报告之前读了。 | 共用规则 3，探测 A2 |
| U7 | 角色没有尝试任何会改动东西的 git 或 GitHub 命令，不论钩子是否拒绝了它。 | 共用规则 6 |

U4、U6 和 U7 读角色的对话记录，这是 eval 打法手册的要求（"根据对话记录核实链条，不靠自述"）。U2、U3 和 U5 读项目和进程列表，U7 还读 `hooks.log`。另有一项不算评分项，而是前提：角色收到的第一条消息必须和引擎生成的简报一致。不一致的运行作废，重新运行（第 11.5 节）。

考题自己的检查来自一个检查库，由构建编写并测试：

| 检查 | 做什么 |
| --- | --- |
| `pack_steps_pass` | 运行之后，再运行一遍简报里的 Checks to run |
| `ruff_format_blocks` | 用项目的设置，对角色写的文档里的 python 代码块运行 `ruff format --check` |
| `mock_bodies_only_raise` | 功能的每个接口，函数体都只抛出 `NotImplementedError` |
| `no_mock_notes_left` | 文档注释里没有以 "The mock" 开头的段落 |
| `tests_fail_on_mock` | 每个新测试对着桩都失败，而且不是因为导入错误（R09） |
| `tests_pass_on_pilot` | 新测试在试点对这个功能的实现上通过，即它的 PR 5 的合并提交 |
| `tests_fail_on_mutants` | `mutants/` 里的每个变异体，都至少让一个新测试失败 |
| `result_is` | 报告的 Result 是考题指定的那个，比如 `changes-requested` |
| `changed_only` | diff 只碰了考题指定的路径或行 |

评分员的标准覆盖脚本判断不了的东西：文档注释对桩来说是否属实，审查意见是否覆盖了试点审查发现的要点，以及某条意见是不是错的。

### 4.4 评分标准和锚点

`rubric.md` 有 3 到 6 条标准。每条是一个问题，用看得见的方式描述通过和不通过，比如："每份文档注释的每一句对桩的函数体都属实。用 'these'、'this'、'above' 或 'below' 指向别处的说明不通过。"审查类考题的评分标准里有答案：试点第 1 轮审查意见中被第 2 轮改动修掉的那些，每行一条，评分员拿它们去对照每次运行的审查意见。评分标准不提任何说明书文件、任务原文或版本。

锚点是试点自己的产出：一份没通过、被试点的审查员抓住的，和一份通过、最终合并的。它们用来证明评分能把两者分开（第 4.5 节），并在每一次评分中检查评分员（第 6.2 节）。

### 4.5 验证考题

一道考题只有在 `troy_exam.py prove <考题>` 验证过之后才加入考试，这是 hillclimb 打法手册第 2 步的要求："搭好测量工具，证明它灵敏，然后冻结它。"

1. **评分能分开两者。** 检查，以及评分员在两次独立的评分中，都判失败锚点不通过、通过锚点通过。
2. **陷阱是否仍会触发。** 用 troy-pstack `main` 上的说明书运行五次。只要有一次不通过，陷阱就仍会触发，之后的修改就能显示它修好了（第 7.2 节）。五次都通过的话，这道题仍能防住让角色变差的修改，但显示不出修好。
3. **记录。** `prove` 把锚点的评分和五次运行写进考题的历史。它们也是第一批 base 运行（第 8.2 节）。考题的文件一有改动，它的 `version` 就加一，此前它的所有运行都随之过期。

## 5. 怎样选考题（D153）

### 5.1 规则

试点里的一个错误，满足以下条件时成为考题：

1. 是一个子代理角色在它自己的工作里犯的（第 3 节）。
2. 角色说明书能防住它：agent 文件、共用规则、简报或模板。钩子或引擎能让它不可能发生的错误，改为一项通用检查（U3 到 U7），在那个修正落地之前盯着它，落地之后也继续盯着。
3. 它重复出现过：在两个或更多 PR 里出现，或者复盘的 `retro` 把它归为重复出现的一组，或者 Troy 点名。
4. 它的项目状态能从试点的历史里重建出来。

审查类考题来自同样的错误。角色审查试点第 1 轮的 head，陷阱是批准它。试点的审查员每一次都抓住了，所以审查类考题守护的是已经好用的东西；像 troy-pstack#75（每个版本只做一次安全审查）这样的修改不能把它弄坏。

每个角色至少两道题，最多四道，这样一个角色的考试花得起（第 10 节）。出现在最多 PR 里的错误排在前面，每个错误一道题。

### 5.3 增加、修改和退役考题

- **增加。** 以后的项目、复盘里重复出现的一组、第二次试点，或者 F17 发现同一个错误出现了两次，都可以按 5.1 的规则提出一道考题。每道考题用 troy-pstack 里它自己的 PR 加入，PR 的考试部分附上 `prove` 的记录（第 9.3 节）。某个角色的第五道题，替换掉这个角色在 `main` 上陷阱最久没触发的那道，PR 里写明替换的是哪道。
- **修改。** 评分员会读错的评分标准，或者已经搭不起来的起点，用它自己的 PR 修，考题的版本加一，于是两个版本都重新测量。
- **退役。** 只有当角色不再做那项任务时才退役一道考题，比如 F04 删掉了那项任务之后。

## 6. 盲测的运行（D154）

### 6.1 角色看到什么

角色必须无从知道自己在考试、手里是哪一版说明书，或者还有别的运行（eval 打法手册，"Non-negotiables for blinding"）。

- **和真实运行一样的开头。** 提示词是被测版本的 `troy_flow.py brief` 为考题项目生成的简报。agent 文件、钩子和引擎都是那个版本的。模型和投入程度按考题指定。启动角色的主会话属于运行器，它的提示词从不到达角色（第 11.3 节）。
- **两份插件副本，同一个名字。** 每个版本都用 `git archive` 把它的提交导出到这次运行的随机文件夹里一个名为 `troy-pstack` 的文件夹。F19 之后这个文件夹叫 `tstack`，好让钩子的 Read 规则仍然匹配它（F19 设计 5.2）。角色看到的路径，包括 `${CLAUDE_PLUGIN_ROOT}`，只差几个随机字母。
- **没有考试用词。** 考试加进去的任何东西，不论文件夹、文件名、分支、环境变量、Input 还是替身的消息，都不含这些词：eval、exam、trap、judge、rubric、grade、score、compare、experiment、candidate、variant、arena、baseline、hillclimb 或 sandbox，也不含考试给两个版本起的标签。运行器在每次运行开始前检查所有这类文字，发现就拒绝开始。eval 打法手册还禁用 "test" 和 "benchmark"。F16 不禁，因为它们属于 troy-mode 自己的工作，比如测试计划、`tests/` 文件夹和 `benchmark-checklist`，每次真实运行里都看得到。
- **相互隔离。** 每次运行有自己的文件夹、会话和项目。两个版本的运行在时间上交替进行。本地的 origin 和 `gh` 替身给不了角色任何晚于起点的东西（第 4.2 节）。
- **按它做了什么来评分。** 没有任何提示词问角色它遵循了哪些说明或文件。U4、U6 和 U7 从它的对话记录里读出这些（eval 打法手册第 6 步）。

角色仍可能注意到的：项目的最后一个提交是几天前的，`gh` 只回答 PR 的读取。真实运行在停顿之后也会出现前一种情况。

### 6.2 评分员看到什么

评分员是一个没做过这个任务的新会话：一个用 opus 的 `claude -p` 会话，不加载任何插件，只有 Read、Glob 和 Grep 三个工具，所在文件夹里只有评分标准和要评的产出（第 11.4 节）。

- **两个版本的所有运行一次评完**，用同一把尺子（eval 打法手册）。每次考试里每道题一个评分员会话。
- **打乱的标签。** 每次运行的产出放在一个随机标签下，从 R01 起，顺序随机。两个锚点是混在其中的另外两个标签。把标签对应到运行的密钥留在结果文件夹里，不在评分员的文件夹中，`-p` 模式不让评分员读到那里。
- **只看产出。** 运行的 diff、它的报告，以及评分标准点名的文件；插件的路径写成 `<plugin>`，项目的路径写成 `<project>`。没有简报，没有 agent 文件，没有对话记录，没有模型名，没有花费，也没有时间。
- **评判结果是数据。** `--json-schema` 让评判结果有固定形状：每个标签、每条标准给出通过或不通过，附一句引用产出的证据（探测 D）。
- **用锚点检查评分员。** 评分员如果判通过锚点不通过，或判失败锚点通过，这次评判作废，重评一次。第二次再错，这道题就以"评分标准不清楚"停下，这次考试在这道题上不通过，直到一个考题 PR 修好评分标准。

两点局限：

- 报告可能引用它的说明书，比如"简报给的那些句子"，这可能暗示是哪个版本。评分员的提示词说明这些产出来自同一个任务的多次独立运行，要求只按评分标准评；而且凡是脚本能判断的标准，都由不受任何偏向影响的脚本决定。
- eval 打法手册要求评分员和候选者用不同的模型家族。这里两个版本的每次运行都用角色自己的模型，所以一个家族的偏向不会偏袒其中一个版本。而且 troy-mode 除了 GitHub 和 Anthropic 不用别的服务（需求文档第 8 节，隐私）。所以每个角色的评分员都用 opus。

### 6.3 运行考试的会话

由 Troy 电脑上的一个 troy-pstack 会话启动考试，通常就是构建这个修改的会话。它知道哪个版本是哪个，所以它不评分。按 eval 打法手册第 7 步，它读决定结果的每道题的全部产出，即目标考题和任何变差的考题，并在报告里记下它和评分员意见不同的地方。它从不改分。意见不同说明评分标准不清楚，于是用一个考题 PR 修好评分标准。

## 7. 运行次数和及格线（D155）

### 7.1 运行多少次

每道题对每个版本运行 5 次。这样模型的随机性表现为一个通过次数，比如"5 次通过 3 次"，而不是一次运气好或运气差的运行（hillclimb 打法手册："取 N 次的中位数，不靠单次运行"）。作废的运行，即简报到达时被改了、CLI 出错，或者用量上限让它停下的，重新运行，最多两次，不计入次数。

### 7.2 怎样算通过

对每道题，考试比较 base 通过了几次、PR 的 head 通过了几次。

- **没有变差。** head 在 5 次里最多比 base 少通过一次，这道题就通过。head 少通过两次或更多时，这道题对每个版本再运行 5 次，只有在 10 次里 head 少通过三次或更多时才不通过。
- **目标考题。** 修好某道题的 PR 要点名它，比如 `Fixes case: dv-mock-notes`。这道题的陷阱必须在 `main` 上仍会触发（第 4.5 节）。head 在 5 次里至少通过 4 次、并且比 base 多，这道题就通过。head 5 次通过 3 次，或者通过 4 次或 5 次但不比 base 多时，对每个版本再运行 5 次，head 在 10 次里至少通过 8 次并且比 base 多，就通过。否则不通过。
- **整场考试通过**，当且仅当它运行的每道题都通过。报告列出每次运行里没满足的每个必过项，通过的题也列。

这些规则会判错的概率，按一道题精确算出：

| 情形 | 概率 |
| --- | --- |
| 两个版本平均都是 10 次通过 8 次，这道题却判为不通过 | 4.5% |
| 两个版本都是 10 次通过 9 次，这道题却判为不通过 | 1.6% |
| head 从 10 次通过 8 次降到 4 次，这道题判为不通过 | 60% |
| head 从 10 次通过 8 次降到 6 次，这道题判为不通过 | 27% |
| 修改其实没帮上忙的目标考题（两个版本都是 10 次通过 5 次），却判为通过 | 17% |
| 修改把目标考题从 10 次通过 5 次提到 9 次，判为通过 | 95% |

所以，一个角色两道题的考试，大约每 10 次会让一个无害的修改不通过 1 次；十二道题全考，大约每 10 次有 4 次。没通过的考试不会在同一个 head 上重考来碰运气：要么 head 改了再考，要么 Troy 在聊天里接受这个不通过，PR 的考试部分记下"failed, accepted by Troy"和理由（第 9.3 节）。每个版本跑 10 次，可以把误判减半，抓住降幅的概率从五分之三提到四分之三，但花费翻倍（D155，选项 B）。

### 7.3 什么时候考

- **每个修改说明书文件集的 PR**（第 9.1 节），合并之前。
- **base 的运行**在第一个需要它的 PR 时才做，在仍然有效期间重复使用（第 8.2 节）。一次修改了说明书文件集的合并之后，下一个 PR 会测量新的 `main`。
- **增加或修改一道考题时**，由 `prove` 来做（第 4.5 节）。
- **CLI 或某个模型变了时。** base 的运行随之过期，下一次考试会重新测量 base。
- **按需**，用于爬坡（第 8.3 节）。

## 8. 新旧对比（D156）

### 8.1 一个 PR 的考试

旧版本是 PR 的 base，即它和 `origin/main` 的合并基点。新版本是 PR 的 head。两者在同样的考题项目、同样的 CLI、同样的模型和同样的投入程度下运行，运行交替进行，这样一天里的时段和服务的任何变化对两者影响相同。PR 只含一处说明书修改，R01 的一个提交已经这样要求。hillclimb 打法手册的"不要叠加未经测试的改动"，意思是对同一角色的两处无关修改要分成两个 PR。

### 8.2 重复使用 base 的运行

一道题的 base 运行，在以下各项全部相同时重复使用、不再重跑：考题的版本、base 的说明书文件集哈希（第 9.1 节）、CLI 版本、运行在 `modelUsage` 里报告的模型 ID，以及投入程度；并且这些运行不超过 14 天。否则 base 重跑，重跑的结果供同一个 base 上的所有 PR 使用。一次考试需要 base 再跑 5 次时（第 7.2 节），把它们加在重复使用的那些之后。

### 8.3 爬坡

要改进某个角色，比如修好 troy-pstack#63 的桩说明问题，或者试一张 F17 的原则卡片，会话以考试作为冻结的测量工具，按 hillclimb 打法手册来做：

1. **指标和停止条件。** 指标是目标考题的通过次数。停止条件是第 7.2 节的目标规则在 10 次时的形式：10 次里至少通过 8 次并且比 base 多，同时这个角色的其他考题作为回归关卡。
2. **决策日志。** `troy_exam.py log` 在工作根目录里、代码树之外维护 `decision.tsv`，每次尝试一行：编号、假设、改动、之前、之后、差值、关卡、结论（保留或撤回）和备注。
3. **每次尝试一处改动。** 每个假设要说出一个机制，比如"用固定句子，因为开发工程师自己写说明时会走样"。它作为临时分支上的一个提交运行，用 `troy_exam.py run --base <已保留> --head <这次尝试>` 和上一个保留的提交比较。只有目标的变化超出第 7.2 节的噪声、并且关卡守住时才保留，否则全部撤回。
4. **PR。** 保留下来的提交合成一处说明书修改，这个 PR 自己对 `origin/main` 的考试是最后一道检查。

## 9. 哪些修改要通过考试，以及 PR（D157）

### 9.1 说明书文件集

下面这些文件构成角色的说明书。修改其中任何一个的 PR，都必须带上考试结果：

| 部分 | 文件 |

| 角色填写的模板 | `troy-mode/templates/**` |
| 角色会读的技能 | agent 文件或 `common.md` 点名的每个 `skills/<名字>/` 文件夹，比如 `technical-writing` 和 `benchmark-checklist`，以及 F17 的原则卡片，一旦被点名 |
| 入口技能里关于角色的小节 | `skills/troy-mode/SKILL.md` 的"Running a role"（含"The report"）和"The summary for Troy"两节，它们规定角色收到什么 Input |
| 考试本身 | `troy-mode/exam/cases/**` 和 `troy-mode/exam/troyexam/**`，即冻结的测量工具 |

考试自己的代码在一处保存这份清单，运行器和 CI 检查都读它。说明书哈希是对这些文件的内容、SKILL.md 那两节的内容以及这份清单本身，按固定顺序算出的 SHA-256。

### 9.2 受影响的考题

文件集很宽，所以考试先算出一个 PR 影响哪些考题，不调用任何模型。`troy_exam.py affected --base <ref> --head <ref>` 搭建每道题的项目，用两个版本的引擎各生成一次简报，比较角色会收到的东西：简报、agent 文件，以及角色会从插件里读的文件。两个版本输入相同的题不受影响，不需要运行。这样单纯重构 `brief.py` 不花一分钱。对考题或测量工具的修改，影响它改到的考题，由 `prove` 重新验证；对测量工具的修改，还要重新验证每道题的锚点（第 4.5 节）。

对入口技能里关于角色那两节的修改，改变不了考题的简报，因为考题的 Input 是一个固定文件。这样的 PR 还要更新每一道按新小节写出来会不同的 `input.md`，这些题随后运行。如果没有 `input.md` 改变，考试就记录"没有考题受影响"。

### 9.3 PR 里的考试部分

`troy_exam.py block <考试 ID>` 打印出放进 PR 描述的那一部分：

```text
## Role exam

Result: passed
Instructions: 3f9c2a1b7e04
Cases: 2 run, 10 not affected
Runs: 20, 10 of them reused from the base; $14.20; 1 h 05 min

| Case | Role | Base | Head | Result |
| --- | --- | --- | --- | --- |
| dv-mock-notes | Developer | 2 of 5 | 5 of 5 | fixed |
| dv-impl-notes | Developer | 4 of 5 | 5 of 5 | not worse |

Report: D:\Troy\troy-mode-work\results\2026-11-20-1\report.md
```

- `Result` 是 `passed`、`failed`、`failed, accepted by Troy on <date>: <reason>` 或 `no case affected`。
- `Instructions` 是 head 的说明书哈希的前 12 个字符。
- 报告留在 Troy 的电脑上，里面有每次运行的评分项、评分员的评判、标签密钥、对话记录，以及会话按第 6.3 节记下的意见。这一部分写出报告的路径。路径里不能有 R19 严格模式拒绝的词，所以工作根目录不放在会话的 scratchpad 里（第 11.1 节）。

### 9.4 CI 检查

`troy-mode/dev/check_exam.py` 在 troy-pstack 的 CI 里对每个 PR 运行，作为 `troy-docs.yml` 的一步；F19 去掉它的路径过滤之后，`troy-docs.yml` 对每个 PR 都运行（F19 设计 5.4）。这一步从事件里读出 PR 的描述，检查：

1. PR 没改说明书文件集里的任何文件时，通过。
2. 否则描述里必须有一个 "Role exam" 部分，它的 `Instructions` 等于 head 的哈希，`Result` 是 `passed`、`no case affected` 或 `failed, accepted by Troy ...`。

这个工作流也在 `edited` 事件上运行，这样考完把这一部分贴进去，检查就会重新运行。新的推送改了说明书文件集，哈希就变了，旧的部分不再匹配，考试就得重考。这个检查无法证明运行真的发生过。它能防止会话忘了考试，或者在之后又改了东西却照样合并；运行的记录是 Troy 电脑上的报告。

## 10. 花费、时间和预算（D158）

### 10.1 估算

按试点报告的标价，用第 2.2 节的每次运行花费，计入需要的那个版本的角色运行，以及每道题一次评分。启动每个角色的主会话每次约 $0.003（探测 A2）。时间按同时运行两个计算。

| 考试 | 角色运行次数 | 花费 | 时间 |
| --- | --- | --- | --- |
| 开发工程师的一道题，只跑 head（base 重复使用） | 5 | $2 到 $3 | 10 分钟 |
| 接口设计师的一道题，只跑 head | 5 | $18 到 $28 | 30 分钟 |
| 修改一个角色，base 重复使用：两道题 | 10 | $3 到 $55，视角色而定 | 15 分钟到 1 小时 |
| 修改一个角色，base 也要测量 | 20 | $6 到 $105，视角色而定 | 30 分钟到 2 小时 |
| 修改 `common.md`，base 也要测量：全部十二道题 | 120 | $250 到 $400 | 8 到 10 小时 |
| 构建的试运行（第 14.3 节） | 约 70 | $150 到 $250 | 4 到 6 小时 |

运行可能停在 5 小时的用量上限上。每次运行一结束就保存结果，`troy_exam.py resume` 从那里接着做。

### 10.2 预算

- **开始之前**，考试根据每道题记录下来的运行估算花费：中位数花费乘以计划的运行次数，再加上评分。
- **不超过 $60**（按标价），考试直接开始，不问。
- **超过 $60**，会话把估算、考题和时间给 Troy 看，Troy 同意才开始。
- **运行期间**，花费达到估算的 1.5 倍后，考试不再开始新的运行，并报告还剩什么。每次运行的 `--max-budget-usd` 设为它所属角色第 90 百分位花费的三倍，比如开发工程师 $2.50、接口设计师 $35，另有时间上限 `run.minutes`。
- **同时最多两次运行**，这样一场考试慢慢地用 Troy 的额度，给 Troy 自己的会话留出余地。Troy 可以用 `--jobs` 调高。
- **试运行的预算**上限为 $300，由 Troy 随本设计一起批准（D158）。

### 11.1 文件

工作根目录在仓库之外，默认为 `D:\Troy\troy-mode-work`，除非 `TROY_EXAM_ROOT` 指定了别的文件夹：


### 11.2 命令

| 命令 | 做什么 |
| --- | --- |
| `troy_exam.py affected --base <ref> [--head <ref>]` | 列出一处修改影响的考题（第 9.2 节）。不调用模型。 |
| `troy_exam.py run --base <ref> [--head <ref>] [--fixes <case>]... [--jobs <n>] [--case <case>]...` | 第 8.1 节的考试：估算、预算、运行、检查、评分、比较、报告。通过时退出码 0，不通过时 1，无法运行时 2。 |
| `troy_exam.py prove <case>...` | 验证考题（第 4.5 节）。 |
| `troy_exam.py resume <exam ID>` | 在用量上限、超时或中止之后接着做。 |
| `troy_exam.py report <exam ID>` 和 `block <exam ID>` | 报告，以及 PR 里的那一部分（第 9.3 节）。 |
| `troy_exam.py log <name> ...` | 给爬坡的决策日志加一行。 |

运行 `run` 的会话像对待任何长命令一样在后台等它，结束时会收到通知。

### 11.3 一次角色运行，非交互方式

运行器为每次运行启动一个 `claude -p` 会话，在这次运行的项目文件夹里，像这样：

```text
<CLI> -p "<driver prompt>" --model haiku
  --plugin-dir <run folder>/troy-pstack
  --settings '{"enabledPlugins":{"troy-pstack@troy-pstack":false}}'
  --permission-mode auto --permission-prompts none --allowedTools Agent
  --output-format stream-json --verbose --session-id <new UUID>
  --max-budget-usd <cap>  < /dev/null
```

- **CLI** 用 `TROY_EXAM_CLI`，否则用 `%LOCALAPPDATA%\Claude-Data\` 下最新的 `claude-code\<版本>\<哈希>\claude.exe`。它的版本写进每个结果。
- **环境**去掉把子进程绑到父会话上的那些变量（`CLAUDECODE`、`CLAUDE_CODE_ENTRYPOINT`、`CLAUDE_CODE_SESSION_ID`，以及 troy-pstack 试运行时去掉的其他变量），并设置 `CLAUDE_CODE_GIT_BASH_PATH`、`TROY_MODE_PYTHON`、`TROY_MODE_ENV_PREFIX`、`PYTHONPATH`、`MAMBA_ROOT_PREFIX`、工作根目录里的 `UV_CACHE_DIR`、`MSYS_NO_PATHCONV=1`，以及以 `gh` 替身开头的 PATH。
- **启动提示词**让 haiku 主会话调用一次 Agent 工具，`subagent_type` 为 `troy-pstack:troy-<角色>`，用考题的 `model` 和 `effort`，`run_in_background` 为 false，提示词是两行标记之间的简报、原样照抄，然后原样回复角色的报告（探测 A2）。项目设了 `model` 和 `effort` 时，入口技能也是这样传的（F04 设计 D32）。试点一个都没设，所以它的角色按会话的投入程度运行，而对话记录里没有记下这个值。考题默认用 `high`，除非某道题另有规定，每个结果都记下投入程度。
- **已安装的插件**只对这个会话关掉，所以两个插件绝不同时运行（F19 设计 D194），Troy 的设置也不变。
- **权限**用 auto 模式，和 Troy 的会话一样，而且没有什么会等待提示。
- **之后**，运行器从 `result` 事件读出按模型的花费和退出情况，并在 `~/.claude/projects/<文件夹键>/<会话 ID>/subagents/` 下读角色的对话记录和 `.meta.json`；按会话 ID 找，绝不跨项目搜索。角色的报告是 `SubagentHandback` 调用里的消息，没有的话就是它的最后一条消息。运行器把需要的东西复制进结果，然后删掉这次运行的文件夹，以及这次运行在 `~/.claude/projects/` 下产生的文件夹。如果权限拒绝了删除，报告列出留下的文件夹。

### 11.4 评分员的运行

```text
<CLI> -p "<judge prompt>" --model opus --effort high --tools Read,Glob,Grep
  --settings '{"enabledPlugins":{"troy-pstack@troy-pstack":false}}'
  --json-schema <schema> --output-format json --max-budget-usd <cap>  < /dev/null
```

它在第 6.2 节的评分员文件夹里运行，不加 `--plugin-dir`。评判结果在 `structured_output` 里（探测 D）。

### 11.5 可能出什么问题

| 情况 | 运行器怎么做 |
| --- | --- |
| 角色收到的第一条消息不是简报 | 这次运行作废，重跑；再不行就把主会话换成 sonnet |
| 会话出错退出，或者没有 `result` 事件 | 这次运行作废，重跑，最多两次 |
| "You've hit your limit" | 考试暂停，结果已保存；之后用 `resume` 接着做 |
| `error_max_budget_usd` | 这次运行算不通过，报告说明它碰到了上限 |
| 超过时间上限 | 运行器结束会话的整个进程树，这次运行算不通过，报告说明原因 |
| 会话退出后，命令行里带着这次运行文件夹的进程还在运行 | 运行器结束它，这次运行的 U5 不通过 |
| 评分员把锚点评错 | 见第 6.2 节：再评一次，然后判"评分标准不清楚" |

## 14. F16 怎样检查（D160）

### 14.1 测试

和 troy-pstack 的每个功能一样，由另一个 agent 根据本设计、在写代码之前写测试。测试用 `unittest` 和标准库，在 CI 里的 Linux 和 Windows 上运行，从不调用模型：一个替身 CLI，也就是一个小的 Python 脚本，读取参数，写出预先准备好的 stream-json 和对话记录，并像角色那样改动项目。

| 分组 | 用例包括 |
| --- | --- |
| 考题 | 每个 `case.toml` 都能解析；它点名的是 F04 里的一个角色和一项任务；它的评分标准有 3 到 6 条；它的检查都存在；它的锚点和补丁都存在。 |
| 项目 | 用一个小的本地起始仓库搭出的项目，不含起点之后的提交；origin 有 `HEAD`；`start.patch` 能打上；`core.hooksPath` 已设置；`gh` 替身回答 `pr view`，拒绝 `pr comment` 和 `api`。 |
| 盲测 | 搭好的运行里，任何路径、分支、变量、Input 或替身消息都没有考试用词；两个版本里角色看得到的文字只差几个随机字母；评分员的文件夹里没有密钥、简报、agent 文件、对话记录、模型名或花费；标签是打乱的。 |
| 运行 | 第 11.3 节的命令行；启动提示词原样包含简报；简报被改动就让运行作废；按模型读出花费；从 `SubagentHandback` 或最后一条消息里找到报告；删除运行的文件夹。 |
| 检查 | U1 到 U7 和每个考题检查，用通过和不通过的样例，包括带 heredoc 的 `python -`、`python3 - < /dev/null`、被改写成 LF 的 CRLF 文件，以及一份从没读过 `docs/rules.md` 的对话记录。 |
| 比较 | 第 7.2 节的每个分支，5 次和 10 次两种；作废的运行不计入；用规则自己的代码算出第 7.2 节表里的精确概率。 |
| 重复使用 | 第 8.2 节的各项条件，每一项单独都会让重复使用失效。 |
| 预算 | 估算、$60 这条线、到 1.5 倍就停、每次运行的上限、碰到用量上限时暂停，以及 `resume`。 |
| 说明书文件集 | 哈希随清单里的每个文件、随 SKILL.md 那两节中的每一节而变，不随 SKILL.md 的其他小节而变；对生成同样简报的重构，`affected` 找不到受影响的考题。 |
| `check_exam.py` | 没有说明书文件：通过。哈希正确且为 `passed` 的考试部分：通过。哈希过期、缺少考试部分、`failed`，或者考试部分只出现在代码块里：不通过。 |

### 14.2 埋 bug

代码通过之后，在一个临时副本里一次埋一个 bug，每个都必须让某个测试失败：评分员的文件夹里有密钥；一个标签带出了它的版本；考题的 origin 里能到达起点之后的提交；比较简报时漏了 agent 文件；"没有变差"的规则差一；目标规则在打平时通过；估算算了角色的花费却漏了评分；预算守卫忽略了重复使用的运行；`check_exam.py` 接受过期的哈希；哈希漏了模板；U4 漏掉 `python3 -`；U3 漏掉从 CRLF 改成 LF；U6 接受在第一次改动之后才读；CLI 版本不同还重复使用；以及 `gh` 替身放过了 `gh pr comment`。数量写进构建 PR 的描述。

### 14.3 试运行

构建 PR 开出之前，考试在 Troy 的电脑上真正运行一次，花费不超过第 10.2 节的 $300 上限：

1. **验证每道题**，在 troy-pstack 的 `main` 上：锚点，以及每道题五次运行，它们也是第一批 base 运行。PR 列出每道题锚点的评分，以及它的陷阱是否仍会触发。
2. **一个埋进去的改进。** 一个临时分支，永不合并，把 troy-pstack#63 的句子加进 DV1 的简报。用 `--fixes dv-mock-notes` 考它，必须让这道题通过。如果这道题的陷阱在 `main` 上不再触发，这一步改用另一个角色的一道仍会触发的题，并为它写一个修正，PR 里写明是哪道。
3. **一个埋进去的损害。** 一个临时分支，把 DV1 的第 2 步换成 "Implement each body as the design describes it."。考它必须让 dv-mock-notes 不通过。
4. **一个什么都不影响的修改。** 一个临时分支，在输出不变的前提下调换 `brief.py` 里两个函数的顺序。`affected` 必须找不到受影响的考题，考试必须记下 `no case affected`，不花一分钱。
5. **CI 里的检查。** 构建 PR 加了考题和测量工具，等于改了说明书文件集，所以它带着第 1 步得出的考试部分，CI 的新检查在它上面通过。
