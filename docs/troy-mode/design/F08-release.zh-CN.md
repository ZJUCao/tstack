## 1. 范围

F08 把版本发布流程（需求文档 5.5）加进 troy-mode 的入口技能（F07）。有了它，主会话会：

1. 在一个版本的第一个功能开始之前，让测试经理写出这个版本的测试方案（5.5 第 2 步，D70）；
2. 收到"发布 v0.1"时，检查这个版本是否就绪，让测试工程师写出这个版本的自动化测试，并在 Troy 的电脑上运行发布测试（5.5 第 3 步，5.6，D71）；
3. 开一个包含 changelog 的发布 PR，请 Troy 在自己的设备上测试这个版本并验收（3.3 第 4 步，D72）；
4. 把发现的每个 bug 交给修 bug 流程，然后再运行一次发布测试（5.5 第 4 步，D74）；
5. Troy 验收之后，合并发布 PR，并以 GitHub release 的形式打上标签 `vMAJOR.MINOR.PATCH`（5.5 第 5 步，D73）；
6. 做复盘，把 Troy 选中的规则交给规则变更流程（5.5 第 6 步，D76）；
7. 为发布之后修好的 bug 发布补丁版本，比如 v0.1.1（D75）。

F08 还解决了 F07 留下的一个问题：F07 的 `approve` 要在文档的修改记录里加一行（D77）。

版本规划（5.5 第 1 步）已经是产品经理的 PM1（F04 第 6.1 节），F07 也会读取版本计划。F08 不新增技能，而是扩展 F07 的技能和引擎。它按 Q10 对每个功能的规定，用一个 PR 合入。

## 3. 引擎

### 3.1 命令

```text
python troy_flow.py release-test   --version <vX.Y> --junit <path>... [common options]
python troy_flow.py accept-version --tag <vX.Y.Z> --notes-file <path> [--date <YYYY-MM-DD>] [common options]
python troy_flow.py release-notes  --tag <vX.Y.Z> --out <path> [common options]
python troy_flow.py retro          --tag <vX.Y.Z> [common options]
```

| 命令 | 作用 |
| --- | --- |
| `release-test` | 读取 `origin/main` 上的版本测试方案和发布测试的 JUnit 文件（第 5.5 节）。给出每个场景的结果、失败的测试、Troy 要运行的场景及其设备和步骤、被测的 commit，以及评论 `Release test, run <n>: passed` 或 `failed` 的正文。有任何失败时退出码为 1。 |
| `accept-version` | 在版本测试方案及其镜像里记录 Troy 的验收：验收记录里加一行（日期、带标签的 "Accepted"，以及 Troy 的备注），升到下一个主版本，状态改为 "Accepted by Troy on <日期>"，并按 D77 加一行修改记录（第 5.7 节）。 |
| `release-notes` | 把 `origin/main` 上 `CHANGELOG.md` 里这个标签的那一节写进一个文件，作为 GitHub release 的说明。 |
| `retro` | 从 GitHub 收集复盘需要的证据并分组（第 7 节）。它不做任何改动。 |

- `status` 增加发布状态和相应的下一步（第 3.2 和 3.3 节）。`brief` 学会 TM7 和 TE5，以及对版本测试 PR 的审查（第 5.3 节）。`approve` 增加 D77 的修改记录行（第 8 节）。
- 和 F07 一样，引擎只读取 git 和 GitHub，从不提交、推送或写 GitHub。这些由技能来做（F04 D29）。退出码与 F07 相同。

### 3.2 状态

发布状态和 F07 的其他状态一样，保存在 git 和 GitHub 上（D58）。

| 内容 | 读取来源 |
| --- | --- |
| 每个功能所属的版本，以及版本的先后 | `origin/main` 上 `docs/requirements.md` 的功能表 Version 列和版本计划 |
| 一个版本的测试方案 | `origin/main` 上的 `docs/versions/<vX.Y>/test-plan.md`。它的第 1 节列出它覆盖的功能。 |
| 一个版本的测试 | `origin/main` 上的 commit `[vX.Y tests] ...` |
| 发布 PR | 标题为 `[docs] Release vX.Y.Z` 的开着的 PR，或 `origin/main` 上这个 commit 标题 |
| 发布测试的每次运行和 Troy 的结果 | F08 在发布 PR 上的评论（第 5.6 节） |
| 已发布的版本 | 用 `gh release list` 读取的这个仓库的 GitHub release |
| 复盘 | 已合并的发布 PR 上的 `Retrospective: vX.Y.Z` 评论 |

### 3.3 下一步

`status` 给出这些新的 `next.action` 值。它们排在 F07 的初始化步骤和开着的 PR 之后，F07 先接着处理开着的 PR。

| 下一步 | 什么时候 | 接下来 |
| --- | --- | --- |
| `version-test-plan` | 下一个功能所属的版本没有测试方案，或者方案列出的功能和需求文档给这个版本的功能不一致（第 4 节） | 在 `troy-mode/<vX.Y>-test-plan` 上运行 TM7，由 F07 合并 |
| `release` | 最早一个还没发布的版本里，每个功能都已验收。`next.step` 根据状态给出发布的下一步：方案里有 Claude 运行的场景、而 `origin/main` 上还没有 `[vX.Y tests]` commit 时是 `version-tests`；然后，还没有发布 PR 时是 `release-pr`；再然后，发布 PR 还没有运行过、或者它最近一次运行失败而之后发现的 bug 都已修好时是 `release-test` | 第 5 节 |
| `tag` | 发布 commit 已在 `origin/main` 上，而 GitHub 上还没有这个标签的 release | 第 5.7 节 |
| `retro` | 一个版本（不是补丁）已经发布，它的发布 PR 上还没有 `Retrospective:` 评论 | 第 7 节 |

- 发布进行中时，发布 PR 排在其他所有开着的 troy-mode PR 之后，比如某个 bug 的 PR，因为它要等它们。F07 的规则是旁支 PR 排在阶段 PR 前面，其余按编号从小到大（F07 第 5.1 节）。
- 发布 PR 等 Troy 时，`status` 把它放进 `waiting_on_troy`，和 F07 处理等待批准的方式一样。

## 4. 版本测试方案（D70）

测试经理在版本规划时写出这个版本的测试方案（5.5 第 2 步）。实际做法是：这个版本里任何一个还没开始的功能，在它的第一个阶段之前，`status` 都会先要这份方案：

1. **TM7** 根据需求文档里的用户流程、原型、性能指标和版本计划，填写 `version-test-plan` 模板，生成 `docs/versions/<vX.Y>/test-plan.md` 及其镜像。每个场景都写明由谁运行：Claude，作为自动化的版本测试；或者 Troy，在只有 Troy 才有的设备上手动运行，比如手机（D71）。性能和压力用例来自需求文档里的指标。
2. **主会话**以产品经理的身份，对照需求文档检查这份方案：版本里的每个功能都出现了，这些功能的每个用户流程都有对应的场景。缺漏作为 Input 退回给 TM7。没有其他角色审查它。
3. **PR** 是 `[docs] Add the v0.1 test plan`。由 F07 合并，因为需求文档 3.3 没有把它列为要 Troy 批准的内容。发布时请 Troy 测试，Troy 那时会读到它。

当一项需求变更改动了这个版本的功能时，方案里的功能列表就对不上了，`status` 会再次要求运行 TM7：`[docs] Update the v0.1 test plan`。如果变更只改动某个功能的内部、功能列表不变，就通过 TM2 对版本测试的审查反映到方案里（第 5.3 节）。

## 5. 发布

### 5.1 步骤

"发布 v0.1"，或者在 `status` 给出 `release` 时说"继续"，就会开始下面这些步骤。只说"发布"指的是 `status` 给出的那个版本。

| 步骤 | 做什么 | PR | 合并者 |
| --- | --- | --- | --- |
| 1. 就绪 | 第 5.2 节的检查 | 无 | |
| 2. 版本测试 | TE5 为 Claude 运行的场景写测试。TM2 和 CR1 一起审查。没有场景由 Claude 运行时跳过。 | `[v0.1 tests] End-to-end and stress tests`，分支 `troy-mode/v0.1-tests` | F07 |
| 3. 发布 PR | PM4 在主会话里起草 changelog 的这一节 | `[docs] Release v0.1.0`，分支 `troy-mode/release-v0.1.0` | Troy 验收之后由 F07 合并 |
| 4. 发布测试 | 在 Troy 的电脑上运行回归测试和版本测试。报告发到发布 PR 上。 | 无 | |
| 5. Troy 的测试 | Troy 在自己的设备上运行 Troy 负责的场景，然后回复 | 无 | |
| 6. 验收 | PM4 设置状态，`accept-version` 填写验收记录。然后合并。 | 发布 PR | F07 |
| 7. 标签 | 在发布 PR 的合并 commit 上创建 GitHub release `v0.1.0` | 无 | |
| 8. 复盘 | 第 7 节 | 无 | |

### 5.2 就绪

F08 检查以下各项，并为每个问题说明怎样解决：

- 版本里的每个功能都已验收：它的 `accept` commit 在 `origin/main` 上。
- 没有开着的 troy-mode PR。开着的 PR 先由 F07 接着做完。
- 没有带 `bug` 标签的未关闭 issue，除非 Troy 决定推迟它（D74）。
- 自上一次发布以来，没有合入过后续版本功能的 mock、测试、实现或验收 PR。否则这个标签会包含一个不属于这个版本的功能。遇到这种情况，F08 升级上报（5.7），并给出 Troy 的选项。
- 版本测试方案列出的功能就是这个版本的功能（第 4 节）。
- 项目里 troy-mode 文件的副本和插件里的一致。版本测试 PR 需要新的 troy-check（第 9 节）。当 `status` 说副本较旧时，F08 先通过 troy-init 的 PR 流程运行它的升级，和 F07 处理"升级 troy-mode"的方式一样（F07 第 10 节）。

### 5.3 版本测试（D71）

- **位置。** 版本测试放在顶层文件夹 `version-tests/` 里，troy-check 把它归为测试类别（第 9 节）。语言包每个 PR 的测试运行不会收集它：pytest 只收集 `tests/`，C/C++ 语言包只在发布测试要求时才构建版本测试。所以每个 PR 的回归测试仍然只有单元、功能和集成测试，和 5.6 的规定一致。
- **TE5** 为方案里由 Claude 运行的每个场景写一个测试，再为每个性能和压力用例各写一个。每个测试自己的名字以它的场景编号开头：Python 里是 `test_v0_1_s01_counts_words_and_lines`，C++ 里是 `TEST(Version, V0_1_S01_CountsWordsAndLines)`。测试像用户那样通过项目的外部接口来做（TE1 的规则）。TE5 对 `origin/main` 上的代码运行它们。在那里失败的测试保持原样：TE5 在报告里列出它，附上场景的预期结果和实际发生的情况，绝不为了通过而改测试（F04 公共规则 11）。
- **审查。** TM2 检查：Claude 运行的每个场景都有测试，没有方案之外的测试，每个测试检查的是场景的预期结果，以及失败的测试是因为代码和方案不一致而失败，而不是测试写错了。CR1 审查代码。如果 TM2 发现某个场景已经和需求文档对不上，就先在一个 `[docs]` PR 里把方案退回给 TM7。
- **合并。** 审查通过、CI 通过后，F07 合并这个 PR，即使有版本测试失败也一样，因为 CI 不运行它们。失败的场景是发布测试的发现（第 5.8 节）。
- **后续版本**把自己的测试加进同一个文件夹，每次发布都运行全部测试，所以之前版本的场景会一直作为回归测试保留。补丁版本不加版本测试（第 6 节）。写错的版本测试，按 TM4 的裁决由 TE3 在 `[v0.1 tests] Fix v0.1-S03` PR 里修正。

### 5.4 发布 PR（D72）

在从 `origin/main` 建出的 `troy-mode/release-v0.1.0` 上，用 `--role product-manager` 拍快照：

- **PM4** 按 `changelog` 模板，在 `CHANGELOG.md` 及其镜像里加上这个版本的一节；项目第一次发布时，两个文件都由它新建。引擎的 `status` 根据 commit 标题列出这个版本的功能，以及上次发布以来修好的 bug。PM4 把它们分到 Added、Changed 和 Fixed 里。改动一个已验收功能的功能（F07 D65）放在 Changed 下。这一节的日期先写发布 PR 的日期，到第 6 步时由 PM4 改成 Troy 验收的日期。
- **PR 说明**写明 Why（版本计划里这个版本的那一行）、What（changelog 的这一节和这些功能）以及 Checks。
- F07 推送分支并开 PR。之后的每一步都在这个 PR 上留评论，所以新会话能在中断的地方找到这次发布。

### 5.5 发布测试

在 Troy 的电脑上，在发布分支上运行。发布分支就是 `origin/main` 加上 changelog：

1. **回归测试。** 语言包的步骤，和实现 PR 一样（F07 第 8.1 节），包括 `troy-check code`。每个测试都必须通过，或者在本平台跳过、以 CI 在 `main` 上的结果为准（F07 D69）。
2. **版本测试。** 语言包的发布命令，来自任务简报里的检查。Python：`pytest version-tests --junitxml=reports/version-junit.xml`。C/C++：用 `TROY_VERSION_TESTS=ON` 构建，再运行带 `--output-junit reports/version-junit.xml` 的 `ctest -L version`。性能和压力用例也在这里、在 Troy 的电脑上运行（Q7）。
3. **报告。** `release-test --version v0.1 --junit reports/junit.xml --junit reports/version-junit.xml`。F08 把它的评论发到发布 PR 上：`Release test, run 1: passed` 或 `failed`，接着是每个场景的结果和失败的测试。

没有测试失败、并且 Claude 运行的每个场景都有通过的测试，这次运行才算通过。失败的情况先按第 5.8 节处理，然后才请 Troy 测试。

### 5.6 Troy 的测试

一次运行通过之后，F08 在发布 PR 上发出 `Waiting for Troy: accept v0.1.0`，运行 `status --waiting`，并用 Troy 的语言在聊天里告诉 Troy：

- 要测试的 commit，以及带 changelog 的发布 PR 的链接；
- Claude 运行过的场景及其结果；
- Troy 要运行的每个场景：设备、步骤和预期结果，都取自方案。

然后它停下。Troy 在聊天里回复，或者在发布 PR 上评论：

| Troy 的回复 | F08 怎么做 |
| --- | --- |
| 验收通过，可能附带备注 | 第 5.7 节 |
| 某个场景失败 | 第 5.8 节。之后 Troy 只重新测试失败的场景，除非 Troy 要求测更多（D74）。 |
| 不验收，原因不是 bug，比如某个功能不是 Troy 想要的 | 需求变更流程（F07 第 11.2 节）。发布要等变更后的功能验收之后再继续。 |

F08 把每次回复记录到发布 PR 上，标题为 `Release test by Troy, run <n>: accepted`、`failed` 或 `not accepted`，后面附上 Troy 的原话，这样新会话也知道答案。

### 5.7 验收和标签（D73）

Troy 验收之后：

1. **PM4** 在发布分支上、用 `--role product-manager` 拍快照：把版本里每个功能的状态改为"在 Troy 的设备上可用"，中英文都改（F01 第 7 节，R13）；需求文档的 `version` 升一个次版本，并加一行修改记录；changelog 这一节的日期改为验收日期。
2. **`accept-version --tag v0.1.0 --notes-file <文件>`**，Troy 的备注写在这个文件里。
3. **合并。** F07 暂存这两部分的路径，修订 commit，运行本地检查，推送，等 CI，然后合并（F07 第 8.6 节）。
4. **标签。** `release-notes --tag v0.1.0 --out <文件>`，然后 `gh release create v0.1.0 --target <合并 commit> --title v0.1.0 --notes-file <文件>`。GitHub 在这个 commit 上创建标签，所以不需要从 Troy 的电脑推送任何东西。
5. **向 Troy 报告**，并运行 `status --write-progress`。

如果 Troy 改为在 GitHub 上合并发布 PR，状态和验收记录就会缺失。这时 `status` 给出 `[docs] Record Troy's acceptance of v0.1.0`，F07 在打标签之前开出并合并它。

创建 GitHub release 加入 F07 的权限（F07 第 9 节）。它只在 Troy 验收之后进行，而且只针对发布 PR 的合并 commit。

### 5.8 失败和 bug（D74）

- **失败的测试或场景**，无论来自发布测试还是 Troy 的测试，都交给 TM5，报告放在 Input 里。bug 会建一个 issue，走修 bug 流程的 PR A 和 PR B（F07 第 11.1 节）。写错的版本测试由 TE3 修正（第 5.3 节）。误解的需求交给变更流程。
- **未关闭的 bug。** 发布要等所有带 `bug` 标签的未关闭 issue 都修好。Troy 可以在聊天里推迟其中一个：F08 在发布 PR 上记下它，`accept-version` 把它写进验收记录里 Troy 的备注。
- **修好之后**，PM4 把修好的 bug 加进 changelog 的这一节，F07 把发布分支 rebase 到 `origin/main` 上并修订 commit，然后发布测试作为第 2 次运行重新进行。它运行全部版本测试，因为成本很低。Troy 只重新测试失败的部分。

## 6. 补丁版本（D75）

"发布 v0.1.1"会发布 v0.1.0 之后合入的 bug 修复。只有在 v0.1.0 之后还没有合入后续版本功能的 mock、测试、实现或验收 PR 时，才允许这样做。否则这些修复随下一个版本发布，F08 会说明这一点。

补丁版本运行第 5.1 节的第 1 步和第 3 到 7 步。它不写版本测试方案，也不写版本测试。发布测试运行同样的回归测试和全部版本测试。Troy 测试修好的 bug 涉及的场景。changelog 的 `v0.1.1` 一节只有 Fixed。功能保持原来的状态。`accept-version` 在 v0.1 的验收记录里为 v0.1.1 加一行。补丁版本不做复盘。

## 7. 复盘（D76）

一个版本打上标签之后，F08 把这个版本期间反复出现的问题变成规则提案（5.5 第 6 步）：

1. **证据。** `retro --tag v0.1.0` 读取上一个版本的标签之后合入的 PR，没有上一个标签时从项目的第一个 PR 开始。它收集 F07 在这些 PR 上的评论：每次要求修改的审查，以及按每条意见所指的规则编号或检查项分组的意见（F04 第 5.2 节）；每次失败的尝试，以及失败的检查；以及每次升级上报。它再加上这段时间修好的 bug（来自它们的 issue），以及 Troy 电脑上还留着的 `hooks.log` 记录（F05 第 10 节）。它统计每一组出现在多少个 PR 里。出现在两个或更多 PR 里的一组就是反复出现的问题，这也是 `correct` 认定一类错误的方式。
2. **提案。** 主会话对这些反复出现的问题，按 `correct` 的方法（`${CLAUDE_PLUGIN_ROOT}/skills/correct/SKILL.md`）来做：为每个问题找出可行的最强执行方式（需求文档 5.8 第 2 步），并判断它属于这个项目还是所有 troy-mode 项目。它不写代码：每个提案都是交给规则变更流程的一条规则。
3. **Troy 挑选。** 给 Troy 发一条消息：每个反复出现的问题及其证据和 PR 链接，每个提案附一个推荐。没有反复出现的问题时，消息就这样说明。F08 把同一份报告用英文发到发布 PR 上，标题为 `Retrospective: v0.1.0`，这次发布到此结束。
4. **规则。** Troy 选中的每条规则逐条走规则变更流程（5.8，F09）。如果 F09 还没实现，F08 就这样说明，并把选中的规则写进进度文件的备注。

需求文档 4.1 也提到了 `reflect`，它挖掘的是一次对话的记录。一个版本跨越很多次会话，所以 F08 改为读取 PR 评论，那里有同样的审查意见和失败记录。

## 8. 在修改记录里记录批准（D77）

F07 的 `approve` 只改文件头的字段（F07 D61），所以文档的修改记录里缺了 Troy 批准时给出的那个版本。试运行仓库的需求文档就是这样：版本是 2.0，修改记录只有 0.1、1.1 和 1.2 三行。

F08 让 `approve` 同时在文档的修改记录里加一行，中英文都加：新的版本号、日期，以及 "Approved by Troy."（中文为"Troy 批准。"）。这一行加在标题为文档修改记录的那张表的最后。没有修改记录的文档不加。`accept-version` 用同样的方式加它的那一行，内容为 "Accepted by Troy as v0.1.0."。这改动了需求文档 3.3：troy-mode 在文档的文件头和修改记录里记录批准。

## 11. F08 怎样检查

### 11.1 测试

测试用 `unittest` 和标准库。由另一个代理在代码写出来之前，根据这份设计来写。它们沿用 F07 的做法：一个临时 git 仓库，用本地裸仓库作 `origin`；`PATH` 上有一个假的 `gh`，从一个 JSON 文件提供 PR、评论、issue 和 release，并记录每次调用。测试放在 `troy-mode/flow/tests/`，对 troy-check、模板和角色的改动在各自的测试套件里加测试。

| 分组 | 用例包括 |
| --- | --- |
| 状态 | 在一个没有方案的版本的第一个阶段之前给出 `version-test-plan`，方案的功能列表不一致时再次给出。版本里每个功能都验收之后给出 `release`。依次给出发布的步骤 `version-tests`、`release-pr` 和 `release-test`，然后是 `tag` 和 `retro`。方案里没有 Claude 运行的场景时，没有 `version-tests` 这一步。发布 PR 排在某个 bug 的 PR 之后。一次通过的运行之后等 Troy。允许补丁版本，以及后续版本的实现合入之后拒绝补丁版本。 |
| 发布测试 | 按编号把场景和测试对应起来，大小写、`-`、`_` 和 `.` 视为相同。Claude 运行的场景没有测试时失败。回归测试失败时失败。在本平台跳过的测试算通过。列出 Troy 的场景及其设备和步骤。评论的标题和运行次数。 |

### 11.2 埋 bug

代码通过之后，在一份临时副本里一次埋一个 bug，每个都必须让某个测试失败。这些 bug 包括：版本的第一个功能之前没有要求写版本测试方案、不比较方案的功能列表、有功能未验收时也给出发布、发布 PR 排在某个 bug 的 PR 前面、没有测试的场景算作通过、跳过的测试算作失败、验收行只写了英文、`approve` 没有加修改记录行、说明取错了一节、后续版本的实现合入之后仍允许补丁版本、`retro` 读了上一个标签之前的 PR，以及只出现一次的意见被算作反复出现。数量写进 PR 说明。

### 11.3 试运行（D78）

PR 开出之前，F08 在 Troy 电脑上的嵌套 `claude -p` 会话里运行，troy-pstack 从 PR 分支加载，用的是私有临时仓库 `ZJUCao/troy-mode-trial`，和 F07 的试运行一样（F07 第 14.3 节）。试运行的提示给出 Troy 的回答，包括 Troy 在设备上的测试结果。这些会话会访问 GitHub，所以只有 Troy 在聊天里同意之后才开始试运行。

这个仓库的 v0.1 包含 F01（已验收）、F03（在第 4 阶段）和 F02（未开始）。

1. **升级。** troy-init 的升级通过它自己的 PR，带来新的 troy-check 和模板。
2. **缩小版本。** 一项需求变更把 F02 移到 v0.2，于是 v0.1 只有 F01 和 F03。Troy 的批准由提示给出。
3. **版本测试方案。** "继续"会在 F03 往下做之前要求写 v0.1 的测试方案。TM7 写出它，F07 合并。
4. **F03。** F03 走完它的测试、实现和验收 PR。
5. **发布。** "发布 v0.1"：TE5 写版本测试，TM2 和 CR1 审查，然后在 Troy 的电脑上运行发布测试。发布 PR 等 Troy，那个会话结束。
6. **接续并验收。** 一个新会话从提示得到 Troy 的验收，合并发布 PR，并创建 GitHub release `v0.1.0`。
7. **复盘。** 对从头开始的所有 PR 运行 `retro`。Troy 的回答（来自提示）不选任何规则。
8. **分派。** "发布 v0.2"会报告 F02 还没验收。"发布 v0.1.1"会报告 v0.1.0 之后没有合入任何修复。

按 F07 试运行的花费估算，大约运行 9 次角色（TM7、TE1、TM2、CR1、DV2、CR1、TE5、TM2、CR1），约 8 到 12 美元，另外大约 9 个 PR 各用几分钟 Actions 时间。仓库和它的 release 保留。是否删除由 Troy 决定。
