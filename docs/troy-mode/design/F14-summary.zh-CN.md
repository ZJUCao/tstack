## 1. 范围

F14 让 Troy 能很快读懂每个要 Troy 批准的 PR。这种 PR 的描述以一页中英文摘要开头：对 Troy 这个用户来说有什么变化，Troy 要决定的每一点和对应的推荐，以及风险，都用平常的话写（需求文档 3.3、5.2 和 Q16）。

F14 交付：

1. 摘要的三个部分、长度上限和写法，做成一个新模板（第 3 节，D133）；
2. 哪些 PR 有摘要（第 4 节，D132）；
3. 谁来写，以及它怎样进入 PR 和聊天（第 5 节，D131 和 D135）；
4. 一条新的硬规则 R22，由 troy-check 在 CI 里检查，以及架构师设计检查清单的第七项（第 6 节，D134）；
5. 一个新的插件版本，把它带进试点（第 8 节，D137）。

摘要放在 PR 描述里，不放在文档里。设计、测试计划、需求和架构都保持原来的样子，只有设计里的架构师审查表多一行。F14 用一个 PR 合入（Q10）。

## 2. Troy 现在读的是什么

在试点项目 `ZJUCao/recipe-menu` 里，Troy 批准每个功能的设计和测试计划：2026-11-11，在 F03 之后，Troy 把 `troy_approves_first` 设成了 16。每个功能的这两份文档有这么多字符：

| 功能 | 设计，英文 | 测试计划，英文 | 两份合计，英文 | 两份合计，中文镜像 |
| --- | --- | --- | --- | --- |
| F01 | 32,466 | 29,611 | 62,077 | 42,296 |
| F02 | 41,790 | 46,957 | 88,747 | 61,104 |
| F03 | 73,793 | 83,391 | 157,184 | 111,704 |
| F04 | 76,724 | 80,811 | 157,535 | 107,451 |
| F05 | 87,122 | 93,621 | 180,743 | 123,400 |
| F06 | 63,887 | 84,514 | 148,401 | 103,105 |
| F07 | 44,127 | 57,544 | 101,671 | 66,181 |
| F08 | 66,018 | 68,117 | 134,135 | 85,388 |
| F09 | 75,047 | 81,287 | 156,334 | 104,713 |
| F10 | 54,700 | 71,784 | 126,484 | 83,708 |

现在告诉 Troy 要决定什么的内容分散在三个地方，没有一个是写给 Troy 看的：

- **PR 描述**按 PR 模板写：Why、What、Checks 和 Soft-limit reason。试点的 20 个设计和测试计划 PR 里，它有 1,473 到 4,190 个英文字符，是为了留档写的，满是接口名、章节号和编号。模板里没有写 Troy 要决定什么的地方。
- **设计文档**在第 2 节快结尾处列出这些点。F10 的设计写着"Troy decides these two points"，也就是 A 点和 B 点，夹在讲模块和常量的段落中间。
- **评论 `Waiting for Troy: approve this PR`** 用 185 到 1,065 个字符把这些点再说一遍，主会话也在聊天里告诉 Troy。它们读起来像角色之间的笔记：PR 59 的几点提到测试用例 `F04-T38` 和常量 `TO_TASTE`，PR 65 的提到常量 `EMPTY_WORD` 和"the places `tag` and `名称`"，架构的 PR 3 提到 ADR-0004 和 PT01。

Troy 说过，满是术语和编号的解释很难看懂。F14 把 Troy 需要的内容放在一个地方，用固定的格式和平常的话写出来。

## 3. 摘要

### 3.1 放在哪里

摘要是 PR 描述里的第一部分，在 Why 之前。先是中文部分，再是英文部分（D135）：

```text
## 给 Troy 的摘要          中文部分（第 3.2 节）
## Summary for Troy        英文部分
## Why                     PR 模板原有的几节，和现在一样
## What
## Checks
## Soft-limit reason
```

英文部分是原文，中文部分说的是同样的内容，和 troy-mode 的每份文档一样（R12）。中文放在前面，是因为 Troy 和 troy-mode 用中文交流，而 GitHub 的通知邮件和 PR 页面最先显示的是描述的开头。

PR 等 Troy 批准时，主会话还会在聊天里发这份摘要，用 Troy 说话的语言，附上 PR 的链接（第 5.3 节）。

### 3.2 三个部分

每种语言都有同样的三个部分，标题固定，顺序固定：

| 英文标题 | 中文标题 | 写什么 |
| --- | --- | --- |
| `### What changes for you` | `### 对你有什么变化` | PR 的内容做出来以后，Troy 要输入、会看到或要做的事有什么不同：新命令和选项、变了的输出、Troy 要编辑的新文件，以及哪些不变。测试计划写：测试检查了其中哪些，没检查哪些，以及有什么要 Troy 手动运行。架构写：Troy 会注意到的东西，比如速度、程序保存的文件、要安装的工具，以及以后难改的地方。需求写：程序会做什么，或者会有什么不同。 |
| `### What you decide` | `### 需要你决定的事` | Troy 要决定的每一点各占一个编号条目，最后是下面那句固定的回复说明。每个条目：用几个加粗的词说决定什么；各个方案，写成 Troy 在每个方案下会看到什么；`推荐：`（`Recommended:`）后面写推荐的方案和一句理由。没有要决定的事时，只写 `没有需要你决定的事。`（`Nothing to decide.`），也不写回复说明。 |
| `### Risks` | `### 风险` | 对 Troy 来说可能出什么问题，可能性多大，出了问题会怎样。没有风险时写 `没有发现风险。`（`None found.`）。 |

回复说明在每份摘要里都一样：

- 英文：`Reply "all as recommended" (全按推荐) to take every recommendation, or give the number and the option you want.`
- 中文：`回复「全按推荐」即可全部采用推荐，或写出编号和你选的方案。`

摘要不重复 Why、What 或 Checks 里的内容。那几节留着，给留档和各个角色用。

### 3.3 一页（D133）

"一页"就是**每种语言最多 2,000 个字符**。一个部分从它的 `##` 标题的下一行算到下一个 `##` 标题的上一行，去掉两头的空白，按写出来的样子计数，Markdown 符号也算。一个字符是一个 Unicode 码位，所以一个汉字和一个字母都算一个。

- 2,000 个英文字符大约是 300 个英文词，读一两分钟，在笔记本电脑上一屏放得下。
- 中文部分更短：英文写满时，中文大约是 900 到 1,200 个字符，因为同样的内容中文用的字符大约只有英文的一半。第 3.5 节的例子比例是 0.43，troy-pstack 自己的中英文对照是 0.51（F11 设计）、0.52（F10 设计）和 0.59（指南第 03 页）。行内代码，比如一条命令，在两种语言里一样长。
- 现在的 `Waiting for Troy` 评论有 185 到 1,065 个字符，放得下；第 3.5 节有两点要决定的例子也放得下。这份设计自己的 PR 摘要有七点要决定，英文部分 1,977 个字符：初稿是 2,033 个，删了一句才放下。要决定的点更多的设计，就要把每一点说得更短，或者拆开，这正是上限的用意。

项目可以在 `.troy-mode/config.toml` 里用 `[summary] max_chars` 改这个上限，走规则变更流程，和改 troy-check 的其他上限一样（F09 设计 D84）。

### 3.4 平实的话（D133）

模板的填写说明和作者的指令给出这些规则：

1. **把 Troy 当用户来写。** 说 Troy 要输入什么、会看到什么、要做什么。不说代码是怎么搭的。
2. **不写内部编号。** 不写规则编号（R03、P01）、决定编号（D12）、问题编号（Q4）、测试用例编号（F04-T07）、场景编号（v0.1-S03）、ADR 编号、性能目标编号（PT01）、任务编号（IF1）或章节号。直接说那个东西："搜索的 1 秒上限"，而不是"PT01"。功能编号（比如 F10）、bug 编号（比如 #12）和版本号（比如 v0.1）可以出现，因为 Troy 在 PR 标题和状态表里看得到它们。
3. **只有 Troy 要输入或会看到的才写成代码**，放在反引号里：命令、选项、Troy 要编辑的文件名，以及程序的输出。不写函数、模块、类或常量的名字。
4. **短句，常用词。** Troy 可能不懂的词，用几个字解释，或者干脆不写。
5. **每个方案都写 Troy 在这个方案下会看到什么。** 写"报错，提示你写一个词"，不写"抛出 `UsageError`"。
6. **每个推荐都用一句话说理由。**

### 3.5 一个例子

按这些规则，根据已批准的设计写出的 F10 设计摘要。中文部分 491 个字符，英文部分 1,137 个字符。

```markdown
## 给 Troy 的摘要

### 对你有什么变化

你可以输入 `recipe-menu search 词...` 来找菜谱。它列出名称、食材或标签里包含你给的每一个词的菜谱，中英文都行，英文不分大小写，每一行还写明词是在哪里找到的。帮助里多一行 `search`。别的命令都不变。

### 需要你决定的事

1. **原型里没有的新提示。** 例如 `2 recipes match "葱" and "quick".` 和 `没有菜谱匹配“lamb”。`。推荐：照写的接受，它们和原型里的句子是同一种说法。
2. **输入空词，比如 `search ""`。** 方案 1：报错，提示你写一个词。方案 2：当作什么都没找到。推荐：方案 1，因为打错字不该看起来像“没有这个菜”。

回复「全按推荐」即可全部采用推荐，或写出编号和你选的方案。

### 风险

- 速度：1,000 个菜谱时，`search` 在你的电脑上大约要 0.8 秒，离 1 秒的上限不远。以后哪次改动让它变慢，会先单独提速。
- `search` 不查菜谱的编号，所以拼错的编号，比如 `tomato-eggs`，什么也找不到。

## Summary for Troy

### What changes for you

You can type `recipe-menu search WORD...` to find recipes. It lists the recipes whose name, ingredients, or tags hold every word you give, in English or Chinese, with English capitals ignored, and each row says where the word was found. The help gains a line for `search`. No other command changes.

### What you decide

1. **New messages that no prototype shows.** For example `2 recipes match "葱" and "quick".` and `没有菜谱匹配“lamb”。`. Recommended: accept them as written, because they follow the prototype's sentences.
2. **An empty word, such as `search ""`.** Option 1: an error that asks you for a word. Option 2: it finds nothing. Recommended: option 1, because a typing mistake should not look like "no such recipe".

Reply "all as recommended" (全按推荐) to take every recommendation, or give the number and the option you want.

### Risks

- Speed: with 1,000 recipes, `search` takes about 0.8 seconds on your PC, close to its 1-second limit. If a later change slows it down, a speed fix comes first, in its own PR.
- `search` does not look at recipe IDs, so a mistyped ID such as `tomato-eggs` finds nothing.
```

这份设计自己的 PR 描述也以同样格式的摘要开头，算第二个例子。

## 4. 哪些 PR 有摘要（D132）

| PR | 标题 | 谁写它的文档 | 有没有摘要 |
| --- | --- | --- | --- |
| 接口设计（PR 1） | `[F04 1/6 design] <name>` | 接口设计师 | 有（需求文档 5.2） |
| 测试计划（PR 2） | `[F04 2/6 test-plan] <name>` | 测试经理 | 有 |
| 需求 | `[docs] Add the requirements`、`[docs] Change the requirements: <summary>` | 产品经理 | 有 |
| 架构 | `[docs] Add the architecture`、`[docs] Change the architecture for <ID>` | 架构师 | 有 |
| 发布 | `[docs] Release <tag>` | 产品经理 | 没有。F08 发给 Troy 的消息已经列出 Troy 要在自己设备上跑的场景（F08 设计 5.6）。 |
| 其他所有 PR | | | 没有。Troy 不批准它们。 |

这几种 PR 的文档都要 Troy 批准（需求文档 3.3 第 1 到 3 步）。设计或测试计划 PR 即使由 troy-mode 自己合并（也就是前 `troy_approves_first` 个功能之后），也照样有摘要，理由有三个：

- 这样 R22 只看标题就知道 PR 要不要摘要，不需要知道合并权限（第 6.1 节）。
- 批准改成抽查以后（F18），Troy 会抽看其中一部分 PR，摘要就是 Troy 快速读懂一个 PR 的办法。
- 写一份摘要，作者大约要写 3,000 个字符，而文档有 60,000 到 180,000 个字符。

升级上报不是 PR，保持它自己的格式（原型 C，需求文档 5.7）。

## 5. 谁来写（D131）

### 5.1 作者

写文档的角色来写它的摘要，因为它最了解这份文档：

| 文档 | 作者 | 返回摘要的任务 |
| --- | --- | --- |
| 接口设计 | 接口设计师 | IF1，以及每次修改用的 IF2 |
| 测试计划 | 测试经理 | TM1，以及每次回答问题或裁决之后重跑的 TM1 |
| 架构 | 架构师 | AR1，以及写架构变更的那次运行 |
| 需求 | 产品经理，在主会话里 | PM1 和 PM2 |

主会话就是产品经理，所以需求的摘要由它自己写。其他文档的摘要它只读不写。要它写，就得在主会话里读完一份 60,000 到 180,000 个字符的文档，而试点里主会话的上下文已经压缩过 10 次了。

### 5.2 报告字段

接口设计师、测试经理和架构师的报告最后多一个字段：

```text
For Troy: <None, or the filled summary template. It runs to the end of the report.>
```

在第 5.1 节列出的任务里，它放填好的模板 `troy-mode/templates/summary-for-troy.md`（第 7 节）；在其他任务里写 `None`。这些任务的简报会写明这一点：引擎给 IF1、IF2、TM1、AR1 和 AR6 架构变更的任务句子加上"Write the summary for Troy from the summary-for-troy template in your report's For Troy field."。在需求变更流程里由 AR4 写架构变更时，主会话把同一句话加进简报的 Input。

### 5.3 从报告到 PR 和聊天

主会话：

1. **写描述**：先放报告里的 For Troy 内容，原样不动，然后是 Why、What、Checks 和 Soft-limit reason，和现在一样。
2. **按第 3.4 节把摘要读一遍。** 它可以把某句话改得更平实，但不改某一点、某个方案或某个推荐的意思。要改意思，就交回作者，算一轮。
3. **跑本地检查。** `troy-check pr --body-file` 现在也跑 R22。不通过就把问题作为 Input 交回作者，算一次尝试，和其他检查不通过一样（F07 设计 D64）。报告里没有 For Troy 内容也算不通过。
4. **把摘要交给 AR2**，放在它简报的 Input 里，供检查清单第七项用（第 6.2 节）。
5. **每次修改之后**，用 `gh pr edit <number> --body-file <file>` 把描述里的摘要换成新的。修改描述后 CI 会再跑一遍。
6. **PR 等 Troy 时**，发 `Waiting for Troy: approve this PR`，下面只有一行："What to decide is in the summary at the top of the description."。然后在聊天里把描述里的摘要原样发给 Troy，用 Troy 说话的语言，附上 PR 的链接。

需求的摘要由主会话以产品经理的身份在第 1 步写，再经过第 2、3、6 步。

### 5.4 Troy 的回复

回复的方式和现在一样（F07 设计 D61）：

- "全按推荐"、"all as recommended" 或 "approved" 表示批准这个 PR，并采用全部推荐。troy-mode 记下批准，描述的 What 写明 Troy 采用了全部推荐。
- 选了别的方案的回复，比如"2：方案 2"，就是要求修改。作者修改，算一轮，PR 再等 Troy 一次。这种修改之后还要不要再等 Troy，是 F18 的问题，不是 F14 的。

## 6. 怎样检查（D134）

### 6.1 troy-check 里的 R22

一条新的硬规则：

> **R22.** 每个设计、测试计划、需求和架构 PR 的描述都以给 Troy 的中英文摘要开头：对 Troy 有什么变化，Troy 要决定的每一点和对应的推荐，以及风险。每种语言最多 2,000 个字符，不含内部编号。

`troy-mode/checks/troycheck/summary.py` 在 `troy-check pr` 里检查它，所以本地检查和 CI 都会跑。在 CI 里，检查程序从基准 commit 运行，和每项 PR 检查一样（F02 设计 8），所以 R22 从带来它的升级合入之后开的第一个 PR 起生效。

**哪些 PR。** 标题的类型是 `design` 或 `test-plan`，或者类型是 `docs` 且标题的摘要部分以 `Add the requirements`、`Change the requirements`、`Add the architecture` 或 `Change the architecture` 开头时，R22 生效。其他 PR 它报 SKIP："Not a PR that needs a summary."。没有描述时，比如本地运行没给 `--body-file`，它也报 SKIP。CI 总会传入描述。

**检查什么。** 每项不通过的检查在 R22 的 FAIL 里加一行：

| 检查 | 不通过的情况 |
| --- | --- |
| 顺序 | 第一个非空行不是 `## 给 Troy 的摘要`，或者下一个 `##` 标题不是 `## Summary for Troy`。 |
| 部分 | 某个部分没有恰好第 3.2 节那三个 `###` 标题，或顺序不对，或某个标题下面没有内容。 |
| 长度 | 某个部分超过 `max_chars` 个字符，按第 3.3 节的方法计数。消息里给出字符数和上限。 |
| 决定 | 在"决定"标题下，某个编号条目（以 `1.`、`2.` 等开头且没有缩进的行）英文里没有 `Recommended:`，或中文里没有 `推荐：` 或 `推荐:`；或者没有编号条目，而内容又不是 `Nothing to decide.` 或 `没有需要你决定的事。`；或者两个部分的条目数不同。 |
| 中文 | 中文摘要的某个 `###` 部分里一个汉字也没有。 |
| 编号 | 某个部分在行内代码和代码块之外含有内部编号（见下表）。消息给出这个编号和它所在的行。 |

| 内部编号 | 格式 | 例子 |
| --- | --- | --- |
| 规则 | `R` 或 `P` 加两位数字 | R03、P01 |
| 决定 | `D` 加一到三位数字 | D61 |
| 待定问题 | `Q` 加一到两位数字 | Q16 |
| 测试用例 | `F` 或 `B`、数字、`-T`、数字 | F04-T38 |
| 场景 | `v`、版本号、`-S`、数字 | v0.1-S23 |
| ADR | `ADR-` 加数字 | ADR-0004 |
| 性能目标 | `PT` 加数字 | PT01 |
| 角色任务 | `AR`、`IF`、`TM`、`DV`、`TE`、`CR` 或 `PM` 加一位数字 | IF1 |

只有前后紧挨着的都不是 ASCII 字母或数字时才算匹配，所以 `F10` 和 `3D` 不算，而紧跟在汉字后面的编号，比如 `见R03`，算。行内代码里的编号交给作者和主会话把关，因为命令和程序输出都放在那里。

**配置。** `config.default.toml` 加上 `[summary] max_chars = 2000`，和其他上限一样从合并基准 commit 读取。

R22 检查的是格式。R20 照样检查没有留下模板标记或填写说明，R19 照样检查描述里没有署名。

### 6.2 架构师的第七项

架构师的接口检查清单（需求文档 5.2，AR2）多一项：

- **给 Troy 的摘要和设计说的一致，并列出 Troy 要决定的每一点。**

设计模板第 4 节的表格在两种语言里都加上这一行，AR2 根据 Input 里的摘要填写。架构师发现要 Troy 决定的点，比如 PR 59 里作为选择交给 Troy 的那几条不阻塞的意见，算这一项下的意见：接口设计师在下一轮把它加进设计和摘要，这样 Troy 要决定的每一点都在摘要里。

### 6.3 检查覆盖不到的

- 话写得够不够平实。R22 能抓出编号和格式问题，主会话会读每一份摘要（第 5.3 节第 2 步），剩下的靠试点里 Troy 的反馈。
- 测试计划、需求或架构的摘要和它的文档是否一致。这些文档在给 Troy 之前没有别的角色审查，所以它们的摘要只有主会话读。第 9.3 节的演练会把摘要和文档对照一次。

## 8. 试点怎样用上 F14（D137）

F14 在 troy-pstack 里的实现 PR 会提高插件版本。F14 是一个功能，所以提高次版本号（F10 设计 D89），合入时取下一个没用过的号：如果 F12 和 F13 都还没提高过，就是 0.3.0。修订号留给修复挡路问题的改动（F11 设计 D96）。

然后，试点不停：

1. **Troy 更新插件**：运行 `claude plugin update troy-pstack@troy-pstack`，然后重启 Claude Code（F10 设计 6）。如果 F12 或 F13 同一天合入，一次更新和一次重启就能把它们都带上，所以由协调会话在最后一个合入之后只告诉 Troy 一次。
2. **Troy 在试点文件夹里输入 `/troy-pstack:troy-mode upgrade troy-mode`。** troy-init 的 `[rules] Upgrade troy-mode to <version>` PR 会替换 troy-check（现在带 R22）、模板、PR 模板和规则表的 R 行，检查通过后由 troy-init 合并（F06 设计 6、F11 设计 7）。技能、代理和引擎随插件本身更新。
3. **下一个设计或测试计划 PR** 就以摘要开头。troy-mode 一次只处理一个 PR，所以升级会等到正在进行的阶段 PR 合入之后，不会有 PR 做到一半才被 R22 检查。

试点现在做到 F10 的实现，后面还有 F11、F12 和 F13。升级之后的每个设计和测试计划 PR 都有摘要，试点报告会写明哪些有（F11 设计 8）。

## 9. F14 怎样检查（D136）

### 9.1 测试

一个单独的代理在代码写出来之前，只根据这份设计写测试，用 `unittest` 和临时 git 仓库，和 F02 的检查一样。`test_r22.py` 至少覆盖：

- 第 6.1 节说的每种 PR，有摘要和没摘要两种情况，以及另一类 `[docs]` PR，它应被跳过；
- 一份能通过的摘要，格式和第 3.5 节一样；
- 第 6.1 节表格里的每一项单独不通过：顺序错、少了或改了名的部分、没有内容的部分、某种语言 2,001 个字符、没有推荐的条目、条目数不同、"没有要决定的事"的写法、没有汉字的中文部分，以及每一种编号；
- 行内代码和代码块里的编号（通过），紧跟在汉字后面的编号（不通过），以及更长的词里的编号，比如 `F10` 或 `PR03X`（通过）；
- `max_chars` 从合并基准 commit 的配置读取，所以 PR 不能自己放宽上限；
- 描述用 CRLF 换行。

简报测试检查新的任务句子。checks、init、flow、dev 和 hooks 这几组测试在 Linux 和 Windows 上都通过。

### 9.2 埋 bug

代码通过以后，在临时副本里一次埋一个 bug，每个都必须让某个测试失败：按字节计数长度、从 PR 自己的 commit 读上限、不检查两个部分的顺序、不比较条目数、在行内代码里找编号、在编号边上用 `\b`（这样 `见R03` 能通过），以及不匹配 `docs` 的那几个开头。数字写进实现 PR 的描述。

### 9.3 在试点文档上演练

在实现会话里，几个新的代理按 IF1 和 TM1 的新指令，给试点已批准的 F09 和 F10 的设计和测试计划写摘要。文档从 `D:\Troy\Projects\recipe-menu` 读取，那里什么也不写。R22 的代码检查这四份摘要。另一个新的代理把每份摘要和它的文档放在一起读，列出写错或漏掉的地方。实现 PR 的描述里放上这四份摘要和发现的问题，这样 Troy 在试点用上 F14 之前就能看到它写出来的样子。
