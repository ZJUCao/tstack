## 1. 范围

F20 让 troy-mode 同时开发互不依赖的功能，每个功能由自己的团队来做，按需求文档 5.11 节的要求。Troy 于 2026-11-22 批准了需求（需求文档 1.54）：一个主会话统筹所有团队并运行所有团队的角色（Q17）；团队数不设上限（Q18）；一个功能在它依赖的功能都已验收、且架构师的规划允许之后开始（Q19、Q20）；每个团队在自己的 git 工作树里工作（Q21）；谁先做好谁先合并，其他团队 rebase（Q22、R24）；一处等待只停它自己的团队（Q23）；需求变更、规则变更和发布只停受影响的团队（Q24）。

本设计交付：

1. **团队。** 一个引擎命令创建团队的工作树，并在功能验收后删除它（第 3.1 节）。
2. **角色在自己团队的工作树里工作。** 简报写明团队的检出目录，F05 的 hook 从简报得知团队，并让角色的命令在那里运行（第 3.2 节）。
3. **按团队的 hook 和检查。** 每个团队的记录和日志行放在它工作树自己的 git 文件夹里，`snapshot` 和 `check-run` 只看这个团队（第 3.3 节）。
4. **批次规划。** 架构师的新任务 AR7 规划每个批次，并对照规划检查每份设计（第 3.4 节）。
5. **主会话管多个团队的循环**：PR 按做好的先后合并，rebase，以及冲突（第 3.5 到 3.7 节）。
6. **有团队时的等待、需求变更、规则、发布和用量上限**（第 3.8 到 3.10 节）。
7. **Python 系列的共用环境和 Troy 的电脑**（第 3.11 节）。
8. **状态和进度**：`status`、进度文件和进度 issue 能同时显示多个功能（第 3.12 节）。

F20 改动 F04、F05、F07、F08、F14、F15 和 F16（第 5 节）。只有一个功能可以开始时，troy-mode 照今天的方式工作：在会话自己的检出目录里运行这个功能的角色，不建团队。

## 2. 探测结果

本设计依赖 Claude Code 的一些事实，它的文档没有写清楚。2026-11-22 用最新的内置 CLI 2.1.330 在嵌套的 `claude -p` 会话里做了探测，沿用 #49 设计的探测插件（F05 设计第 6.1 节）。每个探测在一个临时 git 项目里运行，项目带两个链接工作树，一个插件记下每次 hook 的输入，还有一个 haiku 工作代理。四个会话一共花了 $0.03。另外两个探测在本地运行，不用模型：工作树里 git 的文件夹，以及 tstack 自己的 hook 从多个进程同时写文件。第一列给出三个问题的编号：1，角色在团队的文件夹里工作；2，多个角色同时运行；3，工作树的 git 文件夹。

| # | 问题 | 结果 |
| --- | --- | --- |
| 1 | 主会话能不能在指定的文件夹里启动子代理？ | 不能。Agent 工具的参数是 `description`、`prompt`、`subagent_type`、`model`、`effort`、`run_in_background` 和 `isolation`（`worktree` 或 `remote`），没有文件夹参数。桌面应用的 Agent 工具也一样，只是没有 `run_in_background`。 |
| 1 | 子代理的 `cd` 会不会带到下一次调用？ | 不会。`cd <worktree> && pwd` 打印出工作树，下一次 `pwd` 又打印出会话的文件夹；工作树放在会话文件夹里面时也一样。主会话 `cd` 到项目旁边的工作树，也没有带过去；Claude Code 只在主会话的工作文件夹之内保留它的 `cd`。 |
| 1 | hook 收到子代理调用的 `cwd` 是什么？ | 总是会话的文件夹，连运行 `cd <worktree>` 的那次调用、以及写进工作树的 `Write` 也是。hook 无法从 `cwd` 得知角色属于哪个团队。 |
| 1 | hook 能不能读到角色的简报？ | 在 `SubagentStart` 时不能：它的输入里没有提示词，子代理的对话记录 `<transcript_path 所在文件夹>/<session_id>/subagents/agent-<agent_id>.jsonl` 也还不存在。从角色的第一次工具调用起，这个文件就存在，第一行就是简报，所以简报里的团队那一行可以读到。`SubagentStop` 的输入也用 `agent_transcript_path` 给出这个文件。 |
| 1 | `isolation: "worktree"` | Claude Code 为这次运行新建了一个工作树 `<会话文件夹>/.claude/worktrees/agent-<id>`，在从主会话 `HEAD` 拉出的新分支 `worktree-agent-<id>` 上，并因为这次运行改了文件而保留了它。hook 的 `cwd` 就是这个工作树。它不能命名，也不能基于团队的分支，所以一次运行的工作到不了下一次运行。 |
| 1 | hook 能不能让角色的调用在另一个文件夹里运行？ | 能。`PreToolUse` hook 回答 `hookSpecificOutput.updatedInput`、不给权限决定时，角色的 Bash 命令被改成 `cd "<worktree>" && <command>`：它的 `pwd` 打印出工作树。没有路径的 `Glob` 被填上工作树作为 `path` 后，找到了工作树里的文件。 |
| 2 | 两个角色同时运行 | 同一个主会话的两个后台工作代理拿到不同的 `agent_id` 和相同的 `session_id`，两边 hook 的 `cwd` 都是会话的文件夹。它们的 hook 调用交错进行。每个代理的对话记录里是它自己的团队那一行，每个代理只写了自己的工作树。 |
| 2 | hook 写文件会不会互相冲突？ | 在 Windows 上部分会。tstack 的 `records.save` 写不同的记录，同时有 `read_all` 在读，一次都没有出错：8 个进程，每个写 300 次。往同一个 `hooks.log` 追加会丢行：2 个进程时 600 行丢了 9 行；8 个进程时 2,400 行丢了 182 行，剩下的里面还有 7 行读不了。对同一条记录"读、改、存"，2 个进程时就会丢更新。配置缓存是原地写的，读的一方会读到半个文件，hook 已经能处理这种情况。 |
| 3 | 链接工作树里的 `git rev-parse --git-dir` | 绝对路径 `<主检出>/.git/worktrees/<name>`。`--git-common-dir` 给出 `<主检出>/.git`。 |
| 3 | 删除工作树会不会丢掉它的状态？ | 会。对一个干净的工作树运行 `git worktree remove`，删掉了 `.git/worktrees/<name>` 和其中的 `troy-mode/` 文件夹，包括记录和 `hooks.log`。有改动的工作树不加 `--force` 会被拒绝。删掉文件夹再运行 `git worktree prune` 也会删掉状态。 |

所以团队的角色无法直接在它的工作树里启动，hook 也无法从 `cwd` 看出一次调用属于哪个团队。但从第一次调用起，hook 能从简报读出团队，并且能让每条命令在团队的工作树里运行。第 3.2 节就建立在这上面（D268）。探测脚本留在 Troy 的电脑上，不在仓库里。

## 3. 工作方式

### 3.1 团队和它的工作树（D269）

**团队**是一个功能从 PR 1 到 PR 6 的角色运行，在一个 git 工作树里进行。它照原样运行 F07 第 8 节的功能循环：团队内同一时间只有一个会写文件的角色，有自己的评审、轮数、尝试次数、检查和合并。不同团队的角色同时运行。

- **会话检出**是主会话运行的文件夹，也就是 Troy 输入 `/tstack:troy-mode` 的地方。它不放任何团队的工作。主会话自己的流程在这里运行，像今天一样一次一个 PR（F07 第 4 节）：需求、架构、需求变更、规则变更、版本测试方案和发布。
- **`team start --item <ID>`** 创建工作树 `<会话检出>/.troy-teams/<id>`，`<id>` 是小写的功能 ID，比如 `f08`，以分离 HEAD 的方式停在 `origin/main`。第一次时，它把 `/.troy-teams/` 加进仓库的 `.git/info/exclude`，所有工作树共用这个文件，所以没有哪个检出会列出这个文件夹，也不改任何项目文件。它拒绝还不能开始的功能（第 3.5 节）。
- 工作树在会话的文件夹里面，所以 Claude Code 把其中的文件当成项目的文件：角色在那里写文件不需要额外的工作文件夹或权限。主会话在会话检出里运行的工具会跳过它：`.troy-teams` 以点开头，pytest 默认跳过；ruff 和 git 都遵守 exclude 文件。
- 在工作树里，每个阶段的分支照今天的方式建立：`git -C <worktree> switch -c troy-mode/f08-3-mock origin/main`。
- **`team end --item <ID>`** 在 PR 6 合并之后运行；工作树有改动或团队还有打开的记录时，它拒绝。它把团队的 `hooks.log` 日志行追加到仓库共用 git 文件夹里的日志（第 3.3 节），再运行 `git worktree remove`。这样，即使工作树的 git 文件夹没了，复盘也保住了每个团队的日志行（Q21）。
- **在另一个文件夹里的会话。** 从任何检出运行 `git worktree list` 都能看到每个团队的工作树，所以新会话不管团队在哪里都找得到。团队的工作树在新会话的文件夹之外时，`status` 会说明，技能会在工作树干净、且没有角色在运行时，用 `git worktree move` 把它挪进新会话检出的 `.troy-teams/`。

### 3.2 角色在自己团队的工作树里工作（D268）

Agent 工具不能在指定文件夹里启动角色，角色的 `cd` 也留不住（第 2 节）。所以：

1. **简报写明检出目录。** 对团队的工作树运行 `brief --repo <worktree>` 时，Task 一行在任务本身那句话之后多一句："You work for team F08 in the checkout `<absolute path>`: every path in this brief is inside it, read and write files only there, and your commands start there."（"你为团队 F08 工作，检出目录是 `<绝对路径>`：本简报中的每个路径都在其中，只在那里读写文件，你的命令也从那里开始。"）Read first 的路径变成该检出目录里的绝对路径。给会话检出的简报两者都没有，所以和今天一样。
2. **hook 在角色第一次调用时得知团队。** 在角色第一次被 hook 检查的调用上，`PreToolUse` 读取角色对话记录的第一行，找这句话。检出目录必须是本仓库在 `.troy-teams/` 下的链接工作树，hook 用共用 git 文件夹 `worktrees/` 里的 `gitdir` 文件核对。角色的记录随后写上 `team` 和 `worktree`（第 3.3 节）。仓库里有团队工作树时，`SubagentStart` 不写角色的记录：那时对话记录还不存在，而角色在第一次调用之前什么也没做，所以第一次调用时的状态就是它的起始状态。没有团队工作树时，它照今天的方式写记录，所以一次只有一个团队的 troy-mode 和以前一样。F05 本来就会在第一次调用时补建缺失的记录（F05 设计第 6 节）。
3. **hook 让每条命令都在工作树里运行。** 对团队的角色，`PreToolUse` 对每次 `Bash` 调用回答 `updatedInput`，把命令改成 `cd "<worktree>" && <command>`；对每次 `PowerShell` 调用改成 `Set-Location -LiteralPath '<worktree>'; <command>`；对每次没有 `path` 的 `Glob` 和 `Grep`，把工作树填作 `path`。它不给权限决定，所以 Claude Code 自己的权限照样作用于新的输入。已经以 `cd` 进入该工作树开头的命令保持不变。
4. **文件工具。** `Write`、`Edit` 和 `NotebookEdit` 以团队的工作树作为仓库来检查（F05 第 5.2 节）。项目里其他地方的路径，包括会话检出，都会被拒绝："You work in the checkout <worktree>. Write the file there."（"你在检出目录 <worktree> 里工作。请把文件写在那里。"）临时文件夹和 scratchpad 仍然允许。读取不受限制。
5. **有团队运行时没有团队的角色。** 简报里没有团队那句话的角色在会话检出里工作，和今天的角色一样。主会话自己的流程就这样用：AR4、AR6、版本的 TM1，以及 Troy 接受依赖之后 AR3 的写入（第 3.3 节）。如果 hook 根本读不到对话记录，而仓库里有团队工作树，它就以规则 `team` 拒绝这个角色所有可能改动东西的调用："The hook could not read your brief. Report `failed` and say so."（"hook 读不到你的简报。请报告 `failed` 并说明。"）没有团队工作树时，它退回今天的做法。

### 3.3 按团队的 hook 和检查（D270、D276、D277）

**记录。** 团队角色的记录放在它工作树的 git 文件夹里，`<共用 git 文件夹>/worktrees/<name>/troy-mode/agents/<agent_id>.json`，正如 Q21 所说，并多两个字段 `team` 和 `worktree`。会话检出里角色的记录照今天放在会话检出的 git 文件夹里。因为 hook 的 `cwd` 总是会话的文件夹，每个 hook 都按代理 ID 在仓库各工作树的 git 文件夹里找角色的记录：列一次 `<共用 git 文件夹>/worktrees/` 即可，不启动 git 进程。

- **变更检测**（F05 第 6 节）在记录所指的工作树里运行 `git status`。团队的角色不会因为别的团队的文件、也不会因为会话检出的文件而受指责。
- **主会话的 `TaskStop`** 关闭那个代理 ID 的记录，不管它在哪里；**`SessionEnd`** 关闭结束的会话在每个工作树 git 文件夹里的记录（F05 第 6.1 节）。
- **`SessionStart`** 清理每个工作树 git 文件夹里的旧记录和旧日志行，以及共用 git 文件夹里的日志。
- **已经停止又被唤醒的角色**（F05 D232）：`SubagentStart` 什么也不写，第一次调用找到已停止的记录，照今天一样拒绝。

**日志。** 团队角色的拒绝写进它工作树的 `hooks.log`，主会话和会话检出里角色的拒绝照今天写进会话检出的日志。每次追加以及 `SessionStart` 的重写，都持有日志旁边的锁文件 `hooks.log.lock`：用 `O_CREAT | O_EXCL` 创建，每 10 ms 试一次，最多试一秒，超过 10 秒的锁可以接管。等满一秒后，写入不再等锁，直接进行，所以没人释放的锁最多让一次 hook 调用慢大约一秒，不会挡住它。对一条记录的"读、改、存"也用同样的方式持有自己的锁。在 Windows 上，别的 hook 进程打开着的记录无法被替换，所以读或存时遇到文件被占用，会在最多两秒内重试。探测 2 在没有锁时丢了日志行和记录更新。`team end` 在这把锁下把团队的日志行追加到 `<共用 git 文件夹>/troy-mode/hooks.log`（第 3.1 节），`retro` 读这个日志和每个还在的工作树的日志（第 5 节）。

**按团队的快照和检查。** 引擎的命令用已有的 `--repo <path>`。`snapshot --repo <worktree>` 和 `check-run --repo <worktree>` 把运行记录放在该工作树的 git 文件夹里，也只读这个团队的角色记录。所以团队 A 的 `snapshot` 不会因为团队 B 的角色还在运行而拒绝，团队 A 的 `check-run` 也不会列出团队 B 的改动（Q21）。会话检出的 `snapshot` 只读会话检出里的记录。

**主会话在团队的工作树里（D276）。** F07 第 6.2 节要求主会话在角色运行时不在检出目录里做任何事，因为 hook 会把每个改动都算到角色头上。有团队时，主会话在这段时间里会去别的工作树工作，所以这条要求变成一项检查。主会话的 `PreToolUse` 以规则 `team-busy` 拒绝：在某个团队有打开的记录时，在该团队的工作树里运行会写入的 git 命令（`add`、`commit`、`switch`、`checkout`、`restore`、`reset`、`rebase`、`merge`、`stash`、`clean`、`rm`、`mv`、`cherry-pick`、`am`、`apply`），以及往那里 `Write`、`Edit` 或 `NotebookEdit`。它用 F05 第 7.1 节已有的方式找文件夹：从 `-C`、`--git-dir`、`--work-tree` 和前面的 `cd`，文件工具则看路径。拒绝理由列出这个团队正在运行的代理 ID。

**共用文档（D277）。** Q20 只允许主会话和架构师的规划步骤修改需求文本、架构、ADR 和规则表。因此在团队的工作树里，hook 把 `docs/requirements*.md`、`docs/architecture*.md`、`docs/adr/**` 和 `docs/versions/**` 从每个角色的写入范围里去掉；`docs/rules*.md` 和 `.troy-mode/**` 今天本来就不允许任何角色修改。团队的 PR 6 只改状态表里它自己那一行，由主会话以产品经理的身份照今天的方式写。架构师涉及架构的写入，包括 Troy 接受依赖后 AR3 的写入、AR4 和 AR6，都在会话检出里作为主会话自己的 `[docs]` PR 进行，一次一个；每个团队在下一个阶段或下一次 rebase 时拿到它们。ADR 在合并时才定编号。

### 3.4 批次规划（D271）

一批团队开始之前，由架构师规划这一批（Q20）。**批次**是某一时刻按依赖可以开始的所有功能（第 3.5 节）。规划是架构师的新任务 AR7，有两种运行：

- **规划。** 简报的 Input 列出这一批的功能和已经在运行的团队。对每个功能，AR7 读它的需求行、架构的模块表和它所依赖功能的设计，给出：它会碰的模块，用架构模块表里的名字；它新增或修改的外部接口；以及它需要改的共用文档。两个功能有重叠时，它定出先后：`F10 after F08 1/6` 表示 F08 的设计合并后 F10 再开始；`F10 after F08 6/6` 表示 F08 验收后再开始。改同一个接口的两个功能绝不同时进行：一个至少要等另一个的设计。只共用模块的功能可以同时进行，规划写明这个模块，这样那里出现 rebase 是预料之中的。
- **检查。** 架构师 AR2 批准一个团队的设计（PR 1）之后、合并之前，AR7 把这份设计和规划、以及正在运行的团队已合并的设计对照。设计改动了另一个正在运行的功能的规划里写到的接口或共用文档，或者碰到了自己规划之外的模块时，AR7 给出新的先后，需要等待的团队在当前阶段之后停下。

AR7 不改任何文件。它报告的 Summary 里用固定格式的代码块给出规划，每个功能一行，每个先后一行，比如 `F08 modules: importer, cli; interfaces: import_csv; documents: none` 和 `F10 after F08 1/6`。`plan --report <file>` 解析它，检查这一批的每个功能都有一行、正在运行的功能之间每处模块或接口的重叠都有先后，然后存进 `<共用 git 文件夹>/troy-mode/plan.json`。解析不了的规划退回 AR7 一次，再不行就升级上报。规划和进度文件一样只在本地：在新的 clone 里，`status` 会要求再跑一次 AR7，花一次架构师运行的钱。

### 3.5 哪些功能开始（Q19）

一个功能满足以下条件时可以开始：

1. 它依赖的每个功能，不论硬依赖还是软依赖，都已在 `origin/main` 上验收（Q19）；
2. 规划允许：每条提到它的先后都已满足（第 3.4 节）；
3. 没有影响它的需求变更还开着（第 3.9 节）；
4. 它的版本可以开始：下一版本的功能在当前版本打标签之前只能做阶段 1 和 2（第 3.9 节）。

`status` 按需求文档的顺序把这些功能列为 `may_start`。只有一个这样的功能、又没有其他团队在运行时，troy-mode 照今天的方式工作，在会话检出里，没有规划。有两个或更多，或者旁边已有团队在运行时，主会话为这些功能运行 AR7，然后为规划允许开始的每个功能各启动一个团队，不设上限（Q18）。在 `ZJUCao/recipe-menu` 的 v0.1 里，这样分成 6 批，每批最多 4 个功能（需求文档 5.11）。

### 3.6 主会话的循环

一个主会话运行所有团队（Q17）。它让循环保持简短：

1. **能开始的都开始。** 对每个没有角色在运行的团队，它从 `status` 取这个团队的下一步并开始：一次角色运行（F07 第 6 节），`brief`、`snapshot` 和 `check-run` 都带 `--repo <worktree>`；或者它自己的一步，比如提交、推送或合并。在 Agent 工具有 `run_in_background` 的地方，比如 `claude -p`，有两个或更多团队运行时它传 `true`，让角色同时运行。在桌面应用里，每个角色本来就在后台运行。
2. **等下一份报告。** 一个角色报告后，主会话按 F07 第 6.3 节处理这个团队的报告，然后回到第 1 步。
3. **每次都写明文件夹。** 主会话用 `git -C <worktree>` 和 `--repo <worktree>` 运行 git 和引擎，从不用单独的 `cd`，因为它的 `cd` 在工作文件夹之内会保留，而下一条命令可能属于另一个团队。

**主会话的上下文。** 试点里唯一的主会话花了 $301，经历了 15 次压缩（Q17）。有了团队，每份报告都到同一个会话。所以引擎给每个团队的输出只有一行，技能读角色报告、不读整份 diff，进度文件保存压缩会丢掉的东西，压缩之后技能先运行 `status`。F20 的试运行测量主会话的花费占比（第 8.3 节）。

### 3.7 合并、rebase 和冲突（R24、Q22、D272 到 D274）

**先做好的先合并。** 一个团队的 PR 在每个评审都批准、本地检查都通过时算做好了（F07 第 8.6 节）。做好的 PR 按做好的先后合并（Q22）。

**合并检查（D272）。** 合并之前，主会话运行 `git -C <worktree> fetch origin --prune`，然后运行 `merge-check --repo <worktree> --pr <n>`。它报告：

- `rebase`：`origin/main` 不是 PR head 的祖先时（R24）；
- `outside-plan`，附路径：改动的源码或测试路径落在规划给这个功能的模块之外时，按模块表的路径模式判断，troy-check 检查 R07 时已经读这些模式（F03 D19）。这时 AR7 在合并之前检查这个 PR 的 diff；
- `held`：功能属于下一版本、PR 是 PR 3 到 PR 6、而当前版本还没有标签时（Q24、F08 D75）；
- 其他情况为 `ready`。主会话随后对 head 运行 `wait-checks`，再用 `gh pr merge --rebase --match-head-commit <sha>` 合并（F07 D204）。

**rebase（D274）。** 遇到 `rebase` 时，主会话运行 `git -C <worktree> rebase origin/main`。PR 只在即将合并时 rebase，而不是在别的团队每次合并后都 rebase，所以别的团队每合并一次，这个 PR 最多多跑一次 CI。rebase 干净时，它用 `--force-with-lease` 推送，再跑一次本地检查，并等新 head 的 CI（R24）。然后 `merge-check --rebased-from <old head>` 判断 rebase 有没有改变 PR 的 diff：按文件比较 PR 增加和删除的行是否和之前不同，不算上下文行和行号。不同，而且这个阶段有代码审查员时，也就是 PR 3、PR 4 和 PR 5，代码审查员审 rebase 后的 diff（CR1，下一轮）。PR 1、PR 2 和 PR 6 没有代码审查员，所以只重跑检查。

**冲突（D273）。** rebase 因冲突停下时，主会话列出冲突的路径，然后运行 `git rebase --abort`。`merge-check --conflicts <path>...` 给出在这个阶段写入范围包含所有这些路径的角色：源码给开发工程师，测试给测试工程师，设计给接口设计师，测试方案给测试经理，PR 6 的状态行给产品经理。没有哪个角色的范围能全部包含的路径，升级上报（5.7）。然后这个阶段**在新的 main 上重做**：主会话从 `origin/main` 重新建立这个阶段的分支，拥有这些路径的角色再运行一次，Input 里放它原来的 diff 和冲突的路径，要求在新的 main 上做同样的改动。提交、用 `--force-with-lease` 推送到同一个 PR、检查和评审，都和普通的修订一样。PR 仍然只有一个提交（R01）。拥有者是产品经理时，主会话自己重写它的状态行，并照 F07 第 7 节做快照。重做既不算尝试，也不算轮数，因为冲突来自别的团队的合并，而不是作者的工作。

预计最常见的冲突在 PR 6：先后验收的两个功能改动需求文档状态表里相邻的两行，git 把相邻行的改动算作一处冲突。这种重做是主会话自己的，不花角色运行。

### 3.8 等待和审批（Q23）

- 等 Troy 或已经升级上报的团队停下。等它的功能的团队，不论按依赖还是按规划，也一起等。其他团队继续。
- `status` 给出 `waiting`：每个等 Troy 的 PR，附它的团队、它的摘要链接和它卡住的功能，卡住最多的排在最前。
- 主会话用一条消息询问所有等待的 PR，每个附它给 Troy 的摘要（F14），如原型 E 所示。Troy 可以一起回答："全部批准"或"approve all"，也可以逐个回答，在聊天里或在 PR 上（F15 设计 D145）。"全按推荐"仍然表示采纳它所回答的那些 PR 的全部推荐。
- 升级上报单独一条消息（5.7），因为每次都需要单独决定。
- Troy 也可能在 GitHub 上合并等待中的 PR 1 或 PR 2。R24 挡不住从较旧的基础上合并，但这样的 PR 只包含它自己功能的文档，团队的下一个阶段也从新的 `origin/main` 开始。

### 3.9 需求变更、规则和发布（Q24）

- **需求变更。** 主会话在启动下一个团队之前接收想法或变更（F15 D143），照今天的方式（PM2）在会话检出里写。变更 PR 的描述多一行 `Affects: F08, F10`，来自 PM2 列出的清单。这个 PR 开着时，`status` 让每个受影响的团队在当前阶段的 PR 合并后停下，其他团队继续。变更合并后，受影响的团队按 F07 第 11.2 节从 AR4 的结果继续。
- **规则变更。** 照 F09 的方式在会话检出里进行，它的 PR 和其他 PR 一样合并。每个团队从 `origin/main` 开始下一个阶段时就拿到它，开着的 PR 在 rebase 时拿到它（第 3.7 节），所以它的检查按新规则运行。
- **发布。** 版本的每个功能都验收后开始，如 F08 第 5.2 节所说。下一版本的团队可以在那之前合并它的 PR 1 和 PR 2。它的 PR 3 到 PR 6 等版本打标签（`held`，第 3.7 节），这样补丁发布仍然可行（F08 D75）。
- **性能用例。** PR 5 的性能用例在 Troy 的电脑上运行之前（F07 第 8.1 节），主会话等到别的团队没有角色在运行，并在此期间不启动新角色，让它们的测试不拖慢测量。发布测试会对每个功能再跑一遍。

### 3.10 用量上限和继续（Q18）

Troy 的 5 小时用量上限让会话停下时，每个团队都暂停。它的状态在 git、GitHub 和它的工作树里，所以什么也不丢：

- 新会话，或者额度重置后的"继续"，运行 `status`，从 `git worktree list`、开着的 PR、每个工作树 git 文件夹里的流程记录和规划，重建每个团队。
- 被上限打断的角色留下一条打开的记录。`snapshot` 和 `check-run` 把它报为 `running`，主会话用 `TaskStop` 结束它，这也会清掉过期的记录（F05 D231）。
- 角色没有报告就停下的工作树留着这次运行的改动。对这次运行的 `check-run` 会列出它们；因为角色没有给出报告，适用 F07 第 6.3 节：主会话撤销这次运行自己的改动，再运行这个角色一次。

### 3.11 Python 系列和 Troy 的电脑（D275）

一个 Python 系列共用一个环境（需求文档第 8 节），而 DV1 的 `uv pip install -e . --no-deps` 让它指向一个文件夹。这样两个团队的检查会测同一份代码（Q20）。所以每个团队的检查都把团队自己的源码放在 Python 导入路径的最前面：`brief --repo <worktree>` 给出的检查和技能的本地检查，运行时把 `PYTHONPATH` 设为工作树的源码文件夹，按配置里 `[lang] source_roots` 给的名字，默认是 `src`。`PYTHONPATH` 里的文件夹排在可编辑安装的条目之前，所以团队的测试导入的是团队工作树里的代码。环境和它的锁文件仍然每个系列一份。所以，`[lang] environment` 没有设置时，团队的简报按主检出的文件夹名、而不是工作树的文件夹名来称呼环境；DV1 第一个 mock 的安装安装的是主检出，`uv pip install -e "<主检出>" --no-deps`，这样共用环境永远不会指向 `team end` 会删掉的工作树。构建的测试和试运行检查：在 Python 语言包的构建后端下，`import <package>` 得到的是团队工作树里的文件。

C 和 C++ 的团队各自在自己工作树的构建文件夹里构建，互不共用。

### 3.12 状态和进度

- **`status`** 增加 `teams`：每个团队的功能、工作树、阶段、开着的 PR、下一步、有没有角色在运行（有打开的记录）、以及它是在等 Troy、等另一个功能、等变更还是等版本标签。`may_start` 和 `waiting` 见上文。`next` 变成一个列表，每个团队一个下一步，如果会话检出自己有下一步，也列进去。
- **进度文件**按原型 E 的样子列出每个团队、它的阶段和它在等什么。`status --write-progress` 在代码里写它。F01 的 `progress` 模板不变：`troy-mode/templates/` 下的每个文件都属于 F16 的指令集，改动那里会让全部十二个考试用例都受影响（第 6 节）。
- **进度 issue**（F15）。每个由团队开发的功能都有自己的进度 issue，和今天每个功能一样。F15 的"下一个功能"改成"可以开始的功能"（F15 设计 4.1），所以每一批的 issue 一起出现。
- **费用**（F07 第 8.8 节）。`costs --item <ID>` 把主会话的每条消息平均分给当时有团队在运行的功能，这样各功能的费用加起来等于整个版本的。一个功能从它的第一次角色运行算到它的 `accept` 提交。`--tag` 不变。

## 8. F20 如何检验（D279）

### 8.1 测试

测试用 `unittest` 和标准库，和 F05、F07 一样。由一个单独的代理在代码存在之前，根据本设计编写。引擎的测试建一个临时仓库，带本地裸仓库作为 `origin` 和真实的链接工作树；hook 的测试给 `troy_hook.py` 输入，并配一个假的对话记录文件。

| 组 | 用例包括 |
| --- | --- |
| 团队 | `team start` 建出停在 `origin/main` 的 `.troy-teams/<id>`，exclude 那一行只写一次；依赖未验收、规划的先后未满足或有开着的变更影响它时，拒绝。`team end` 在有改动或有打开的记录时拒绝，追加团队的日志行，删除工作树。 |
| 简报 | 带团队的 `--repo`：Task 一行里团队那句话恰好一次，Read first 是工作树里的绝对路径，检查里有 `PYTHONPATH`。会话检出：简报和以前逐字节相同。 |

### 8.2 植入的 bug

代码通过后，在临时副本里一次植入一个 bug，每个都必须让某个测试失败。包括：从 `cwd` 而不是简报读团队，接受那句话写的任何文件夹，`SubagentStart` 仍把记录写进会话检出，PowerShell 没有改写，有路径的 `Glob` 也被改写，团队角色往会话检出 `Write` 被允许，变更检测在会话检出里运行，只在会话检出的 git 文件夹里找记录，`SessionEnd` 只关闭会话检出的记录，追加日志不加锁，过期的锁永远不被接管，`team-busy` 只看主会话的 `cd` 不看 `-C`，团队 A 的 `snapshot` 因团队 B 的记录而拒绝，`team end` 先删工作树再归档日志，`merge-check` 比较了上下文行，测试里的冲突交给开发工程师，下一版本的 PR 3 在打标签前合并，`may_start` 忽略 `after F08 1/6` 的先后，接受有未定先后重叠的规划，主会话的费用整份算进每个功能，以及团队的检查漏掉 `PYTHONPATH`。数目写进 PR 描述。

### 8.3 在示例项目上试运行

第 2 部分的 PR 开出之前，F20 在内置 CLI 的嵌套 `claude -p` 会话里，在 `ZJUCao/troy-mode-trial` 上运行，tstack 通过 `--plugin-dir` 从 PR 分支加载，和 F07 的试运行一样（F07 设计 14.3）。Troy 的 `autoMode.allow` 规则涵盖只作用于该仓库的启动。

1. **一个批次。** 一次需求变更加入两个小功能，它们只依赖已验收的功能，并且都增加一个命令行选项，所以共用 `cli` 模块。架构师规划这一批，两个团队开始，各在自己的工作树里。
2. **同时进行。** 两个团队会写文件的角色同时运行。hook 的日志和 `check-run` 表明，哪个团队都没有因为对方的文件受指责，哪个团队的 `snapshot` 都没有等对方的角色（Q21）。
3. **合并。** 先做好 PR 的团队先合并。另一个团队 rebase、推送，再等一次 CI（R24）。PR 6 相邻的状态行冲突，主会话重写自己那一行。共用的 `cli` 模块里的改动改变了第二个 PR 的 diff，于是 CR1 再审一次。
4. **暂停。** 在一个角色运行时停掉会话，就像遇到用量上限。新会话用"继续"重建两个团队，结束过期的角色，完成两个功能。
5. **事实。** 在 `-p` 里，两个团队用 `run_in_background` 的角色是否重叠运行；以及每个功能里主会话的花费占比，和 F07 第 1 部分试运行单独做一个功能时相比。

大约 30 次角色运行：每个功能约 13 次，三次 AR7，以及 rebase 之后的一次 CR1。按试点每次运行的中位数，角色约 $55，加上主会话，一共约 $85，每个 PR 再用几分钟 Actions。有两件事只有桌面应用能看到：自动模式会不会放行改写后的命令，以及多个后台角色的通知怎样到达主会话。第一次带团队的真实运行检查它们。
