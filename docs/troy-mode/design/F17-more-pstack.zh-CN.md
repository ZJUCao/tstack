## 1. 范围

F17 只在试点出现过两次同样错误的地方，给 troy-mode 加一个 pstack 技能，而且每项添加先通过角色考试（F16）（需求文档 F17 行和 4.1）。本设计：

1. 用证据逐个检查 F17 行列出的候选，给每个实例加链接，没有两个实例的候选就去掉（第 2 节）；
2. 选定要加的内容，以及每项接在哪里（第 3 节）；
3. 说明角色怎样读 pstack 技能而不复制它（第 4 节），以及角色考试必须看到它的哪些部分（第 5 节）；
4. 设计每项添加：测试行为卡片（第 6 节），清单没有列出的架构师设计审查（第 7 节），复盘中的 `reflect`（第 8 节），以及加入 `interrogate` 之前的一次测量（第 9 节）；
5. 说明上游 pstack 的更新怎样继续合并（第 10 节）、F17 需要的需求文字（第 11 节）和构建（第 12 节）。

事实来自 `c5ce288` 上的仓库（插件 0.18.0，需求文档 1.65）、F07、F08、F09、F16 和 F18 的设计、F11 试点报告、通过 `gh` 读取的 `ZJUCao/recipe-menu` 的 PR #1 到 #125 及其评论、`D:\Troy\troy-mode-work\` 中角色考试的结果和考题日志（考试 2026-11-17-2、2026-11-23-1 和 2026-11-25-3），以及 F18 的交接笔记。F11 收尾的交接笔记不在笔记文件夹里；试点报告和 F16 设计 2.1 记着它列出的角色错误。不需要探测，也没有运行模型：本设计花费 $0。

### 2.2 测试检查得太少，或太多

**太少。** 试点问题 2 是测试工程师重复最多的错误：测试检查的比它的计划用例要求的少，比如只查退出码（#17、#43、#62、#68、#75、#82、#89）。F16 的考题 te-plan-asserts 和 tm-test-review 就来自它。v0.2 里它还在出现：

- #105 第 1 轮：两位审查者都发现 F13-T22 和 F13-T27 不再检查错误流是否为空，F13-T27 "only exit code 0"（只查退出码 0）。
- #117，代码审查员第 1 轮：F15-T16 的第 3、4 行 "check only the last line or only the exit code, as the rows of the plan ask"（只查最后一行或只查退出码，正如计划的行所要求的）。
- #119："No test saw that"（没有测试看到这一点）：F15-T03 和 F15-T04 的包装器用的 `newline` 本来就是通用换行，所以没有设计修复的实现也能在每个系统上通过。

计划的行本身也要求得太少：在 #75 上，代码审查员写道 "each case's own row asks only for what it checks"（每个用例自己的行只要求它检查的东西）。

**太多。** 已验收功能的两组测试绑定了超出用例约定的东西，后来的功能把它们弄坏了：

- #105：F14 的模拟实现加了一个命令和一个设置键，这改变了帮助和 `UNKNOWN_KEY` 的文字，于是 F05、F11 和 F13 的六个测试失败（F05-T10、F05-T11、F11-T32、F13-T01、F13-T22、F13-T27）。F13-T01 期望的是 F05 原型的整段 21 行帮助，而不是 `shop` 那一行。
- #115：F11-T01 把 "the two lines right after the line of `search`"（紧跟在 `search` 那一行之后的两行）当作 `menu new` 和 `menu show` 的行，于是 F15 的 `add` 把它弄坏了。

两次都是在后来那个功能的设计里发现的（#102，架构师的第 5 条发现："The six tests break again when F15 and F16 add `add`, `edit`, and `editor`"；#113），每次都多花了一个带两轮审查的测试修复 PR。两次裁定都改了测试经理的计划行，所以原因既在计划里（TM1），也在测试里（TE1）。

**是否对路。** 这张卡片的两种设想改动正好对应这两种错误："Break the behavior"（破坏行为）抓住用例结果坏了测试却还通过的情况（"an assertion looser than the contract"，比约定更松的断言），"Change the internals"（改内部）抓住测试绑定了用户不能依赖的东西。它的规则是 "Assert what the contract promises, no less and no more."（约定承诺什么就断言什么，不多也不少。）troy-mode 自己的文字只说 "Test behavior through external interfaces only"（只通过外部接口测试行为，TE1 第 3 步，TM2 第 3 步），没有说一个测试该检查多少。

### 2.3 架构师的设计审查

两道架构师考题在考试 2026-11-23-1 和 2026-11-25-3 中共运行了 40 次，用的是 `main` 的指令，或离它只差一处改动：

| 考题 | 通过 | 其余运行做了什么 |
| --- | --- | --- |
| ar-error-review | 20 次中 3 次 | 20 次中 16 次批准了设计。这 16 份报告中有 13 份写出了列出失败时的完整路径或 ADR-0009，却把它当作备注放过，例如 "I read this case as covered by ADR-0009"（考试 2026-11-25-3，head 第 1 次运行）。 |
| ar-design-review | 20 次中 0 次 | 每次都要求修改。K4，即 `ruff format` 会重新折行的示例行，20 次全漏：没有一份报告运行了 `ruff format`，有一份写着 "I did not run Linux, ruff, mypy, or troy-check. The PR has no code."。K2，即偏离架构第 6 节的完整路径，20 次中找到 3 次，还有一份报告提到它但说不阻塞。 |

所以架构师犯两个错误：看到了偏离架构原文的地方，却把规则读得足够宽，放它过去；检查设计的示例时会去运行它们，却不运行 CI 会在设计文件上运行的检查。在 ar-error-review 里，20 份报告中有 13 份运行了 `ruff format`。

试点里的架构师在第 1 轮就找到了这两个问题：考题的答案就是它在 #52 和 #71 上的发现。所以考试显示的是在今天的指令、模型和 CLI 上的错误，而不是试点里的错误。它们仍是两道考题、两次考试里的同一个错误，F18 的抽查也在等它们（F18 设计 D178，E3）。

没有哪个 pstack 技能告诉审查者照原文读规则。`principle-prove-it-works` 对得上第二个错误：对照真实产物去验证，不靠替代物，并把检查写成脚本。第二个陷阱在新项目里已经不存在：自 tstack issue #51 起，Python 语言包的 `ruff` 跳过 `docs/`（F03 设计 D214）。在考题的项目里，也就是试点当时的状态，CI 仍会格式化设计里的 python 代码块。

### 2.4 复盘

#94 上 v0.1 的复盘通过 `retro` 读了 94 个 PR：56 组审查发现，其中 8 组重复，提出了提议 A 到 D。整个版本里重复出现的四条教训被漏掉或少算了：

| 教训 | 复盘说了什么 | 记录里有什么 | 由谁发现 |
| --- | --- | --- | --- |
| 测试检查的比用例少 | 什么也没说：这些发现分散在 "R09 (#52, #75)" 和 "test plan details (#89, #92)" 这样的组里 | 7 个 PR，#17 到 #89 | 试点报告问题 2，F16 设计 2.1 |
| 从标准输入读程序的 Python | "5 times while F11 to F13 were built" | 168 次这样的运行中有 39 次卡住 | 试点报告问题 14 |
| 等 Troy 和停顿 | 什么也没说 | 34 条 `Waiting for Troy` 评论，48 小时；63 次停顿，100.4 小时 | 试点报告 5.5，F18 设计 2.1 |
| 作者文件里的 CI 失败 | "1 failed attempt" | CI 在作者文件的四次推送上失败 | 试点报告问题 19，现在由 `ci_attempts` 计数 |

原因在于 `retro` 看的地方。它读 PR 评论，按每条发现提到的规则 ID 或检查项分组，而问题 2 的发现提到的是计划用例 ID，不是规则。卡住、等待、拒绝和用量上限只在会话的记录里，而这些记录很大：recipe-menu 到目前为止有 548 MB，包括 3 份主会话记录和 425 份子代理记录。试点报告和 F18 的证据工作读了这些记录，复盘没有读。

### 2.5 改变存储文件的设计

- **F14**，一周菜单的文件（#102，架构师在第 2 轮批准）。它的测试计划 #103 写着："Two rare file layouts have no test, because the design does not say what happens: a day's header as the last line of the file with no line break after it, and spaces around a key of `dishes`."（两种少见的文件布局没有测试，因为设计没有说会发生什么：一天的标题作为文件最后一行且后面没有换行，以及 `dishes` 键两边的空格。）
- **F15**，由输入的回答写成的菜谱文件（#113，架构师在 Windows 上探测了管道输入之后，第 1 轮就批准了）。测试的两位审查者（#117）都发现设计 3.3 说换行 "stay universal"（保持通用）只在 Windows 上成立，#118 在设计里、#119 在测试里修复了它。
- v0.1 里的 **F01**（#6）：对数量的位数没有限制，而 Python 拒绝超过 4,300 位；测试经理在写计划时发现，#7 修复了设计。

每一次都是下一阶段在写代码之前发现的。`interrogate` 的证据在一点上很弱：#113 的架构师已经搭了模型并探测了输入，和对手会做的差不多，却因为问题在另一个系统上而漏掉了。

### 2.6 没有找到什么

- **缺陷。** 两个版本都没有报告、分诊或修复过缺陷，所以缺陷流程的候选没有实例。
- **别处的破坏。** 连带影响都在该发现的地方被发现了：在后来的设计里（#102 的第 5 条发现，#113），以及在架构师的变更影响清单（AR4）里，即 #34、#104、#108 和 #125，后来没有 PR 修正过它们。没有哪个代码 PR 在合并后弄坏了别的功能，v0.1 发布时的真实运行 48 条原型命令全部匹配。
- **F18 的试运行。** 一次测试工程师在前提尝试中绕过了环境里的原因而没有报告，F18 的前提文字现在已经覆盖；一次产品经理把新功能排在了已验收的功能之前。每样各一次，都在临时试运行里。
- **出现过两次，但不是技能的活。** 两个角色用脚本改文档时改变了文档的字节：架构师的 `sed -i` 把 CRLF 变成了 LF（#3，试点问题 3），一个八进制转义在架构文档里留下了 U+0082（#104，在 #108 中修复）。检查比技能更合适（`principle-encode-lessons-in-structure`）：第 15 节把它留作一个 tstack issue 的想法。

## 4. 角色怎样读 pstack 技能（D162）

### 4.1 卡片表

新的引擎模块 `troyflow/cards.py` 每个任务和卡片一行：任务 ID、卡片在 `skills/` 下的文件夹，以及一行固定的话。对于列出的任务的简报，`brief` 把卡片在插件里的绝对路径加进 Read first，就像 F18 以来它加入前提卡片那样（`premise.py`），并把那一行话加到 Task 字段里任务自己的文字之后，以 "Apply `<card>`:" 开头。

- **卡片只读，从不复制。** 角色读的是 tstack 附带的 `SKILL.md`，也就是上游的原文；troy-mode 从不复制或修改它。公共规则 9 已经说了角色怎样读 pstack 技能：读它的 `SKILL.md` 并照做，因为 Skill 工具拒绝它们。
- **那一行话是 troy-mode 的。** 它说明这张卡片在这个任务里用在哪里，以及两者不一致时以哪条 troy-mode 规则为准（需求文档 4.1）。例如，测试行为卡片说精确的错误消息 "pins wording that no caller reads"（钉住了没有调用者会读的措辞），而在 troy-mode 里，设计和原型的文字是 Troy 的，测试要精确检查它们。所以给测试工程师的那一行写着："In troy-mode, the design's and the prototypes' texts are the contract: check your case's own texts exactly, and nothing that another feature adds or owns."（在 troy-mode 里，设计和原型的文字就是约定：精确检查你的用例自己的文字，不检查别的功能加入或拥有的任何东西。）
- **只有列出的任务会变。** 其他简报照旧渲染，所以只有那些任务的考题受影响（第 5 节）。
- **缺少卡片就拒绝。** 某一行的 `SKILL.md` 不在插件里时，`brief` 以问题 `card` 拒绝，tstack 的一个测试检查每一行。

### 4.2 为什么不放在代理文件里

troy-mode 今天是在代理文件里点名技能的：公共规则 7 里的 `technical-writing`，以及 TM1 第 3 步里的 `benchmark-checklist`。在那里点名卡片，对角色来说效果一样。但代理文件是这个角色每道考题的输入，所以对它的任何改动都会让这些考题全部运行：在测试经理的文件里为 TM2 加一句话，就会让 tm-plan-expected 运行，它在考试 2026-11-17-2 里每次运行花 $8.22 到 $14.38，一个首轮约 $125。卡片表让一项添加的考试只涉及它所服务的任务的考题。

## 5. 角色考试看到什么（D163）

今天的考试有两个缺口，会让卡片绕过把关：

1. **前提卡片在指令集之外。** `named_skills` 只读代理文件和 `common.md`。`premise.py` 是从简报里点名 `skills/principle-attack-the-premise/` 的，所以改这个文件夹不会改变任何指令哈希，也不会运行任何考试。只由卡片表点名的卡片也会有同样的缺口。
2. **一个技能的改动影响每道考题。** `affected` 对每道考题都比较每个被点名技能的文件，所以改 `benchmark-checklist`，即使只有测试经理读它，也会影响全部十二道考题。

PR 1 在 `troy-mode/exam/troyexam/` 里改这两处：

- `named_skills` 也读简报的模块（`brief_modules`），所以它们点名的每个 `skills/<name>/` 都加入指令集：现在是前提卡片，以后是卡片表里的每张卡片。
- `affected` 对每道考题，只比较它的角色的代理文件、`common.md` 或它自己渲染出的简报所点名的技能文件夹。
- `check_exam.py` 从同一段代码读指令集，所以 CI 也跟着变。

这是对考试工具的改动，所以 `prove --anchors` 要重新验证每道考题的锚点：按考试自己的估算是 $40.00，而考试 2026-11-21-1 里同样的验证花了 $11.46。它会改变 `main` 的指令哈希，所以之后的考试都不会复用它之前的基线运行。在这个计划里这不多花钱，因为之后每一步都重新测量基线。

## 8. 复盘中的 `reflect`（D166）

### 8.1 现在

入口技能的 "Retrospective" 一节（F08 D76）：`retro --tag <tag>` 把版本的 PR 证据分组，主会话对每个重复的问题按 `correct` 去做，给 Troy 发一条带提议的消息（W5），并把报告贴到发布 PR 上。规则变更流程（F09）接手 Troy 选中的每条规则。

### 8.2 加上 `reflect`

1. **会话摘要。** `retro --tag <tag> --digest` 还会写出版本里各会话的摘要，来源是 `costs --tag` 已经能找到的记录（F07 D264）：每次角色运行一行，含角色、任务、条目、结果、分钟数、花费和失败的检查；每个被钩子或权限拒绝的工具调用及其原因；每条卡住或到达时间上限的命令；每次 `Waiting for Troy` 及其等待时间；每次用量上限停止和压缩；Troy 的每条消息，截到 200 字符；以及每条审查发现的第一行及其 PR。它最多 200,000 字符；超出时，最早的运行行改为计数。它留在 Troy 的电脑上，放在公共 git 文件夹里（`troy-mode/retro/<tag>.md`），从不贴出。
2. **reflect 的三个视角。** 主会话按 `reflect` 的第 2 到第 4 步做：判断、工具和发散三位审查者，每位都是只读的子代理，拿到 `reflect` 自己原封不动的提示模板，用摘要代替记录路径（模板允许这样："or use the digest below"），再加上 `retro` 的分组；然后是综合者。模型取自模型规则中 `reflect` 的那几行，由 tstack 的适配层映射。审查者可以读文件、运行只读的 `gh`；它们不改任何东西。
3. **troy-mode 的分流。** `reflect` 的第 5 步在用户同意后修改技能。在 troy-mode 项目里，没有什么会修改技能或角色的文件，所以以 troy-mode 的规则为准（需求文档 4.1）：

| `reflect` 的输出 | 在复盘里 |
| --- | --- |
| Accepted，关于项目的代码、测试或文档 | 一条项目规则的提议，走规则变更流程（F09） |
| Accepted，关于 troy-mode 的角色、引擎或 tstack 技能 | 一条对所有项目都适用的规则的提议：一个 tstack issue（F09 D83） |
| Backlog：一项检查就能强制它 | 提议的级别是检查（F09 D79），`reflect` 的第 4 步和需求文档 5.8 都偏向这样 |
| Rejected | 在 "Dropped" 下每条一行 |

4. **其余不变。** `correct` 的方法照旧用于每条提议，给 Troy 的那条消息（W5）和发布 PR 上的报告把来自会话的提议放在单独的标题下。

额外的花费是四个子代理，每次复盘约 $10 到 $20：每个读一份约 50,000 token 的摘要，大约是一次 AR2 运行所读设计的大小，而 AR2 运行的中位数是 $2.79，它们推理得更久。复盘本来就等 Troy（W5），所以不增加停顿。

### 12.5 第 1 步定下的事

第 1 步的构建，即 PR 1（插件 0.20.0），定下了以上各节留着没定的这些点：

- **表的形式。** `troyflow/cards.py` 里的 `Row(task, path, line)`，`path` 写成 `skills/<name>/SKILL.md`，这样考试能在模块自己的文字里找到每张卡片。在 PR 2 之前 `ROWS` 是空的。
- **问题。** 某一行的卡片插件里没有时，给简报的其他问题再加一条 `card:` 问题，简报被拒绝。
- **顺序。** 卡片的那句话排在引擎今天加的每句话之后（团队的、模拟实现说明、CR1 的风险、平台跳过说明），排在前提文字之前；它的路径排在简报自己的 Read first 条目之后，排在前提卡片之前。团队简报保留插件里的路径。

第 1 步的检查：
