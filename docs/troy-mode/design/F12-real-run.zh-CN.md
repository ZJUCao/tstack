## 1. 范围

在一个功能的验收 PR（PR 6）之前，产品经理像 Troy 那样，按这个功能原型里的每条命令把真实程序跑一遍，把真实输出及其和原型的对比写进 PR（需求文档 5.2）。对不上的地方先走修 bug 流程（5.3），再验收。F12 为命令行项目构建这一步，这类项目的原型是 Markdown 格式的终端记录（Q9）。有图形界面或网页界面的项目以后再做（Q13）。

F12 交付：

1. 每个原型旁边一个运行文件，写明真跑时这个原型的每一节怎样准备（第 4 节，D103）；
2. 一个引擎命令 `troy_flow.py real-run`，在真实程序上重放终端记录、比对输出并写出证据（第 5 节，D102）；
3. PR 6 里的真跑步骤，由主会话以产品经理身份来跑（第 3 节，D101），外加测试经理的新任务 TM8，对每处不一致作出裁定（第 7 节，D107）；
4. 项目状态标签"在 Troy 的电脑上真跑过"（第 9 节，D109，Q12）；
5. 每次发版测试时把所有已验收功能真跑一遍（第 11 节，D112）；
6. 一个新的插件版本，让试点在 v0.1 发布之前用上 F12（第 13 节，D113，Q11）。

F12 按 Q10 对每个功能的规定，用一个 PR 合入。

## 3. PR 6 里的真跑

PR 6 由产品经理负责（PM3），在主会话里做。只有主会话能和 Troy 对话，而 F05 的钩子除了 F05 第 8.2 节对 git 和 gh 的防护之外，不限制主会话的命令。真跑不在仓库里写任何东西，所以钩子和写入范围都不用改（D101）。

1. **分支。** 和现在一样，从 `origin/main` 建 `troy-mode/<id>-6-accept`。
2. **运行文件。** 在 `snapshot --role product-manager` 之下，产品经理为这次真跑需要的（第 5.2 节）、还没有运行文件的每个原型写运行文件，每一节怎样开始，从这一节的文字说明里读出来。它先读 `${CLAUDE_PLUGIN_ROOT}/skills/principle-prove-it-works/SKILL.md`。然后 `check-run`，再做第一次提交，主题是 PR 标题。先不推送。运行文件在产品经理的写入范围内（`docs/prototypes/**`）。
3. **运行。** 在干净的工作区上运行 `troy_flow.py real-run --item <ID>`。
4. **未修的 bug。** 报告的 `open_bugs` 列出这个功能之前真跑留下的、仍未关闭的 `bug` issue 时，先走完它们的修 bug 流程（第 7.3 节）。
5. **不一致。** 退出码 1 且有不一致：TM8 用一次运行对全部不一致作出裁定（第 7 节）。产品经理按每条裁定处理，在新的快照下把运行文件或原型的改动修订进那次提交，然后回到第 3 步。一条命令在第三次运行时仍不一致，就升级上报（5.7，F07 设计 D64）。
6. **问题。** 退出码 1 且只有 `problems`，例如运行文件写了一个不存在的节：产品经理改好运行文件，回到第 3 步。程序或其环境的问题升级上报。
7. **验收。** 退出码 0：PM3 按报告的 `label` 设置状态（第 9 节），提高需求文档的版本号，然后修订提交。PR 描述的 Checks 一节写上报告的一行总结，新增的 "Real run" 一节放报告的 `description`（第 8 节）。和现在一样：`check-text`、`troy-check pr`、推送、开 PR、如有报告的 `comments` 就发出去、等 CI，然后合并。

Troy 在阶段汇报里看到的样子，和原型 B 一样：

```text
[6/6] 真跑：6 个原型的 41 条命令在你的电脑上都对得上。3 条在等 F12。
      验收 PR #96 已合并。F11 的状态现在是"在 Troy 的电脑上真跑过"。
      还没有在 Windows Terminal 里面、也没有在你的设备上检查过。
```

## 4. 运行文件（D103）

### 4.1 放在哪里，为什么要有

每个含终端记录的原型旁边都有一个运行文件：`docs/prototypes/F09-list-show.md` 对应 `docs/prototypes/F09-list-show.run.toml`。终端记录就是脚本。运行文件只记原型用文字说明的那些事：每一节开始时数据文件夹里有什么，有些节往里加了哪些错误，以及原型里提到的文件夹在真跑时放在哪里。它随验收 PR 一起提交，所以之后每次真跑和发版都重复同样的步骤。

运行文件是 TOML，不是文档：它没有 troy-doc 头，所以不需要中文镜像（R12），R20 也不扫描它。troy-check 把它归为 `docs` 类，PR 6 可以改这一类（R02）。

### 4.2 键

`<home>` 是真跑用的家目录，`<scratch>` 是真跑用的临时文件夹；`<home>` 在 `<scratch>` 里面。在 Windows 上路径用 Windows 的 `\`，写成 TOML 的字面字符串（`'...'`）。

| 键 | 写的是什么 |
| --- | --- |
| `[paths]` | 路径对照表：原型里提到的每个文件夹，以及真跑时它在哪里，例如 `'C:\Users\Troy' = '<home>'` 和 `'D:\OneDrive\recipe-menu' = '<scratch>\OneDrive\recipe-menu'`。每个真跑路径都以 `<home>` 或 `<scratch>` 开头。 |
| `[environment]` | `unset`，要去掉的变量，例如 `["RECIPE_MENU_DATA"]`；`set`，要加上的变量。 |
| `[start]` | 每一节怎样开始，除非这一节另有说明：`copy`，从仓库复制的文件夹，例如 `[{ from = "tests/data/example", to = '<home>\recipe-menu' }]`；`mkdir`，要建的空文件夹；`setup`，先要运行的命令，例如 `["recipe-menu init"]`。准备命令必须以 0 退出，它的输出不做比对。 |
| `[programs]` | 只用于不是项目 Python 环境里控制台脚本的命令：它的名字和构建出的程序在仓库里的路径，例如 `hilog-demo = "build/coverage/hilog-demo"`。 |
| `[sections."<heading>"]` | 原型的一节，用它原样的标题来指明。同一个标题出现第二次时写作 `"<heading> (2)"`。 |

一节的表里可以有：

| 键 | 作用 |
| --- | --- |
| `start` | `"previous"` 表示接着上一节的文件夹状态，`"empty"` 表示没有文件，或者一个像 `[start]` 那样的表，代替默认的开始方式。 |
| `replace` | 开始之后的文字修改，例如 `[{ file = '<home>\recipe-menu\recipes\mapo-tofu.toml', text = "郫县豆瓣酱", with = "豆瓣酱" }]`。这段文字必须恰好出现一次。 |
| `write`、`delete` | 开始之后要写入给定文字的文件，以及要删除的文件。 |
| `commands` | 真跑时替换掉的一条输入的命令，附上理由，例如 `[{ typed = "recipe-menu menu new next", run = "recipe-menu menu new 2026-W47", reason = "next is 2026-W47 on the prototype's date, 10 November 2026" }]`（第 5.6 节）。 |
| `later` | 需要一个尚未验收的功能的命令，例如整节用 `[{ feature = "F09" }]`，单条命令用 `[{ feature = "F09", typed = "recipe-menu list" }]`（第 6 节）。 |
| `skip` | 无法通过管道运行的命令，附上理由，例如 `[{ reason = "edit opens Notepad" }]`（第 10 节）。 |
| `files` | 程序写出的文件，每个都在这一节的命令跑完后，和这一节里一个不是终端记录的代码块比对，例如 `[{ path = '<home>\recipe-menu\shopping\2026-W47.md', block = 1 }]`。 |

### 4.3 试点的数据

试点的原型用的是 `example-data.md` 描述的数据文件夹，里面有 7 个菜谱和一份周菜单，而 `recipe-menu init` 只创建一个菜谱。项目里已经有这份数据，作为测试数据放在 `tests/data/example/`，它的测试也会对照 `example-data.md` 检查它。所以运行文件复制这个文件夹：`[start] copy = [{ from = "tests/data/example", to = '<home>\recipe-menu' }]`，再用 `mkdir` 建空的 `shopping\` 文件夹。在数据文件夹还不存在时开始的节用 `start = "empty"`，需要 `init` 建出的文件夹的节用 `setup = ["recipe-menu init"]`，F07 原型里的两处错误就是两条 `replace` 修改。

引擎通过 git 从 `HEAD` 复制文件夹，而且只复制 git 跟踪的文件，所以证据和它的提交一致。项目里没有这样的文件夹时，由产品经理在 `docs/prototypes/data/` 下加一个，这在它的写入范围内。

## 5. 引擎命令（D102）

### 5.1 命令

```text
python troy_flow.py real-run --item <feature ID> [--keep] [common options]
python troy_flow.py real-run --all [--keep] [common options]
```

`--item` 运行这个功能验收需要的原型（第 5.2 节），并决定它的标签。`--all` 运行所有已验收功能的原型，供发版测试使用（第 11 节）。`--keep` 保留临时文件夹，方便事后查看。和每个引擎命令一样，它从不提交、不推送、不写 GitHub（F07 设计 D57）。

### 5.2 跑哪些原型（D105）

引擎在 `HEAD` 上读取需求文档里的原型表（需求模板第 3.1 节：原型、功能、文件）。它运行功能一栏写着正在验收的功能、或某个已验收功能（即 PR 6 已合入的功能）的每个 Markdown 原型。需求文档里没有这张表时，它取 `docs/prototypes/<feature ID>-*.md`。表里列出、但没有终端记录的原型，例如试点的 `example-data.md`，报告为没有终端记录，也不需要运行文件。要运行的原型没有运行文件，算一个问题。

所以每次验收都会在真实程序上把之前的原型再跑一遍，只需几秒钟。F12 进入一个项目之后的第一次验收，也要为之前功能的原型写好运行文件。在试点里就是 F05、F07、F08、F09 和 F10。

一个功能的**自己的命令**，是功能一栏写着它的原型里的命令，去掉等待别的功能的那些（第 6 节），再加上任何原型里等待它的命令。标签取决于这些命令（第 9 节）。其他所有运行了的命令也必须对得上，否则这次真跑失败。

### 5.3 读终端记录

- **终端记录**是第一个非空行以 `PS> ` 开头的代码块。其他代码块，例如 TOML 或保存下来的文件，都不运行；`files` 可以拿其中一个来比对。
- **一节**是代码块上方最近的标题。同一节的代码块在同一个状态里按顺序运行。
- **输入**是每一行以 `PS> ` 开头的行。**输出**是它后面的行，直到下一个 `PS> ` 行或代码块结束，去掉末尾的空行。
- `PS> $LASTEXITCODE` 显示前一条命令的退出码：它输出的第一行就是期望的退出码。
- `PS> $env:NAME = "value"` 在这一节余下的部分设置一个变量，先套用路径对照表。
- `PS> Get-Content <path>` 打印真跑里的那个文件，先套用路径对照表，并像命令的输出一样比对。
- `PS> <program> <arguments>` 运行程序（第 5.4 节）。引擎在空格处切分参数，`"..."` 或 `'...'` 里的文字保持在一起。
- **其他任何行**，例如管道、重定向或别的 PowerShell 命令，都不运行，报告会注明。

### 5.4 程序和它的环境（D110）

命令的第一个词是程序。在 Python 项目里，它是 `pyproject.toml` 的 `[project.scripts]` 里的一个控制台脚本，从项目的环境里运行：Windows 上是 `<environment>\Scripts\<name>.exe`，其他系统上是 `<environment>/bin/<name>`。设置了 `TROY_MODE_ENV_PREFIX` 时，环境就是它，和简报一样；否则是 `mamba env list --json` 里 `[lang] environment` 的文件夹。`[programs]` 里写了的名字改为运行那个路径。找不到程序算一个问题，报告会给出修法，例如在环境里运行 `uv pip install -e . --no-deps`（F06 设计 5.4）。

每条命令运行时：

- 激活后的环境会放到 `PATH` 最前面的那些文件夹，也放在最前面；
- `PYTHONPATH` 里放这个检出的源码根目录（`[lang] source_roots`），这样即使环境里的可编辑安装指向另一个检出，跑的也是这次提交的代码。在第一条命令之前，引擎会检查这一点：用同样的环境导入控制台脚本所在的包，检查这个包位于这个检出之内；
- `HOME`、`USERPROFILE`、`HOMEDRIVE` 和 `HOMEPATH`、`APPDATA`、`LOCALAPPDATA`，以及 Linux 和 macOS 上的 XDG 文件夹，都指向 `<home>` 里面；
- 去掉 `PYTHONIOENCODING`、`PYTHONUTF8`、`PYTHONLEGACYWINDOWSSTDIO`、`PYTHONHOME` 和 `PYTHONSTARTUP`，普通的 PowerShell 不设置它们，而它们会改变 Python 输出文字的方式；
- 加上运行文件的 `[environment]` 和这一节的 `$env:` 行；
- 工作文件夹是 `<home>`，也就是 Windows Terminal 里新开的 PowerShell 所在的位置；
- 标准输入为空，每条命令限时 60 秒。

### 5.5 安全

真跑从不碰 Troy 自己的文件夹，也不碰仓库：

- 临时文件夹是新建的空文件夹，放在系统的临时文件夹里，真跑结束后删除，除非给了 `--keep`；
- 命令、`$env:` 的值或准备路径里，如果有路径对照表没有覆盖的绝对路径，就不运行，并算一个问题：Windows 上是像 `D:\...` 这样的盘符路径或网络路径 `\\...`，其他系统上是以 `/` 开头的路径；
- 工作区必须干净，因为证据要写明一个提交；
- 引擎把报告写到 `<git dir>/troy-mode/flow/real-run-<item>-<n>.json` 和 `.md`，在临时文件夹之外不写别的东西。

它拦不住一个自己往固定绝对路径写文件的程序。试点的程序从 `--data`、`RECIPE_MENU_DATA` 或家目录找数据文件夹，所以不存在这种情况。

### 5.6 比对（D104）

真实输出和原型逐字比对，只做下面这些规范化，证据里会一一列出：

1. CRLF 和 LF 算同一种换行。
2. 行末的空格和制表符忽略不计，因为终端不显示它们。
3. 命令输出末尾的空行忽略不计。
4. 路径对照表：输出里的每个真跑路径，都显示成原型里的路径，长的先换。临时文件夹的长写法和短写法，以及 `\` 和 `/`，都算在内。
5. 原型里恰好是 `...` 的一行，可以匹配任意多行。

别的都不放宽。列与列之间的空格必须完全一致，因为中文每个字占两列，靠这些空格才能对齐。日期和数字也必须一致。

- **输出**是标准输出，接着是标准错误。一条命令两者都写时，证据会注明屏幕上的先后顺序没有得到证明。
- **退出码**在原型显示 `$LASTEXITCODE` 时比对，并且总会记录下来。
- **不是 UTF-8 的文字**算不一致。
- **取决于当天日期的词**，例如 `this` 和 `next`，通过这一节的 `commands` 在命令里替换成原型所写日期那天它们指的那一周。输出从不修改。每次替换及其理由都写进证据。
- **不一致**会附上原型的行和真实的行之间的统一格式差异（unified diff）。

### 5.7 报告

| 字段 | 内容 |
| --- | --- |
| `commit`、`program`、`system`、`date` | 代码的提交、程序的路径和 Python 版本、Windows 版本，以及真跑的时间 |
| `prototypes` | 每个原型、它的运行文件，以及每一节的开始方式和命令：输入的命令行和实际运行的命令行、期望的输出和真实的输出、两个退出码、结果（`matches`、`mismatch`、`waits for <ID>` 或 `not run`）、理由和差异 |
| `counts` | 对得上、对不上、在等待、没有运行的命令数，分为全部和这个功能自己的原型 |
| `label` | 用 `--item` 时：这个功能能否得到"在 Troy 的电脑上真跑过"（第 9 节） |
| `open_bugs` | 标题以 `Real run of <ID>:` 开头、仍未关闭的 `bug` issue（第 7.3 节） |
| `description` | PR 描述里的 "Real run" 一节（第 8 节） |
| `comments` | 那一节太长时，拆进 PR 评论的真实输出（第 8 节） |
| `problems` | 运行文件的错误、没有对照的路径、找不到的程序，或者代码位置检查失败 |

退出码和每个引擎命令一样：每条运行了的命令都对得上且没有问题时为 0，有一条对不上或有问题时为 1，引擎无法运行时为 2。

## 6. 需要后面功能的命令（D106）

原型里可能会运行一条由后面某个功能构建的命令。试点 F05 的原型讲语言和数据文件夹选项时，运行了 `recipe-menu list`，而它是 F09 才带来的。产品经理在运行文件里用 `later` 加上那个功能的 ID 标出这样的命令。

- 引擎检查这个功能在需求文档里存在。等待一个尚未验收功能的命令，报告为 `waits for <ID>`，不影响标签。
- 当那个功能正在验收或已经验收，这个标记就不再起作用：命令照常运行，并且必须对得上。因为每次验收都会把之前的原型再跑一遍（第 5.2 节），这条命令一能工作就会被检查到，不需要另外记一张清单。
- 标记里写的是已验收的功能时，报告注明它已过时，产品经理可以把它删掉。

输出也可能指向后面的功能。在试点里，`recipe-menu show mapo` 打印提示 `Run "recipe-menu search mapo" to find it.`，而 `search` 是 F10 才带来的；F09 的设计把这称为过渡状态。这样的输出和原型对得上。产品经理阅读真实输出，找出提到尚未验收功能的命令或选项的提示，把每一处连同它的功能列在 PR 的 "Points at later features" 下面，让 Troy 知道这条提示暂时还不能用。那条命令由后面那个功能自己的原型来检查。

## 7. 不一致（D107）

### 7.1 TM8

每处不一致都交给测试经理，因为原型和运行文件都是产品经理写的。一次 TM8 运行对一次真跑的全部不一致作出裁定，报告放在 Input 里（`brief --task TM8 --item <ID> --input-file <file>`）。它阅读这个功能的需求行、涉及的原型和运行文件、这些原型所属功能的设计，以及规则表。它和 TM5 一样不改任何文件。它的报告是 `done`，每处不一致一行：类型、原型、节、命令和理由。

| 类型 | 什么时候 | 接下来 |
| --- | --- | --- |
| `bug` | 程序没有做到原型或设计所说的 | 开一个 bug issue，走修 bug 流程（第 7.3 节）。Summary 写明重现测试必须证明什么。 |
| `prototype` | Troy 批准过的某个设计有意选择了这个输出，而原型没有跟着改 | 产品经理在 PR 6 里更新原型。PR 列出这处改动和那个设计的章节。 |
| `requirement` | 原型和设计不一致，而 Troy 还没有在两者之间作出选择 | 走需求变更流程（5.4）。由 Troy 决定保留哪一种输出。 |
| `later <ID>` | 这条命令需要一个尚未验收的功能 | 在运行文件里加 `later` 标记（第 6 节） |
| `setup` | 运行文件把这一节准备错了 | 产品经理改好运行文件。PR 列出第一次真跑之后对运行文件的每一处改动。 |
| `console` | 这条命令无法通过管道工作：它要读按键或回答，或者会打开编辑器 | 加 `skip` 标记并写明理由（第 10 节） |

在 Troy 审批的前几个功能（Q2）之后、只经过架构师批准的设计，不能把一处不一致判为 `prototype`：那属于 `requirement`，所以凡是改动 Troy 批准过的内容，仍由 Troy 决定。

### 7.2 再跑一次

裁定之后，产品经理再次运行 `real-run`。PR 里只展示最后一次真跑。bug issue，以及列出的运行文件和原型改动，保留了来龙去脉。

### 7.3 真跑发现的 bug

每条 bug 裁定，产品经理开一个 `bug` issue，标题为 `Real run of <ID>: <summary>`，写上原型、节、命令、提交、差异和 TM8 的 Summary。和现在一样，issue 编号就是 bug ID。TM8 已经做过分诊，所以不再运行 TM5。这个 bug 的 PR A 和 PR B 是打断第 6 阶段的旁路 PR（F07 设计 8.7）：这个阶段的提交先不推送，等 PR B 合入后，把分支变基到 `origin/main` 上，再从头真跑。

新会话走到第 6 阶段时，先运行 `real-run`。它的 `open_bugs` 列出还没修好的 bug，所以会话会接着走这些 bug 的流程，不会为同一处不一致再开一个 issue。

## 8. 证据（D108）

需求文档要求把真实输出及其对比写进 PR。PR 描述里的 "Real run" 一节由引擎写出，产品经理复制过去，而不是自己重打：

| 部分 | 内容 |
| --- | --- |
| 头部 | 代码在 `origin/main` 上的提交、程序及其 Python 版本、Windows 版本、日期，以及一行："through pipes, not a console (F12 design section 10)" |
| 结果 | 各类计数，例如 "41 commands match. 3 wait for F12. None did not run." |
| 命令 | 每条命令一行：原型、节、输入的命令、退出码和结果 |
| 调整 | 路径对照表、被替换的命令及理由、每一节怎样开始，以及那五种规范化 |
| 改动 | 这个 PR 里的原型改动及对应的设计章节，以及第一次真跑之后对运行文件的改动 |
| 指向后面的功能 | 产品经理列出的清单（第 6 节） |
| 没有证明的 | 第 10 节的一份简短清单 |
| 真实输出 | 每个原型一个折叠的 `<details>` 块，用终端记录本身的格式：每个 `PS> ` 行、套用路径对照表后的真实输出，以及真实的退出码，让 Troy 可以和原型对照着读 |

证据用命令和环境的名字来指明程序，不写本地路径；真跑的路径只在套用路径对照表之后出现；临时文件夹的其他写法一律显示为 `<scratch>`。所以证据里不含 Troy 电脑或会话里的任何文件夹，R19 的严格模式会拒绝其中一些。

GitHub 拒绝超过 65,536 个字符的描述。这一节超过 60,000 个字符时，真实输出放进报告的 `comments`，每条以 `Real run output, part <n>` 开头，那一节里给出链接。描述和评论和其他 PR 文字一样要通过 `check-text`（R19）。

运行文件会提交，让真跑可以重复。完整的 JSON 报告留在 git 文件夹里，供当前会话使用。失败那次真跑的差异写进它的 bug issue。不提交任何输出文件：那会是一份需要镜像的长英文文档，却没有任何 PR 里没有的内容。

## 10. 管道能证明什么、不能证明什么（D111）

引擎把每条命令作为子进程、通过管道运行，而不是在 Windows Terminal 里运行。真正的控制台需要 Windows 的伪控制台接口和多得多的代码，而且仍然看不到 Windows Terminal 是怎样把文字画出来的。

| 真跑能证明 | 真跑不能证明 |
| --- | --- |
| Troy 输入的命令能通过它声明的入口启动程序，跑的是这次提交的代码 | Windows Terminal 怎样画出文字：字体、是否让每个中文字占两列、颜色，以及在窗口宽度处的换行 |
| 原型里的每条命令，在五种规范化之后输出原型里的文字，退出码也和原型显示的一样 | Python 在真正的控制台里怎么做：它在那里通过控制台自己的文字接口输出，而不是输出字节 |
| 列与列之间的空格，按程序计算的每个字符的宽度 | 一条命令同时写标准输出和标准错误时，屏幕上的先后顺序 |
| 不靠 Python 的编码变量，输出也是 UTF-8 | PowerShell 自己怎样切分命令行：引号、空参数，以及 Windows PowerShell 5.1 和 PowerShell 7 之间的差别 |
| 程序在真实的文件夹里读写真实的文件，`files` 指明的、它写出的文件也对得上 | 要读按键或回答、或者会打开编辑器的命令 |
| 之前功能的原型在这次提交上仍然能用 | Troy 自己的安装：`uv tool install`、`PATH`，以及 uv 管理的 Python（试点的 ADR-0006） |
| | 运行文件替换掉的 `this`、`next` 以及其他取决于当天日期的词 |

真跑不能证明的部分，留给发版时 Troy 在自己设备上的测试（5.5），以及版本测试方案里由 Troy 执行的场景。

## 15. 怎样检查 F12

### 15.1 测试

在代码写出来之前，由另一个代理只根据本设计编写测试，使用 `unittest`、一个临时 git 仓库、一个在 `[programs]` 里指明的小示例程序，再加一个用于控制台脚本路径的假环境文件夹。用例包括：

- 终端记录：提示符、`$LASTEXITCODE`、`$env:`、`Get-Content`、不运行的行、`...`、末尾的空行、节和重复的标题，以及不是终端记录的代码块；
- 运行文件：未知的键、不存在的节、从 git 不跟踪的文件夹复制、`replace` 的文字出现零次或两次、路径对照表没有覆盖的绝对路径，以及 `later` 写了一个未知的功能；
- 原型：原型表、按文件名的后备方式、已验收的功能，以及标签；
- 比对：换行、行末空格、双向且长的先换的路径对照表、`...`、退出码、不是 UTF-8 的文字，以及两个输出流；
- 环境：用户文件夹、被去掉的 Python 变量、工作文件夹，以及包位于检出之外时会失败的那项检查；
- 报告：超过上限的描述拆进评论，以及退出码。

### 15.2 植入的 bug

代码通过之后，在一个临时副本里一次植入一个 bug，每个都必须让某个测试失败。包括：不比对退出码、不处理 `...`、路径对照表只套用一个方向、放过 `PYTHONUTF8`、运行了没有对照的绝对路径、自己有一条命令被跳过却给了标签、`later` 标记在它的功能验收后仍然起作用，以及从工作区而不是 `HEAD` 复制。数量写进 PR 描述。

### 15.3 试运行（D114）

在 PR 打开之前：

1. **在试点的原型上跑引擎。** 在构建会话的临时文件夹里，新克隆一份当前 `main` 上的 `ZJUCao/recipe-menu`，为它已验收功能的原型写好运行文件，在试点的环境里运行 `real-run --all`，对那个环境只读不写。2026-11-14 的一次探查看到这些命令都对得上，中文的列也对齐了。然后在克隆的源码里改掉一条消息，报告必须显示这处不一致及其差异；一条带有没有对照的 `D:\OneDrive` 路径的命令必须被拒绝。`D:\Troy\Projects\recipe-menu` 里什么都不改，也什么都不推送。
2. **在 `ZJUCao/troy-mode-trial` 上跑流程**，用嵌套的 `claude -p` 会话，从 PR 分支加载 troy-pstack，依据 Troy 对试运行的长期许可。先运行 troy-init 的升级。一次需求变更加入一个带 `PS> ` 原型的小命令行功能，例如一个 `wordcount` 命令，并带它走完六个 PR。它的控制台脚本通过架构变更写进 `pyproject.toml`，由提示里给出的 Troy 的回答接受。提示里给出的一条 Troy 对设计的评论，要求在原型显示 1 的地方用退出码 2，所以 PR 6 的第一次真跑对不上，由 TM8 裁定。中途换一个新会话继续。PR 6 合入时描述里带着这次真跑。按 F07 到 F09 的试运行估算，大约 15 次角色运行、15 到 25 美元，另加每个 PR 几分钟的 Actions。

### 15.4 状态

| 什么时候 | F12 在需求文档 7.2 中的状态 |
| --- | --- |
| F12 的 PR 在试运行之后合入 | 在示例项目上运行过：引擎在一份临时克隆上重放了试点的原型，并抓住了一处植入的不一致；troy-mode 带 `ZJUCao/troy-mode-trial` 的一个命令行功能走到 PR 6，做了真跑。还没有在真实项目上使用。 |
