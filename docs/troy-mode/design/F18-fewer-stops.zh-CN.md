## 1. 范围

F18 让 troy-mode 只在需要 Troy 拍板的地方停下来，正如需求 7.2 里 F18 一行所说。它分三部分：

1. **等 Troy 的环节。** 产品经理的说明书列出所有要等 Troy 的环节：需求 3.3 的审批和 5.7 的升级上报。其他环节都继续做，并在 PR 里汇报（第 4 节）。
2. **审查循环的第 3 轮，以及产出方的第 3 次失败。** 审查循环到第 3 轮仍有分歧时不再停下：由架构师裁定；如果这个循环就是架构师自己的审查，则由产品经理裁定。裁定的理由写进 PR，Troy 事后可以推翻（第 5 节）。产出方第 3 次尝试失败后（F07 设计 D64），再多试一次，这一次先检验前几次失败共同依赖的前提，之后才升级上报（第 6 节）。
3. **抽查。** 等真跑验收（F12）和角色考试（F16）积累了足够的证据，Troy 可以把前几个功能的设计 PR 和测试方案 PR 的审批（3.3 第 3 项）改成抽查：由 Claude 合并，Troy 看一部分样本，以及所有被标为有风险的 PR。本设计提出待定问题 Q15 要的规则（第 7 节）。

F18 改的是 troy-mode 在项目里的做法，比如在 `ZJUCao/recipe-menu` 里。它不改 tstack 自己的开发方式：tstack 的设计 PR、Troy 对小问题的长期同意、tstack 自己的自动合并都保持不变。

事实来自仓库的 `ecd5041`（插件 0.17.3，需求 1.63）、F07、F12、F14、F15、F16、F20 的设计、F11 试点报告、通过 `gh` 读取的 `ZJUCao/recipe-menu` 的 PR 和评论、Troy 电脑上它的三个主会话的对话记录（只读），以及 `D:\Troy\troy-mode-work\cases\` 里角色考试的用例记录。不需要任何探测，也没有运行模型。F18 改动 F04、F07、F08、F14、F15、F16 和 F20（第 9 节）。

- **troy-mode 在 v0.1 的 150 小时里有 67% 在等 Troy，此后的 139 小时里有 87%。** 试点报告的 48 小时只算了 34 条 `Waiting for Troy` 评论。
- **两个阶段里都没有一次停顿来自审查循环的第 3 轮、失败的尝试或升级上报。** F18 的第 2 部分去掉的，是在真实项目上还没发生过的停顿。
- **3.3 和 5.7 没有列出的停顿里，最大的是请求范围的结束：** 34 次，67.9 小时。在 v0.1 里，15 次中有 12 次发生在一个功能验收之后，因为每个请求只说了一个功能（试点报告问题 10；对于写明版本的请求，F07 D203 后来已经修好）。试点之后，19 次中有 14 次发生在单个阶段之后：其中 12 次，Troy 的请求只说了那个阶段，比如"Start the mock"；另有两次，请求说的是整个功能，troy-mode 却在合并已批准的设计后停下（#113、#123），D203 的"Troy 批准之后，在同一范围内继续"现在已经覆盖这种情况。

### 2.2 Troy 的审批改变了什么

Troy 批准了全部 32 个设计和测试方案 PR（v0.1 的 26 个和此后的 6 个），什么都没改：没有在任何 PR 上评论，没有要求修改，每个决定点都选了推荐的方案，或者直接批准。有两个接近例外：F03 的设计（#20）批准时两个决定点没回答，后来按推荐解决；F06 的设计（#40）按原样批准，没采用架构师两条可选的建议。其他审批也一样：需求、架构、五次架构变更、一次需求变更，以及复盘的规则。设计和测试方案的审批一共等了 58.6 小时。

### 4.2 清单放在哪里，由什么来查（D171）

清单只放一处：`troy-mode/roles/product-manager.md` 里新的一节"等 Troy 的环节"，入口技能每次启动都会读它。技能每一处停下的地方都写明等待的编号，引擎也认得这些编号：

- 新的引擎模块 `troyflow/waits.py` 存放这 11 个编号、它们的类别（审批或升级上报）和简短的英文名。
- `status --waiting <text>` 新增 `--wait <编号>`，拒绝没有清单编号的等待（退出码 1，问题 `wait`）。进度文件写成比如 "Waiting on Troy: W3, approve PR #41"。
- 在 `Waiting for Troy:` 和 `Escalation:` 标题下，评论的下一行是 `Wait: W<n>`。`status` 在 `waiting_on_troy` 里给出编号，F15 的进度 issue 也显示它。没有这一行的旧评论仍算等待，编号记为 `unlisted`。
- `retro` 按编号统计这个版本的等待和每次等了多久，并把没有清单编号的等待列为 `unlisted`，让复盘看到清单不允许的停顿。

主会话在聊天里不记录任何东西就结束回合，引擎看不见。这个缺口保留：清单和记录让这样的停顿在下一次 `status`（没有在等的东西，所以 `next` 是下一步）和复盘里显出来；如果复盘发现了不在清单上的停顿，以后可以用一个 issue 加 hook（D171 方案 B）。

### 4.3 取消的停顿（D172）

- **请求范围的结束**（S16）。功能循环的请求，比如"next feature""F04""Start the mock"或"continue"，覆盖当前版本里所有尚未验收的功能，以及之后发布步骤里直到 Troy 设备测试（W4）为止的部分：版本测试、Troy 电脑上的发布测试和发布 PR，在 Troy 验收之前这些都不是不可逆的。Troy 要限制一个请求，就说明在哪里停，比如"only F04"或"stop after the mock"。下一个版本由 Troy 的请求开始。这改变了 F07 的 D63 和 D203：只说一个功能或一个阶段的请求不再在那里结束，而第 2.1 节的 34 次停顿正是这样发生的。
- **没有任何说明要求问的问题**（S17）。按 pstack 对可逆工作的"不要卡在等人上"原则，产品经理自己决定，并在 PR 的描述和汇报里说明选了什么、为什么。会改变 Troy 将看到或保存的东西的选择属于 W6，因为它改变需求。
- **角色给 Troy 的问题**（S7）。产品经理依据已批准的需求、架构、设计和测试方案回答，把答案放进下一份简报的 Input 和 PR 的描述。只有这些文档不改就答不了的问题才算等待，即 W6。TM8 裁定为需求问题的真跑不一致（PM3 第 4 步）也一样。
- **审查循环的第 3 轮**（S8）：改为裁定，见第 5 节。
- **产出方第 3 次尝试失败**（S9）：先做一次前提尝试，见第 6 节。
- **产出方文件之外的 CI 失败**（S13）。F07 把失败的作业重跑一次（`gh run rerun <run ID> --failed`，这一项加进它的权限），再等一次检查。同一个提交第二次这样失败才是 W11。试点里唯一一次这样的失败，是 #87 检出时的 "Repository not found"，下一次推送就通过了。
- **想法已关闭、变更 PR 还开着**（S14）。F07 不合并就关闭这个 PR，并在汇报里说明。关闭 PR 在 F07 的权限之内，Troy 可以重新打开。

第 3 节的其他停顿都保留，现在各有编号。

## 5. 审查循环的第 3 轮（D173、D174）

### 5.1 谁来裁定（D173）

审查循环第 3 轮仍以 `changes-requested` 结束时（F07 第 8.3 节），F07 启动裁定，而不是升级上报：

| 循环 | 审查者 | 第 3 轮由谁裁定 |
| --- | --- | --- |
| PR 1 设计，以及 `[docs]` 设计更新（F07 第 8.7 节） | 架构师（AR2） | 产品经理，新任务 PM7，在主会话里 |
| PR 2 测试方案向接口设计师提的问题 | 接口设计师（IF3） | 架构师，新任务 AR8 |
| PR 3 和 PR 5、bug 的 PR B、规则的清理 PR | 代码审查员（CR1） | 架构师（AR8） |
| PR 4、bug 的 PR A、测试修正 | 测试经理（TM2）和代码审查员（CR1） | 架构师（AR8） |

### 5.2 裁定（D173）

1. **输入。** 三轮的审查评论、产出方报告里的回应，以及 PR 的 diff 或文档。裁定方只读未解决的意见点到的那部分文档：对 PM7 来说，这样一份多达 185,000 字符的设计不会进主会话（F14 设计 D131）。
2. **第 3 轮每条未解决的意见** 判为 `fix` 或 `does not block`，各附一句来自需求、架构、设计、测试方案或规则的理由。需要改动其中某份文档才能解决的意见属于 W6，升级上报。不挡路、但以后值得做的意见，记成给后续功能的备注（F07 第 6.6 节）或一个想法 issue。
3. **没有 `fix`：** 这个阶段继续走到合并。
4. **有 `fix`：** 产出方再运行一次，Input 里只有判为 `fix` 的意见。这次运行既不算一轮，也不算一次尝试，除非它的检查失败，那时照常算一次尝试。裁定方随后只检查这些意见，每条都改好了，阶段就继续走到合并。仍没改好的意见是 W7。
5. **裁定方不改任何文件。** AR8 和 PM7 是裁定，和 TM4、IF4 一样（F07 第 6.3 节）。

### 5.3 记录和 Troy 的推翻（D174）

- **评论。** F07 用新的固定标题发出裁定：`<Ruler> ruling, round 3: <result>`，裁定方是 `Architect` 或 `Product Manager`，结果是 `merge`、`fix`、`fixed` 或 `not fixed`；之后每条意见一行编号：`1. fix: <理由>` 或 `1. does not block: <理由>`。`status` 把这些标题读成 `rulings`。
- **PR。** 描述的 What 加一句："The <ruler> ruled at round 3 (<链接>): <一行>. Troy can overturn it on the feature's progress issue."
- **Troy 看到它**，在合并后的汇报里（用 Troy 的语言），也在功能的进度 issue 上：F15 的正文为每次裁定加一行，附链接。
- **推翻。** 在功能验收之前，Troy 可以在功能的进度 issue 上评论，或在聊天里说明哪一方对，来推翻一次裁定。这样的评论本来就被当作聊天里的消息来读（F15 D145）。F07 在进度 issue 上回复一条以 `Overturn: <裁定的链接>` 开头的评论，这是 F15 在 issue 上使用的标题里新增的一个（F15 设计 8.4），这样任何会话都能在 GitHub 上找到这次推翻；F07 并让这个功能（以及它的团队，F20）在当前阶段 PR 之后停住。它用被裁定的阶段已有的流程来执行推翻：

| 被裁定的 PR | 怎么执行推翻 |
| --- | --- |
| PR 1，设计 | 由 IF2 做一次 `[docs]` 设计更新，Input 是 Troy 的决定，由 AR2 审查（F07 第 8.7 节）；接口有变时，按旧设计已合并的阶段像返工一样重做（F07 第 11.2 节） |
| PR 2，测试方案 | 由 TM1 做一次 `[docs]` 测试方案更新；PR 4 已合并时再做一次测试修正 |
| PR 3 或 PR 5，代码 | 一个 bug：PR A 的测试和 PR B 的修复（5.3），以 Troy 的决定作为报告 |
| PR 4，测试 | 由 TE3 做一次测试修正，由 TM2 和 CR1 审查 |

这些 PR 合并后功能继续。它们执行的是 Troy 自己的决定，所以由 F07 合并；Troy 在汇报里看到它们。功能验收后，它的进度 issue 已关闭，Troy 的不同意见就和其他想法 issue 一样：一次需求变更或一个 bug（F15 D143）。

## 6. 前提尝试（D175）

产出方在一个阶段第 3 次尝试失败后（F07 第 8.5 节），F07 让它在一次全新的运行里再试一次，并给出一段固定文字，要它先检验前提：

1. 阶段的尝试次数为 3 时，`status` 给出 `next.premise: true`。F07 用 `brief --premise` 运行产出方的任务，Input 里是前三次的失败。
2. `brief --premise` 在 Task 行加上新模块 `troyflow/premise.py` 里的一段固定文字，并把 `skills/principle-attack-the-premise/SKILL.md` 加进 Read first。这段文字说：这是第 4 次尝试，前三次都失败了，失败的检查在 Input 里；改任何文件之前，用一句话写下三次尝试共同依赖的前提；用一个不改文件的检查去检验它，并说明如果前提不成立，哪个观察结果会不同；然后跟着证据走：新原因在本角色的写入范围之内就修，在范围之外（比如在某个检查里、在本角色不负责的测试里、在设计里或在环境里）就报告 `escalate`；报告的 Notes 以三行开头：`Premise:`、`Check:` 和 `Result:`。
3. 这次运行算第 4 次尝试；失败时用平常的评论标题 `<Role> attempt 4: failed`，下面附那三行。产出方文件里的 CI 失败照旧计数（F07 D261）。
4. 第 4 次尝试失败，或它报告 `escalate`，F07 就升级上报（W7）。上报信息写明前提、检查和结果，让 Troy 从证据出发。证据指向另一种等待时，比如依赖（W8）或架构（W6），上报就用那一种。
5. 产品经理自己是产出方时（PR 6），主会话在第四次尝试之前自己按这张原则卡做。

试点里失败不止一次的阶段是 F08 和 F09 的设计（#52、#59）：它们的 Python 示例各有两次过不了 CI 的 `ruff format`，而这个检查接口设计师跑不了（试点报告问题 9）。如果当时有前提尝试，它会把"设计里的示例格式不对"写成共同的前提，检查 CI 怎样格式化它们，然后发现原因在产出方的范围之外：CI 的 `ruff` 读了 `docs/`。这就是一次带着证据的升级上报；后来 tstack issue #51 让 `ruff` 不再读 `docs/`，修掉了这个原因。

## 7. 抽查（D176 到 D179）

抽查只替换 3.3 第 3 项的审批：前 `troy_approves_first` 个功能之后的功能的 PR 1 和 PR 2。在 Troy 于某个项目里打开之前它都是关的，troy-mode 从不自己打开。

### 7.1 样本（D176）

- **哪些功能。** 每三个功能抽一个，按拓扑顺序，从已审批的功能之后的第一个功能数起：第三个、第六个、第九个，依此类推。`[flow] spot_check_every` 设定这个数，默认 3。任何会话都能从 `origin/main` 上的顺序得出同样的样本，F15 的进度 issue 会说明某个功能在样本里。
- **Troy 什么时候看。** 合并之后。F07 像合并 PR 3 到 PR 6 一样合并被抽中的 PR 1 或 PR 2，在 PR 上发 `Spot check for Troy: review after the merge`，下面一行写 "What to decide is in the summary at the top of the description."，并在汇报里把它给 Troy 的摘要连同链接发给 Troy。Troy 同意时不用做什么，或者写一条评论；不同意时在功能的进度 issue 上评论，这就是一次推翻（第 5.3 节）。功能验收之后，Troy 用一个写明这个 PR 的想法 issue 表示不同意，PM6 把它当作需求变更或 bug 接收，它也算推翻了这个样本（第 7.4 节）。
- **版本发布之前。** 版本的清单 issue（F15 D144）为这个版本里 Troy 还没回应的每个抽查 PR 加一个勾选框，所以验收版本就意味着 Troy 看过了每个样本。Troy 勾上就记为看过。
- **有风险的 PR** 在合并之前等 Troy，和现在的审批一样（第 7.2 节）。

在 v0.1 里，前三个功能经过审批后，这样会抽中 F06、F09 和 F12，即后面 20 个 PR 里的 6 个；其余 14 个不经 Troy 就合并。

### 7.2 有风险的 PR（D177）

PR 1 或 PR 2 有下列任一标记时就算有风险，合并之前要等 Troy（W3）：

- **引擎**，依据状态：设计改动了一个已验收功能的接口（设计的第 3 节列出了它，F07 第 11.2 节）；PR 上的审查循环到第 3 轮需要裁定（第 5 节）；或这个阶段需要前提尝试（第 6 节）。测试方案（PR 2）也带上 PR 1 的标记。
- **架构师**，在 AR2 对 PR 1 的报告里：新的一行 `Risky: no`，或 `Risky: <理由>`，理由取自固定的清单：存储的数据格式或 Troy 保存的文件有变；Troy 的文件被删除或移动；Troy 会看到、而原型里没有的行为；网络访问、子进程或凭据（F04 设计 D280 的信号）。F07 把这一行放进审查评论，`status` 从那里读取。
- **Troy**，在 PR 合并前的任何时候：在聊天里说"F12 有风险"，或在进度 issue 上评论"risky"。F07 把它记成给那个功能的一条备注（F07 第 6.6 节），正文以 `Risky:` 开头，任何会话都能看到。

### 7.3 足够的证据（D178）

只有下面三项都成立时，troy-mode 才在一个项目里建议开抽查；每次问 Troy 时（第 7.4 节）都把它们列出来：

| | 证据 | 由什么测 | 现在在 `ZJUCao/recipe-menu` 里 |
| --- | --- | --- | --- |
| E1 | Troy 的审批：Troy 对这个项目最近 6 次 PR 1 和 PR 2 等待的回答什么都没改：每次都采纳了全部建议，没有选别的方案，也没有在评论里要求修改 | `status`，依据 PR 的评论和 Troy 的回复 | 成立：最近 6 次（F14 到 F16 的 PR 1 和 PR 2）什么都没改，32 次里也没有一次改过（第 2.2 节） |
| E2 | 真跑：这个项目上一个版本的真跑不一致，按 TM8 的裁定，没有一处来自设计或测试方案的错误 | `status`，依据验收 PR 的 Real run 一节和 TM8 的评论 | v0.1 成立，v0.2 到目前也成立 |
| E3 | 角色考试：PR 1 和 PR 2 背后那些角色的每个用例（if-example-format、if-error-rules、ar-design-review、ar-error-review 和 tm-plan-expected）在插件当前的说明书上 5 次至少通过 4 次（F16 D155 对修复的门槛） | `status`，依据 Troy 电脑上考试的用例记录（`TROY_EXAM_ROOT`，默认 `D:\Troy\troy-mode-work`）；电脑上没有这些记录时为"未知" | 不成立：架构师的用例 5 次分别通过 0 次和 1 次，另外三个没有运行 |

所以现在不建议开抽查。最早也要在以下三步之后，它们都不属于 F18 的构建：

1. 在 `main` 上为三个产出方用例做基线运行，按 `troy_exam` 的预算代码约 $51：if-example-format 和 if-error-rules 各 $18.95，tm-plan-expected $13.05。到时要等 Troy 同意。
2. 对架构师的 AR2 做一次爬坡优化（F16 设计 8.3），让两个架构师用例都到 5 次通过 4 次。设计出来之前不知道花费；两个用例跑一轮约 $60。
3. 在 recipe-menu 的 v0.2 结束时重新测 E1 和 E2。

Troy 仍可以随时开抽查；那时 troy-mode 会说明缺哪项证据。

### 7.4 打开和关闭，按项目（D179）

- **设置。** 项目的 `.troy-mode/config.toml` 里新增两个键，放在 D62 的计数旁边：`[flow] spot_checks`，取 `true` 或 `false`，默认 `false`；以及 `spot_check_every`，2 或以上的整数。troy-check 的配置读取器学会它们，项目通过 troy-init 的升级拿到，和 `[flow]` 本身一样（F07 第 12 节）。
- **那个问题。** 前 `troy_approves_first` 个功能验收后，D62 的问题多出第三个答案：Troy 继续审批（以及审批几个），打开抽查，或者让 Claude 合并以后每个 PR 1 和 PR 2。问题里列出 E1 到 E3 和 troy-mode 的建议。
- **打开或关闭。** Troy 随时可以在聊天里说，或在任何进度 issue 上评论。F07 用 D62 那种 `[rules] Set the features Troy approves` PR 记下来：`troy_approves_first` 设为到目前已验收的功能数，加一行注释写明 Troy 的决定和日期，然后合并。关闭就恢复对以后每个 PR 1 和 PR 2 的审批。
- **一次推翻就关闭抽查。** Troy 推翻了一个抽查的 PR，或推翻了对某个 PR 1 或 PR 2 的裁定（第 5.3 节）时，证据已不成立，F07 立刻用同样的 `[rules]` PR 关闭抽查，并说明。关闭只会增加等待，所以 troy-mode 可以自己做；重新打开由 Troy 决定。
- **按项目。** 每个项目的配置各自保存这个设置，所以 `ZJUCao/recipe-menu` 和第二个项目可以各自选择。

### 7.5 和功能团队、合并的配合（D179）

- **团队（F20）。** 有风险 PR 的等待只停住它自己的团队，以及在等它这个功能的团队，并归进列出所有等待中 PR 的那一条消息（Q23）。抽查的 PR 不停住任何团队：汇报在单独一行"抽查，合并后看"下列出它。一次推翻让它所在功能的团队在当前阶段 PR 之后停住，和需求变更停住受影响的团队一样（Q24），`held` 的原因是 `overturn`。样本按拓扑顺序数功能，所以哪个团队做一个功能，不影响它是否被抽中，和 `troy_approves_first` 一样（Q23）。
- **合并。** 抽查下的 PR 1 或 PR 2，F07 完全像合并 PR 3 到 PR 6 那样合并：对推送的头提交运行 `wait-checks`，按 R24 rebase 到最新的 `main`，再 `gh pr merge --rebase --match-head-commit`。troy-mode 在项目里不用 GitHub 的自动合并：Troy 的私有仓库没有分支保护（需求第 6 节），R24 也需要 rebase 检查。tstack 自己的自动合并不变。

### 13.5 第 1 部分的构建定下的事

第 1 部分的构建定下了上面各节没有写死的几点，它的测试和试运行检查这些点。

- **等待那一行。** `Wait: W<n>` 是 `Waiting for Troy:` 或 `Escalation:` 标题下第一个非空行。缺这一行，或者编号不在 W1 到 W11 之内，都读作 `unlisted`。`status --waiting` 必须带 `--wait <编号>`，否则被拒绝（退出码 1，问题 `wait`）。`status` 在 `wait` 里给出编号，`waiting_on_troy` 以它开头："W3, approve PR #41"，或者 "W3, PR #7: Waiting for Troy: approve this PR"。
- **`next`。** 新增四个键：`premise`，正好 3 次尝试时为真；`escalate`，要升级上报的等待，从第 4 次尝试起或者裁定为 `not fixed` 之后为 W7，直到记下一次升级上报；`ruling`，带裁定方、它的任务和最新结果；以及 `overturn`。新增三个动作：`ruling`、`ruled-revision` 和 `overturn`。
- **推翻的结束。** 引擎分不清执行推翻的 PR 和这个功能的其他 PR，所以这些 PR 合并后，troy-mode 在进度 issue 上用第二个标题 `Overturn carried out: <裁定的链接>` 记下结束。
- **已合并 PR 的裁定。** 进度 issue 也显示这个功能已合并 PR 的裁定。每次同步都读每个已合并阶段 PR 的评论，每个 PR 约要半秒，所以已合并 PR 的裁定在每个检出里只读一次，存在共用 git 目录的 `troy-mode/rulings.json` 里。
- **报告字段。** 角色报告没有 Notes 字段（F04 第 5.2 节），所以前提尝试的三行写在它 Summary 的开头，AR2 的 `Risky:` 一行写在 Summary 的末尾。第 1 部分加上这一行，第 2 部分读它。
- **重跑。** `ci_failures` 新增 `rerun`，来自运行的 `attempt` 字段，所以产出方文件之外的失败只重跑一次，换了会话也一样。
- **AR8 和 `--premise` 用在哪里。** AR8 的任务简报用于功能的第 2 到 5 阶段，以及测试修正、bug PR、版本测试 PR 和规则的清理 PR。`brief --premise` 接受产出方任务 IF1、IF2、TM1、TM7、DV1 到 DV5、TE1 到 TE6 和 AR1，并把插件里这张卡片的绝对路径加进 Read first。
- **前提尝试里的环境。** 试运行的第一次前提尝试里，测试工程师找到了原因，即 `MAMBA_ROOT_PREFIX` 设错了，接着却在自己的检查命令上设好这个变量，没有升级上报。现在前提文字写明：原因在环境里时，即使角色自己的命令能绕过去，它也在写入范围之外；下一次前提尝试就带着证据升级上报了（W7）。
- **模板。** 不改模板，因为改模板会让所有考试用例都要跑。规则模板里的 R17 一行和两条模板注释仍说循环会升级上报，等下一个改模板的 PR 再改。

第 1 部分的检查：

- **测试。** 一个独立的代理在写代码之前，按本设计和构建的约定写了 104 个测试，放在七个新模块里。其中 99 个在旧引擎上失败，每个都因为功能缺了一块；另外 5 个覆盖不变的行为。这个代理还更新了约定改变其预期输出的已有测试。埋 bug 之后，构建又加了 4 个测试，检查团队的 `premise` 和 `escalate`。各测试套件都通过：flow 1,468、hooks 436、init 282、checks 751、dev 324、exam 420。
